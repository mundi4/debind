## 1. 지금 나가는 모양 — 전송 포맷 v1

아래는 코드가 내는 실물이다. 프로필을 세워 `BuildExportPayload`를 돌려 찍은 것이고 손으로 쓴
것이 아니다.

```lua
{
  v = 2,                        -- 스키마 버전. BringPayloadForward가 사다리를 태우거나 거절한다
  class = "DRUID",              -- 보내는 쪽 클래스. shared.classes를 읽으려면 필요
  states = {                    -- 참조된 것만. 하나도 없으면 이 필드 자체가 없다
    ["$state3"] = { mode = 0, initialValue = true, displayMessage = "Burst" },
  },

  -- 여기서부터는 저장 구조 그대로다. 경로가 곧 주소이고, 서술 테이블이 없다.
  shared = {
    GENERAL = {
      { type = "spell", value = 774, key = "F", seq = 3, priority = 2,
        conditions = { combat = true, units = { target = {} } } },
      { type = "spell", value = 8936, key = "F", seq = 7,
        conditions = { ["$state3"] = true } },
      { type = "setstate", key = "CTRL-9", seq = 1,
        setstate = { mode = "toggle", state = "$state3" } },
      { type = "macro", value = "Kick+Pet", key = "SHIFT-G", seq = 1 },
      { type = "spell", value = 5176 },           -- 키가 없다 = 아무 그룹에도 안 속한다
    },
    classes = {
      DRUID = {
        [0] = { { type = "spell", value = 8921, key = "F", seq = 2,
                  conditions = { forms = 6 } } },
      },
    },
  },
  char = {                      -- guid를 뗀다. "이 캐릭터"라는 뜻
    [0] = { { type = "spell", value = 22812, key = "SHIFT-G", seq = 1 } },
  },
}
```

읽는 쪽이 알아야 할 것:

- **경로가 주소다.** `shared.GENERAL` / `shared.classes[직업][특성]` / `char[특성]`, 곧 프로필이
  저장하는 그 모양이다. 서술 테이블도 레이어 **번호**도 안 나간다(2~6이 "내 클래스"라 안 통한다).
  `spec = 0`은 "그 직업 전체"이고 상한은 `MAX_SPEC`이다. `char`에서 guid를 뗀 것이 유일한 번역이다.
- **`key`가 액션에 있고, 그것이 곧 그룹이다.** 같은 `key`면 한 묶음이고, 그것을 선언하는 층이
  없다. 한 키가 레이어 둘에 걸쳐도 갈리지 않는다. 주소가 둘일 뿐이다.
- **키가 문자열이 아니라 숫자일 수 있다.** 승인은 했지만 아직 키를 안 준 묶음이 그렇게 나간다.
  `type(key) == "number"` 하나로 갈린다. 받는 쪽은 그 번호를 자기 프로필 안에서 다시 매긴다.
- **묶인 적 없는 액션은 키 없이 나간다.** 아무와도 같은 그룹이 아니라는 뜻이고, 규칙이 아니라
  표현이다.
- **`seq`는 보낸 쪽 번호 그대로다.** 저장할 값이 아니라 이 문자열 안에서만 뜻이 있는 차례이고,
  받는 쪽이 `MAGIC + seq`를 거쳐 자기 번호로 바꾼다. 배열 차례에 안 기대는 이유는 그것이
  암묵적이어서다. 디코드부터 배치까지 아무도 다시 담지 않아야 성립한다.
- **`MACRO`의 `value`는 이름 문자열이다.** 본문은 안 실린다(6절 "★ 매크로는 이름만 나간다").
  슬롯 번호를 든 `MACRO`는 애초에 존재할 수 없는 값이고, 그런 것이 실려 오면 문자열이 통째로
  거절된다(3절 "문").
- **`setstate`가 붙으면 `value`는 없다.** 비트팩 대신 이름 축이다. `setcustom`은 손 안 댄
  `value` 그대로다. 커스텀 **대상**이라 인덱스가 구조적이다.
- 조건은 걸린 것만 실린다. 안 건드린 축은 필드 자체가 없다.
- **배지 달린 액션은 안 나간다**(2절).
- 액션 필드 명단은 `Export.lua`의 `ACTION_FIELDS`이고 `KEYS_TO_SAVE`와 동기화가 강제된다
  (`tools/check-export-fields.js`). 예외는 `imported` 하나다.

봉투는 `DEB1:<printable>`이다. **버전이 둘인 이유**는 압축기를 갈면 옛 문자열이 죽어야 하고
필드를 더하면 안 죽어야 하기 때문이다. 한 숫자로 두면 읽는 쪽이 그 둘을 같은 사건으로 다뤄야 한다.

`DecodeExportString(str)`은 페이로드 또는 `nil, 사유`를 준다. 사유는 `NOT_A_STRING` /
`NOT_A_DEBIND_STRING` / `UNSUPPORTED_ENVELOPE` / `LIBS_MISSING` / `BAD_ENCODING` /
`BAD_COMPRESSION` / `BAD_PAYLOAD` / `UNSUPPORTED_SCHEMA` / `SCHEMA_TOO_OLD`.
**붙여넣기는 남이 준 입력이라 전부 실패할 수 있고 어느 것도 오류를 던지지 않는다.**

크기 감각: 액션 5개 289자, 30개 464자, 100개 709자, 300개 1363자.

### 커스텀 상태는 이름으로 싣는다

액션의 상태 참조는 저장에서는 인덱스인데(SETSTATE의 `mode|index` 비트팩), 전송 포맷에서만
**이름 축으로 정규화한다**: `{ mode = "toggle", state = "$state3" }`. 참조된 상태의 정의는
`payload.states` 매니페스트가 이름째 든다.

- 인덱스는 항상 "성공"하는 참조라 받는 쪽 상태 3을 조용히 가리킨다. 이름이면 댕글링이 보이고,
  `BINDING_ISSUE_UNDEFINED_STATE`가 그것을 빨갛게 띄운다.
- `$state1~5`는 커스텀 상태 재설계(`redesigning-custom-states.md`) 뒤에도 유효한 이름이라,
  이 포맷은 저장 표현에 대해 아무것도 미리 정하지 않는다.
- **그리고 이것이 3.3이 v1을 읽을 수 있는 근거다.** 3.3이 상태를 이름으로 갈아도 v1 페이로드는
  이미 이름을 들고 있다.

### 스키마 버전 — 이제부터는 올린다

> **소유자(2026-08-19)** — *"migration 가능하게 해야지"*, *"export/import 기능을 3.3까지
> 기다리는건 너무 늦어"*

배포 전까지는 안 올렸다. v1 문자열이 저장소 밖으로 나간 적이 없어서 호환을 지킬 상대가 없었고,
손에 있던 옛 문자열은 소유자가 지웠다. **그 근거가 3.2 배포로 사라졌다.** 남의 공략글과 남의
메모에 붙은 문자열은 지워달라고 할 데가 없다.

**첫 범프가 왔다 (2026-08-21, `SCHEMA_VERSION` 2).** 커스텀 상태 이름이 아니라 조건 중첩이
먼저였다. 조건이 `action.conditions` 안으로 들어가면서 전송 액션의 모양이 바뀌었고, 안 올리면
v1 문자열이 관문을 그대로 통과한 다음 `BuildAction`의 화이트리스트에서 **조건을 전부 잃는다.**
무조건 액션으로 도착해 조건부 밴드가 아닌 자리에 서고, 키를 받으면 작성자가 제외한 상태에서도
발동한다. 거절이 아니라 조용한 손실이라 더 나쁘다.

3.2 쪽에 들어가 있던 것이 그 사다리를 가능하게 했다:

- `payload.v`가 문자열에도 있고 서랍에 저장된 페이로드에도 남는다. 3.3이 v1을 알아볼 근거가
  이미 디스크에 있다.
- **두 문이 같은 함수로 묻는다.** `BringPayloadForward` 하나이고, 붙여넣기(`DecodeExportString`)와
  서랍에서 열기(`GetBatchPayload`)가 둘 다 지난다. 붙여넣기 쪽에만 마이그레이션을 얹으면
  **서랍에 쌓여 있던 것만** 검사 없이 새 코드로 들어간다. `tests/batch_spec.lua`가 그 문을 잡고 있다.

**단계는 자기가 올릴 판을 정확히 짚는다.** `MigrateLayer`는 `dbver <= N`으로 여는데 이쪽은
`payload.v == N`이다. `<`로 열면 세상에 없던 번호까지 같이 태우게 되고, 그건 모양을 모르는
것을 추측으로 읽는 것이다. `SCHEMA_TOO_OLD`가 그것들을 거절하라고 있는 자리다.

v1 -> v2 단계는 `Profile.lua`의 `dbver <= 5`와 **같은 변환**이고, 무엇이 조건인지는 양쪽 다
`Constants.IsConditionField` 하나에 묻는다.

## 2. 익스포트

### 공유 창

`Debind/ExportUI.lua`, `ExportUI.xml`. 메인 창의 탭 하나다.

**클립보드에 직접 넣는 길이 막혀 있어서 이 창이 있다.** 블리자드가 특성·편집 모드·청사진에서
쓰는 `CopyToClipboard`를 애드온 코드에서 부르면 `ADDON_ACTION_FORBIDDEN`이다. 프로브로 재봤다
(12.1.0.69299, 2026-08-15). 복사 창은 우리가 고른 모양이 아니라 **유일한 문**이다.

- 레이어가 그룹 머리글, 그 안이 액션. **액션이 체크 대상**이고 tristate 3단이다
  (전체 → 레이어 → 액션). 기본은 전부 선택.
- 머리글은 블리자드의 `ListHeaderThreeSliceTemplate`이다. 퀘스트 로그의 `ListHeaderVisualTemplate`이
  아닌 이유는, 이 목록에서 레이어는 고르는 대상이 아니라 자르는 선인데 그쪽 바 아트는 전자로
  읽히기 때문이다. 영역이 갈린다. **왼쪽 체크박스는 선택, 나머지 바는 접기/펴기.**
- **열면 전부 접혀 있다.** 펼쳐 두면 액션이 길게 늘어져 이 창의 축인 레이어가 파묻힌다. 접기는
  보기 상태일 뿐이라 **접힌 레이어도 그대로 내보내진다.** 그래서 목록이 둘이다. `self.layers`가
  "무엇이 선택됐나", `BuildDisplayList`가 "무엇을 그리나".
- **선택은 그리기 전에 세운다.** 목록을 먼저 깔면 그 사이에 만들어진 행이 빈 선택을 보고 그려지고,
  뒤이은 갱신은 그때 존재하는 프레임에만 닿는다.
- **행에는 체크박스가 없다.** 선택된 행을 메인 창과 같은 아트로 밝힌다(`auctionhouse-ui-row-select`).
  상자를 세 단으로 늘어놓으니 레이어의 상자와 액션의 상자를 눈으로 가를 수가 없었다.
- tristate 중간 상태는 체크가 아니라 대시(`common-icon-minus`)다. 흐린 체크는 한눈에 "전부"로
  읽히는데 그게 이 상태가 절대 말하면 안 되는 것이다.
- 목록은 이름순이되 **한 키의 액션은 붙여 놓는다.** 이름순은 메인 목록이 정한 규칙이고(한
  레이어짜리 목록은 발동 순서를 말할 자격이 없다), 그룹은 이 창이 실제로 보내는 단위라 한
  덩어리로 보여야 한다. 그룹을 그 그룹 첫 액션의 이름으로 정렬해서 둘을 같이 만족시켰다. 그룹
  사이는 머리글이 아니라 경계선이다.
- **비활성 스펙 레이어도 목록에 선다.** 데이터가 이미 있고, 없으면 세팅 절반을 공유하려고
  캐릭터를 갈아야 한다.
- **메인 창에 수명이 안 묶여 있다**(복사 창 이야기). 익스포트한 창을 닫았다고 복사하려던
  문자열이 같이 사라지면 안 된다. 문자열은 창 안이 아니라 별도 다이얼로그에 뜬다. 한 번 읽고
  복사하고 다시 안 보는 물건이라 붙박이 상자는 대부분의 시간 동안 높이만 먹는다. 편집은 막혀
  있다. 반쯤 지워진 문자열의 사고는 **남의 컴퓨터에서** 난다.
- **선택이 바뀌면 떠 있는 복사 창을 닫는다.** 접기/펴기로는 안 닫는다. 그건 선택을 안 바꾼다.

### 무엇이 나가고 무엇이 안 나가나

- **잘못된 액션도 그냥 싣는다.** 검사하지 않는다. 받는 쪽에서 빨간 글씨로 보이고 지우면 된다.
  이것 하나로 "보내는 쪽 클래스 주문을 받는 쪽이 못 가졌을 때" 류의 질문이 전부 사라진다.
- **배지 달린 액션은 안 나간다** (2026-08-15, 소유자 결정).

  > *"accept하지 않은 액션은 우리 액션이 아니니까 내보내지 않는다. 이 결정이 바뀌지는 않을 것 같다."*

  내보내기가 하는 말은 "이게 내 세팅이다"인데 배지 달린 것은 아직 내 것이 아니다. 그걸 실어
  보내면 **결정 안 된 것이 사람을 건너 퍼진다.** 받는 쪽에서 또 배지를 달고 서고, 그 사람도
  판단할 근거가 없다.
- **판정은 `IsExportable` 하나이고 선을 만드는 쪽과 창이 같은 함수를 부른다.** 레이어 머리글
  개수도 [전부 선택] 총계도 고를 수 있는 행도 전부 창의 목록에서 나오므로, 그 목록과 실제로
  나가는 것이 갈리면 창이 "12개"라 해놓고 9개를 보낸다. 한 함수를 두 번 묻는 것이 그걸
  **합의가 아니라 사실로** 만든다.
- **한 키가 반만 나갈 수 있다.** F에 승인된 둘과 배지 달린 하나가 있으면 둘만 나간다.
- **`BuildLayers`는 `EnumerateAllProfileLayers`로 훑는다.** 손으로 `1..11`을 도는 것과 게임에서는
  같은 열한 개지만 `/debtest`에서는 아니다. 격리가 그 열거자를 갈아끼운다.
- 전부 배지면 페이로드가 빈다. 그 자리는 `EXPORT_EMPTY`가 든다.

**검사는 두 층이다.** `tests/export_spec.lua`가 넷을 본다(안 나가는 것, 골라도 안 나가는 것, 한
키가 반만 나가는 것, 배지 없는 숫자 키는 그대로 나가는 것). 헤드리스가 원리적으로 못 보는 것,
곧 창의 목록과 문자열이 서로 갈리는 것은 `/debtest`의
`Export: the window's count is what the string carries`가 본다.

⚠ **스펙은 액션 타입 다섯 개만 왕복시킨다**(SPELL·MACRO·MACROTEXT·SETSTATE·SETCUSTOM).
나머지 열 개는 실물로 한 번 확인했을 뿐 `tests/export_spec.lua`에 안 걸려 있다.

⚠ **LibDeflate는 fengari에서 압축을 못 푼다.** 실제 lua 5.1(luajit)·5.4에서는 왕복하는데
`node tests/run.js`에서만 실패한다. 라이브러리도 우리 코드도 아니고 와우는 5.1이라 게임에서는
안 닿는다. 스펙이 두 겹으로 갈라져 있고 어느 쪽이 돌았는지 매번 찍는다.

## 3. 임포트

### 세 걸음

```
붙여넣기  →  서랍          →  [가져오기]        →  오버뷰에서 병합
            (배치로 쌓임)     레이어를 골라       배지를 떼거나 키를 준다
                              프로필에, 배지 달아서
```

흔한 경우는 버튼 두 번이다. [가져오기] 다음 [N개 모두 받기].

**서랍은 아직 병합을 시작하지 않은 것을 담는다.** `DebindStorage/Import.lua`의
`AddBatch` / `GetBatches` / `GetBatch` / `DeleteBatch` / `GetBatchPayload` / `CountBatch`.

- **못 읽는 것은 서랍에 안 들어간다.** 붙여넣는 자리에서 거절한다. 열 때마다 실패하는 줄이
  서랍에 앉아 있으면 안 된다.
- **커밋해도 서랍에서 안 지운다.** 승인 전에 배치째 지우고 다시 시작할 수 있어야 하고, 그러려면
  원본이 남아 있어야 한다. 행에 "이미 가져옴" 표시만 붙는다.
- 배치가 든 것은 `id`, `received`, `payload`, `name`, `class`, `committed`. 전부 저장 가능한
  평범한 값이라 `/reload`를 건넌다.
- **지운 id는 재활용 안 한다.**
- **자동 삭제는 없고 만료 판정도 없다** (2026-08-15, 소유자: *"자동 삭제가 지금 없으니까 핀도
  보여주지마"*). 실행이 없는 판정은 화면에 아무 일도 안 일어나는 날짜를 띄우는 것이었다. 남은
  것은 받은 날짜 한 줄이고 그건 사실이다. **설계가 기각된 게 아니라 안 지어졌다**(7절).

### [가져오기]가 묻는 것

행의 [가져오기]가 대화상자를 연다. **결정이 press와 같은 순간에 일어나서 모드가 없다.** 예전에
행에 붙어 있던 `[ ] 단축키는 빼고` 체크박스는 한순간에만 뜻이 있는데 배치에 저장까지 되어
세션을 건너 살아남았다.

```
가져오기 — <배치 이름>

[x] 공유 / 일반
[x] 공유 / <직업명>
[x] 캐릭터 / 일반
[x] 캐릭터 / <직업명>

                    [가져오기]  [취소]
```

- **줄은 실제로 놓일 수 있는 것만 선다**(`CollectImportLines`). 없는 레이어와 갈 데가 없는
  레이어는 읽는 사람에게 같은 것이다. 켜도 꺼도 아무 일이 없는 체크박스이고 둘을 구별할 방법이
  없다. 줄이 하나도 없으면 대화상자를 안 열고 `IMPORT_NOTHING_PLACED`로 답한다.
- 넷 다 **기본 켜짐**이다. 다 가져오는 것이 온 목적이고, 이 상자는 덜 가져오려는 사람을 위한
  것이다. 넷을 켜게 만들면 대화상자가 통행료가 된다.
- **줄 이름은 문자열 안의 것을 부른다**(`IMPORT_BRING_LINE_*`). 목적지가 아니다.
  `GetLayerLabel` / `GetSideTabaLabel`은 전부 **지금 캐릭터 기준으로** 이름을 지어서 못 쓴다.
  그대로 부르면 마법사 레이어에 "드루이드"라고 적히고, 캐릭터 탭에는 보낸 사람이 아니라 **내**
  캐릭터 이름이 붙는다.
- **캐릭터 이름은 문자열에 없다.** 일부러 안 싣는다. 공개 채널에 붙일 것이 캐릭터 이름을 나르면
  안 된다. 그래서 캐릭터 줄은 이름 없이 "캐릭터 / …"로만 부른다.
- **어느 줄을 골랐는지는 배치에 안 남는다.** 그 답은 딱 한 번의 press만큼 값이 있다. 저장하면
  일주일 뒤에 돌아온 사람이 자기가 안 고른 것을 받는다.
- **하나도 안 고르면 버튼이 꺼진다**(`UpdateAcceptButton`).
- ESC는 `UISpecialFrames`에 안 넣는다. `CloseSpecialWindows`가 목록에 있는 떠 있는 프레임을
  전부 닫아서 한 번 누르면 뒤의 창까지 같이 닫힌다. `OnKeyDown`에서 ESCAPE만 잡고 나머지는
  `SetPropagateKeyboardInput(true)`로 흘려보낸다.

### 도착한 것은 내 키에 앉지 않는다 (2026-08-16)

**도착하는 키는 전부 합성 키(숫자)로 바뀐다.** 보내는 쪽의 실키도 포함이다.

그 전에는 가져온 액션이 보내는 쪽이 쓰던 키에 그대로 앉았다. 받는 사람이 이미 그 키를 쓰고
있으면 두 세트가 한 세트가 되는데, **어느 멤버가 어디서 왔는지를 적어두는 필드가 아무 데도
없었다.** 배지는 액션이 발동하지 않게 할 뿐 세트를 갈라놓지 못하므로, 격리가 열어두려던 그
결정이 묻기도 전에 사라져 있었다.

키가 곧 그룹이라 묶음은 그대로 살아남고, 받는 사람이 갖고 있던 것은 손대지 않는다.

- **도착한 키는 `imported`의 값이 된다.** `"SHIFT-G"`이거나, 키 없이 왔으면 `true`. 그 자리에
  있던 배치 번호는 출하 코드에서 읽는 데가 한 곳도 없었다. `DeleteBatch`가 서랍 행을 아무 가드
  없이 지우므로 배치 번호는 어차피 포인터로 못 쓴다.
- 머리글은 `Imported Binding #1 (was SHIFT-G)`이다. 번호는 그룹 자신의 합성 키다. 최고 + 1로
  발급되고 전부 키를 받으면 1부터 다시 시작하므로 작게 유지되고, 옆 묶음을 수락해도 커서 밑에서
  안 바뀐다. 화면상의 순번이었다면 그렇게 된다.
- 한국어 로케일에는 이 두 문자열을 두지 않았다. 영어로 나간다.
- **키를 정하는 것이 곧 승인이다**(4절).

### 자리 — `(scope, class, spec)`

`DebindStorage.ImportAddress(scope, class, spec)`. **레이어 ID가 아니다.** 레이어 ID는 지금
캐릭터가 보는 뷰이고, 마법사의 레이어는 드루이드 세션에서 ID가 아예 없다.

| 보낸 쪽 | 받는 쪽 |
|---|---|
| `general` | `shared.GENERAL` 그대로 |
| `class / MAGE / spec N` | `shared.classes.MAGE`의 spec N. **내 직업으로 바꾸지 않는다** |
| `character / spec N` | 이 캐릭터의 spec N |
| `class / NOSUCHCLASS` | **자리 없음.** `C_CreatureInfo.GetClassInfo` 명단에 있는 것만 받는다 |
| `character / spec 4` (3특성 직업이 받음) | **자리 없음. 세어서 뺀다** |

- `PlaceImportedActions(placements)`의 원소가 `{ scope, class, spec, action }`이다.
  `Profile.lua`의 `StoredActionsAt`이 저장 테이블을 직접 짚는다. 로드 안 된 레이어에는 씌울
  레이어 객체가 없어서 `ProfileLayerProto`를 저장 테이블에 씌운 스크래치 하나를 돌려 쓴다.
- **캐릭터 자리는 `db.char`에서 받는다.** `characters[guid]`는 아직 안 붙어 있을 수 있고,
  그때 거기 쓰면 `CleanUpDB`가 나중에 붙일 그 테이블이 아니다.
- **모르는 직업 이름을 받으면 안 되는 이유**는, 직업 이름이 저장의 열쇠라 아무 문자열이나 받으면
  어느 화면도 못 닿고 `CleanUpDB`도 못 치우는 테이블이 붙여넣을 때마다 하나씩 늘기 때문이다.
- **`skipped`는 액션 수다.** 주소가 액션마다라 세는 단위도 액션이다. **안 고른 줄은 skip이
  아니다.** 둘 다 안 들어오지만 하나는 읽는 사람이 준 답이고 하나는 이 버전이 놓을 데가 없는
  것이다. 단, **줄이 아예 없는 것은 안 고른 것이 아니다.** 모르는 scope는 체크박스로 물은 적이
  없으니 필터에서 조용히 빠지면 안 된다.

### 문 — 우리가 만들 수 없는 것이 하나라도 있으면 문자열을 통째로 거절한다

> **소유자(2026-08-18)** — *"와우의 매크로는 절대 index나 숫자로 보관 사용하면 안 돼."* /
> *"순전히 내 클라이언트에만 존재해도 깨지는 거다."* /
> *"우리 애드온이 만들 수 없는 문자열을 직접 만들어서 거기서 오류가 났다면 나머지도 믿을 건 못 된다."*

`PayloadIsImpossible`(`Import.lua`) 하나이고, **붙여넣을 때(`AddBatch`)와 서랍에서 열 때
(`GetBatchPayload`) 둘 다** 지난다. 읽는 쪽에도 서 있으므로 문이 생기기 전에 들어간 배치도 같이
닫힌다. **이 문 뒤에 고쳐 쓸 것이 없다는 뜻이고**, 거절할 것만 있다. 사유는 `IMPOSSIBLE_PAYLOAD`
이고 화면에는 `IMPORT_FAILED_DAMAGED` 한 줄로 나간다.

보는 것 셋:

- **`VALUE_SHAPES`에 어긋나는 액션.** 타입마다 `value`가 무엇인지 적은 표다. 값 모양만이 아니라
  **모르는 타입**도 여기서 걸린다. 판정은 **만들어진 액션**에 대고 하지 실려온 표에 대고 하지
  않는다. 포맷이 `SETSTATE`를 값 없는 `setstate` 테이블로 적기 때문에, 실려온 모양을 보면 그
  사실이 두 군데에 남는다.
- **`payload.class`가 모르는 직업 이름인 것.** 툴팁이 `%s`로 찍어서 던지고, 그 배치는 이미
  디스크에 있다.
- **NaN 키.** 테이블 인덱스로 쓰이는 순간 던진다.

**거짓 거절이 이 문의 비싼 실패다.** 멀쩡한 문자열을 거절하면 사용자는 똑같이 실패할 문자열을
다시 받으러 간다. 그래서 열다섯 타입을 하나씩 코드에서 짚었고, 멀쩡한 것이 안 걸리는 쪽 스펙을
같은 무게로 붙였다.

**감수한 것.** 포맷이 엄격해졌으므로 나중 버전이 값 모양을 하나 늘리면 옛 클라이언트가 그
문자열을 "상했다"고 거절한다. 그건 스키마 버전이 답할 일이고, 이 결정이 그 규율에 무게를 더 싣는다.

**답이 두 번 바뀌었다.** 처음에는 그런 액션을 페이로드 훑는 자리에서 액션으로 안 쳤다. 소유자가
꺾었다(*"조용하게 액션이 사라지는 건 틀린 답이다"*). 다음 안은 값만 떨어뜨리고 액션은 들이는
것이었는데 근거가 거짓이었다. **기존 액션의 대상을 바꾸는 길이 이 애드온에 없다.** 드롭은 언제나
새 액션을 만들고, `action.value`에 쓰는 자리는 매크로 본문 편집기와 그 취소뿐이다. 그러면 받는
사람이 할 수 있는 일은 삭제 하나고, 빨간 줄은 고치라는 말이 아니라 치우라는 말이 된다. 세 번째
답만이 사용자가 실제로 할 수 있는 일을 남긴다. 고칠 대상이 프로필 안의 행이 아니라 **문자열**로
옮겨가고, 문자열은 다시 받으면 된다.

**안 고른 안 — 익스포트가 같은 것을 걸러내기** (소유자 결정: 그대로 둔다). 그런 액션은 이
애드온이 못 만든다. `MACRO`를 만드는 자리는 픽커와 커서 드롭 둘뿐이고 둘 다 `GetMacroInfo`가 낸
이름을 넣는다. 이 갈래에 닿으려면 SavedVariables를 손으로 고쳐야 하고, 그건 문이 말하는 "누가
손댔다"가 참인 경우다. **없는 위험에 문을 하나 더 세우지 않는다.** (리뷰가 이것을 *"옛 Debounce
데이터가 슬롯 번호를 들고 있다"*로 올렸는데 그 전제는 사실이 아니다.)

**안 고른 안 — `type`·`icon`·`name`만으로 그려서 "알 수 없음".** 그 두 필드가 문제의 타입들에는
비어 있다. `MACRO`·`SETCUSTOM`·`COMMAND`·`WORLDMARKER`는 이름과 아이콘을 그릴 때마다 `value`로
다시 뽑으므로, 그 셋으로 그리면 타입 하나만 남는다. 살리려면 익스포트가 `name`/`icon`을 채워
보내야 하는데 그건 파생값을 문자열에 굽는 것이라 클릭 시점 재측정 원칙과 어긋난다.
**이 결정과 떼어서 볼 주제로 남긴다**: 깨진 경우와 무관하게, 받는 쪽이 그 사람이 무엇을 걸어뒀는지
보는 편이 나을 수 있다는 물음은 그대로 열려 있다.

## 4. 배지 = 격리

**배지를 달고 있는 동안은 바인딩 빌드에 넣지 않는다.** 사용자가 배지를 제거해야 비로소 실제로
동작한다. **이 컨셉 전체가 이것 위에 서 있다.** 없으면 붙여넣는 순간 남의 키가 실제로 걸리고,
뭐가 달라졌는지도 모른 채 되돌릴 방법도 없다.

- 임포트하면 프로필에는 들어가지만 격리 상태다. 회색으로 보이고 아무것도 안 건드린다.
- 배지 제거가 곧 활성화다. 그래서 임포트가 내 바인딩을 바꾸는 순간이 임포트할 때가 아니라
  **내가 승인할 때**가 된다.
- 막는 자리는 `BuildKeyMap`의 `if (action.key)` **바깥**이다. `ActiveActions[action]`은 이슈가
  있어 `KeyMap`에서 빠진 액션에도 붙는다. 그 필드의 뜻은 "빌드에 들어감"이 아니라 **"키가 있음"**
  이라, 안쪽에 걸면 회색이 안 된다. 바깥에 걸어야 키 없는 액션과 같은 대접이 되고 그때 공짜다.
- **표시는 이름 색과 아이콘 위 점 둘 다.** 회색이 두 뜻을 갖는 것이 실제 문제였다. 격리된 액션은
  어차피 회색이 되는데 "키 없음"과 구별이 안 됐다. 밝은 파랑(`BRIGHTBLUE_FONT_COLOR`)이 그 자리를
  가져가고 같은 파랑의 점(`NewDot`)이 아이콘 모서리를 걸친다. **뜻이 하나다. 색을 갈아 두 번째
  뜻을 얹지 말 것.**
- **액션이 그려지는 모든 자리에 그린다.** 임포트된 액션은 어느 화면에서도 뭉쳐 있지 않다.
  이름순인 곳에서는 알파벳 자리대로 흩어지고, 키로 모으는 곳에서는 이미 그 키에 있던 액션들
  사이에 끼어든다.
- 편집했다고 자동으로 떼지 않는다. "내가 넣은 거였나" 추적이 끊긴다.

**순서에도 없다.** 순서는 나가는 것들 사이에서만 뜻이 있다. 배지 달린 행이 순서 계산에 끼어
있어서 셋이 틀렸었다. ↓를 누르면 자리가 바뀌는데 그 키가 하는 일은 그대로였고, `seq`는 실제로
쓰였고, 사유 칸이 겨루지도 않는 행을 상대로 계산됐다. `BuildKeyMap`이 배지를 빌드에서 빼니
순서에도 없는 게 같은 규칙이다. 배지 행에는 화살표 대신 [받기] 버튼이 선다.

**낱말은 accept / reject다.** keep/discard와 섞지 않는다. **keep을 안 쓰는 이유는 "이미 동작 중"
이라고 말하기 때문이다.** 격리가 세우려는 사실을 버튼이 정면으로 뒤집는다. 한국어는 받기/버리기가
그 자체로 짝이라 그대로 둔다.

**벌크가 기본, 개별이 예외다.** 임포트의 목적이 일일이 액션을 만드는 수고를 더는 것인데 배지가
**액션마다 처리해야 할 목록**이 되면 목적을 배반한다. [N개 모두 받기] / [N개 모두 거절]이 그
자리이고, 집합은 `CollectImportedActions`다. 거절만 확인창을 받는다. 받기는 임포트의 정상적인
끝이라 라벨의 숫자가 경고 전부이지만, 거절은 N개를 한 번에 지운다. 확인창이 **문자열은 서랍에
남는다**를 말하고, 그래서 **거절이 승인보다 되돌리기 쉽다**(배지는 다시 못 단다).

개별이 열려 있는 대가는 **키 그룹이 반만 받아들여진 상태가 될 수 있다**는 것이다. 받기는 넘겨받은
액션의 배지만 뗀다. 화면에서 그걸 말하는 것은 머리글 색 하나뿐이고, 판정이 "**하나라도** 배지가
남았나"인 것(`keyHasImported`)이 그래서다.

### 배지 달린 것에 할 수 있는 일 (2026-08-17, 소유자 결정)

**받기 · 거절 · 단축키 지정 셋뿐이다.** 나머지를 뺀 근거는 하나씩 다르다.

- **조건 · 대상 · 중요도 · 매크로** — 배지가 붙어 있는 동안 이 액션은 발동하지 않는다. 발동하지
  않는 것에 값을 거는 것은 **결정 전에 결정 다음 것을 하는 일**이다.
- **이동 · 복사** — 아무 일도 안 하는 쪽이 아니라 **해를 끼치는 쪽**이다. `MoveAction`이
  `CopyTable`로 액션을 통째 복사하므로 배지가 따라간다. 복사하면 받아야 할 것이 하나 더 생기고,
  이동하면 안 보고 있던 레이어로 하나가 숨는다. 그리고 이동은 다른 그룹의 맨 뒤 번호를 새로
  발급하므로 **보낸 사람이 정한 순서가 아무 표시 없이 사라진다.**
- **삭제** — [버리기]가 그 자리를 이미 맡고 있고 더 정확한 말을 한다. 삭제는 내 것을 지우는
  물음이고 되돌릴 수 없다는 얼굴인데, 이쪽은 받아온 것이라 문자열이 서랍에 그대로 있다.
- **단축키 지정은 남는다.** 같은 물음의 세 번째 답이라서다. 자리를 정해서 받기 / 그냥 받기 /
  버리기.

**여럿 고른 메뉴는 배지가 몇 개 섞였느냐로 갈린다.**

| | 이동 / 복사 | 받기 / 거절 | 삭제 |
|---|---|---|---|
| 전부 배지 | 회색 + `BULK_BLOCKED_ALL_IMPORTED` | 선다 | 그대로 |
| 일부 배지 | 회색 + `BULK_BLOCKED_SOME_IMPORTED` | 선다 | 그대로 |
| 배지 없음 | 원래대로 | 안 선다 | 그대로 |

**부분 실행이 아니라 죽은 항목으로 막는다.** 다섯은 옮기고 둘은 남기는 것은 아무도 안 들은
결과이고, 이동에는 그걸 말해줄 확인창이 없다. 경고를 툴팁에 얹는 안까지 갔다가 접었다.
**툴팁은 스스로 불러서 읽는 글이라, 안 읽었을 때 손해가 나는 것을 담으면 안 된다.**

**삭제는 그 근거에 안 걸려서 그대로 둔다**(소유자 결정). 옮기는 것이 없으니 잃을 랭킹이 없고
복제되는 것도 없다. 열두 줄을 골라 없애려는 사람은 어느 것을 뜻했는지 이미 말한 것이다.

### 키를 정하는 것이 곧 승인

그 등식은 저장소에 세 군데 적혀 있었는데 **셋 중 하나만 코드였다.** 한 벌 경로
(`SetKeyForActions`)는 `action.imported = nil`을 했고, 낱개 경로(`SetActionKey`)는 `key`와 `seq`만
썼다. 같은 손짓이 대상 개수에 따라 다른 뜻을 갖고 있었다.

지금은 `SetActionKey`도 뗀다. **키를 줄 때만이다.** [키 설정 해제]는 아무것도 정하지 않고,
도착한 것에서 그것이 떼어내는 것은 애초에 키가 아니라 합성 번호다.

- **바인딩 모드의 트랜잭션에 `imported`를 실었다.** 모드는 액션마다 `{ key, seq }`를 적어두고
  [취소]가 되돌리는데, 배지를 안 실으면 **취소해도 승인만 남는다.** 배지는 다시 발급되지 않으므로
  그 세션의 유일한 못 되돌리는 변경이 된다.
- **배지가 실제로 떨어진 경우에만 `PruneSelectionToBinFilter`.** `imported`는 필터가 읽는 축이라,
  [대기 중]만 켜둔 채로 승인하면 행이 목록에서 빠지는데 선택은 계속 센다.

### 한 벌에 키 주기 — 어디까지 모으나

대상은 화면이 아니라 **이 캐릭터의 열한 레이어**를 훑어 모은다(`EnumerateAllProfileLayers`).
점유자 쪽도 같은 함수 위에 선다. 한쪽만 모자라면 교체가 반만 일어난다.

| | | |
|---|---|---|
| 이 캐릭터의 열한 레이어 | **채택** | 아래 |
| 저장 전체(`ForEachStoredActionList`) | **기각** | 오프스펙이 화면에 없던 때의 답이다. 지금 그 밖에 남는 것은 다른 직업 레이어뿐이고, 거기까지 가면 본 적 없는 키보드를 고쳐 쓴다. 되살릴 근거: 다른 직업 레이어의 배지를 화면에서 말하게 되면 |
| 살아있는 레이어만 | **기각** | 오프스펙 멤버에서 그룹이 잘린다. 그 액션들은 왼쪽 열에 그려지므로 화면에서 보이면서 조작에서만 빠진다 |
| 그려진 행에서 | **기각** | [모두 거절]이 물렸던 구멍. 열린 탭의, 필터를 통과한 행만 안다 |

**다른 직업의 레이어가 범위 밖인 이유는 키가 키보드의 것이기 때문이다.** "이 키는 이제 이 그룹
것"은 지금 도는 열한 레이어에 대한 말이다. 그 말을 접속한 적 없는 직업까지 끌고 가면, 보여준 적
없는 충돌을 놓고 본 적 없는 바인딩을 고쳐 쓴다. **두고 온 멤버는 아무것도 안 잃는다.** 배지·키·
순서를 그대로 들고 있어서, 그 직업으로 접속하는 날 여전히 한 묶음이고 그 키보드의 점유 상황을
보고 키를 받는다.

**`seq`는 그룹 차례대로 발급한다.** 한 액션씩 주면 만진 차례대로 번호가 붙어서 보낸 사람의
순서가 사라진다. 그래서 이 조작은 편의가 아니라 순서를 지키는 유일한 길이다.
`tests/keygroup_spec.lua`가 그것부터 세운다. 저장 배열의 차례와 실려온 차례를 어긋나게 해두고,
순진한 구현에서 실제로 빨갛게 뜨는 것을 보고 넣었다.

**재빌드는 다 쓰고 나서 한 번.** `Profile.lua`는 액션을 놓기만 하고 바인딩이 언제 올라가는지는
안 정한다. 부르는 쪽이 다 쓰고 한 번 올린다.

**키를 잃은 액션은 안 지운다.** `key = nil`이면 바인딩까지 못 가고 회색으로 남는다.

### 질문의 문구 (`KEY_GROUP_CONFLICT`)

> `F`에는 전문화를 가리지 않고 이 캐릭터에서 그 키에 걸리는 것이 이미 `3`개 있습니다.
> `키를 모름 #2`이(가) 그 키로 가면 그것들은 어떻게 할까요?

- **문장이 수집 범위를 그대로 말해야 한다.** 한때 "이 캐릭터의 모든 전문화를 통틀어"라고 적혀
  있었는데 그것이 범위를 **좁게** 말하고 있었다. 열한 레이어에는 직업 공유 둘과 계정 공유 하나가
  들어 있어서, 세어준 것 중에 다른 캐릭터에서도 그 키에 걸려 있는 것이 섞일 수 있다. 공유 범위
  것이 실제로 있을 때만 한 줄이 더 붙는다(`KEY_GROUP_CONFLICT_SHARED`).
- **키 그룹의 이름은 머리글의 낱말 그대로다**(`KeyGroupLabel`). 머리글과 이 문장이 같은 키
  그룹을 두 이름으로 부르면 읽는 사람은 둘이라고 생각한다.
- **버튼은 `Keep both` / `Unbind them` / 취소다.** "Merge"도 "Overwrite"도 클라이언트에 0회이고,
  그 개념을 게임이 부르는 자리는 "Replace"다. 반대로 `UNBIND`는 클라이언트 전역이고 바로 앞 캡처
  창의 버튼이 쓰는 낱말이다. "합치기"는 **일어나지 않는 조작**을 이름으로 달고 있었다. 아무것도
  합쳐지지 않고 둘 다 그대로 남는다.
- **축이 안 맞는 것을 알고 받아들였다.** 앞은 "이 키가 어떻게 되나", 뒤는 "저것들이 어떻게
  되나"다. 축을 진짜로 맞추는 `Keep them`은 **[취소] 옆에서 "손대지 마"로 읽히고**, 그 오독은
  옆 버튼이 지정을 걷어내는 자리에서 제일 비싸다. `both`가 새로 오는 쪽을 문장 안에 끌고 들어와서
  그 오독을 막는다.
- 질문은 오프스펙 개수를 따로 세지 않고 **점유자 수 하나**를 말한다. 세는 집합과, 필터를 끄면
  보이는 집합이 같기 때문이다.

**키 그룹이 어디로 갔는지 보여준다.** 키가 바뀌면 왼쪽 열에서 자리가 통째로 옮겨가고, 새 자리가
화면 밖이면 조작이 아무 일도 안 한 것처럼 보인다. 고르는 것과 스크롤이 둘 다 필요하다. 선택은
왼쪽 열을 자기 자리로 굴리고 강조로 어느 줄인지 짚어주며, 오른쪽 목록은 그 열을 안 보므로
`ScrollActionIntoView`가 따로 굴린다.

## 5. 애드온 경계 — UI는 Debind에 있다

```
DebindStorage   DebindStorageVars · Libs · Export.lua · Import.lua
Debind          나머지 전부. ExportUI.* 와 ImportUI.* 가 여기다
```

**UI는 포기할 수 없는 축이고, 분리는 리소스 절약이다. 그 정도는 감내한다.** 패널 둘이 로그인에
로드되는 값을 치른다. 최적화가 양보할 수 없는 축을 제약하게 두지 않는다는 뜻이라, 이 결정은
재본 뒤에 바뀌는 종류가 아니다.

**경계를 남겨두면 설계가 조용히 비틀린다.** 작업대가 이미 이 실패로 죽었다(6절). 저쪽 폴더에
있으니 오버뷰에 손을 안 뻗고 자기 기능을 키웠고, 그러다 기본 UI를 넘어서는 역전이 나서 접었다.
남겨두면 행을 그리는 **두 번째 방법**이 생기고, 그것이 "재사용을 안 한 이유"로 굳는다. 특히
미리보기가 그 자리다.

> **아직 안 한 설계의 입력으로 모듈 경계를 쓰지 않는다.** 경계는 설계가 끝난 뒤에 값을 재서 긋는다.

**남는 쪽은 이 물음과 무관하다.** `DebindStorageVars`가 저쪽에 있는 이유는 개념이 아니라 플랫폼
사실이다. SavedVariables는 애드온이 로드될 때 통째로 읽히고 서랍은 계속 자란다. LoD가 그걸
미루는 유일한 수단이고 취향이 아니다. Libs(208K)와 선 코드는 그 데이터 없이는 쓸 일이 없으니
같이 남는다. **애드온 경계와 코드 경계는 다른 종류의 근거로 서 있고, 그래도 된다.**

모델 손잡이는 `DebindPrivate.Store`다. 저쪽 첫 파일이 `LoadAddOn` 창 안에서 자기 테이블을
걸어주고, UI는 **호출 시점에** 읽는다. 파일 스코프에서 잡으면 영원히 nil이다. UI는 로그인에
읽히고 저쪽은 아니다.

### 선이 왜 하필 거기인가

**로캘 문자열**과 **`DebindPrivate` 참조**를 각각 재봤고 같은 답이 나왔다. `Export.lua` /
`Import.lua`는 로캘을 0개 쓰고, `ExportUI.lua` / `ImportUI.lua`가 46개를 다 쓴다. `DebindUI`도
`L`도 `DisplayMessage`도 옮기는 파일 둘에만 있고 남는 쪽은 모델만 짚는다. **내가 그은 선이 아니라
코드가 이미 그어놓은 선이다.**

`Export.lua`가 짚는 것 중 넷은 **순서 기계**다(`CompareActionOrder`, `EnumerateAllProfileLayers`,
`GetBindingInfoForAction`, `IsConditionalAction`). "순서를 말하는 자리가 하나뿐이어야 한다"가
애드온 경계를 넘어 뻗은 자리라 맞는 의존인데, **Debind의 순서 내부가 곧 DebindStorage의 API**라는
뜻이기도 하다.

### 폴더 이름

`DebindStorage`. 소유자가 후보를 냈고 골랐다. **떨어져 나간 후보들과 이유가 근거다.**

- **`DebindCodes`** — 낱말(문자열/코드)이 아직 안 정해져서 이름이 그 결정에 매달린다.
- **`DebindVault`** — 소유자: *"볼트는 와우에서 사람을 희망고문하는 단어인데"*. 클라이언트가 쓰는
  낱말이냐가 아니라 **플레이어 귀에 뭘로 들리느냐**가 기각 사유다.
- **`Keep` / `Silo` / `Archive`** — 소유자가 낸 셋. `Keep`은 클라이언트에서 던전·지역 이름이고
  동사로도 읽힌다. **셋 다 장소 은유다.**
- **틀을 바꾼 것도 소유자다** — *"Debind Migration이란 애드온을 쓰고 있지. 같은 톤으로 생각해봐"*.
  동반 애드온의 `## Title`은 은유가 아니라 **일을 그대로 말하는 평범한 명사**다. 그 톤에서 이
  애드온의 일은 보관이고, `Storage`는 클라이언트가 그 뜻으로 쓰는 낱말이다(하우징 창고).

**폴더 이름과 `## Title`은 별개다.** `Debounce/`가 그 산 증거다. 여기서는 둘 다 자유로워서 같이 갔다.

첫 배포로 개명이 공짜인 구간은 닫혔다. 이제 폴더를 바꾸면 `.pkgmeta`의 `move-folders`가 정하는
SavedVariables 파일 이름이 같이 움직인다.

### 왜 저장 포맷을 닮았나

**그리는 코드를 재사용하려고.** 소유자가 말해줬고, 이 문서에 한 번도 안 적혀 있었다. 적혀 있던
것은 전부 결과였다. 의도가 없는 자리에서 뒤늦게 읽는 사람은 결과를 보고 이유를 지어내고,
2026-08-15 대화에서 실제로 여섯 개가 지어졌다.

페이로드가 프로필과 같은 모양이면 **프로필을 그리는 UI가 페이로드도 그린다.** 노리는 것은
임포트 창에서 그 문자열의 레이어-액션 목록을 보여주는 것과, 가져오기 전 미리보기다(7절).

**이미 되는 부분이 많다.** 맨 액션 목록에 레이어 껍데기를 씌워 쓰는 것은 확립된 수법이고
(`PlaceImportedActions`), 그러면 `BuildSortedElements`가 그대로 먹는다. `ACTION_FIELDS`가
`KEYS_TO_SAVE` 마이너스 하나라 페이로드의 액션은 사실상 액션 테이블이고,
`NameAndIconForAction`·`GetBindingIssue`·`GetBindingInfoForAction`이 다 산다. 빨간 글씨는
미리보기에서 오히려 있어야 하는 값이다.

**그리고 이 의도가 최상위를 정했다.** 저장과 갈라지는 자리가 정확히 최상위 하나였으므로, 그리기
재사용을 위해 고른 shape인데 그리려면 shape을 바꿔야 하는 상태였다.

### `key`가 그룹을 나른다

**같은 `key`면 같은 그룹이고, 그것을 선언하는 층이 필요 없다.** 무너진 것들:

- 최상위 `groups`와 `group.id`
- "그룹 정체성을 `key`에 얹지 않고 별도 id로 둔다"는 결정
- "묶인 적 없는 액션에는 `id`를 안 붙인다"는 규칙. **키 없이 나간다로 저절로 표현된다**
- 액션의 `importGroup`. 번호가 키 이름 안에 있다
- `CollectImportGroupActions` / `CollectKeyGroupActions`가 하나로

**구조가 "한 그룹에 키 하나"를 강제한다는 점에서 지금보다 강하기도 하다.** 같은 키가 곧 같은
그룹이라 정의상 두 키를 가질 수 없다.

*"가짜 키가 프로필로 흘러들어갈 일이 없다"*는 옛 항목은 이 안에 대한 반박이 아니었다. **가짜
키를 저장하자**는 안에 대한 반박인데 그건 아무도 제안한 적이 없다.

### 레이어는 이미 저장 주소 그대로다

`StoredActionsAt(scope, class, spec)`가 짚는 것이 정확히 선의 서술이다. 번역이 필요했던 것은
둘뿐이다.

1. **레이어 번호 1..11.** `LAYER_INFOS`가 2~6에 `PLAYER_CLASS`를 구워 넣는다. 주소가 아니라 뷰
   인덱스다. 저장은 애초에 이름으로 키를 잡는다.
2. **character에서 guid를 뗀다.**

중첩이 저장 모양을 따라가면 **서술 테이블이라는 물건이 사라지고 경로가 곧 주소가 된다.**

### `seq`를 그대로 싣고, bring이 우리 공간으로 옮긴다

**선의 이름은 `seq`다.** `order`도 `importOrder`도 없다.

이름을 피하려던 이유가 *"`BuildAction`이 블랙리스트라 `seq`가 실리면 아무도 안 시켜도 액션에
꽂히고, 받는 레이어가 이미 나눠준 번호와 섞인다"*였는데 **그 사유가 거짓이었다. 섞일 구간이
없다.** 도착 번호를 얹고 그 그룹을 재부여하는 것이 `PlaceImportedActions`이고, 실려온 번호는 그
자리에서 덮인다. 같은 거짓이 세 군데 있었고 셋 다 고쳤다.

**남는 진짜 이유는 비대칭 하나뿐이다.** 내보내는 쪽 `ACTION_FIELDS`는 화이트리스트인데 받는 쪽
`BuildAction`은 블랙리스트다. 그걸 화이트리스트로 맞추면 이름으로 피해 갈 일이 없다.

```
1. 들어온 액션 전부에  seq = MAGIC + 실려온 seq
2. 목적지 레이어에 넣는다
3. 닿은 (레이어, 키) 그룹을 재부여 → 1..n
```

1번이 **"어느 것이 새로 온 것인가"를 숫자의 성질로 만든다.** 그러고 나면 비교자도 재부여도 특별한
갈래가 필요 없다. MAGIC이 지배하니 도착한 것들은 자기 밴드에서 기존 것들 뒤에 서고, 낮은 자리가
보낸 쪽 차례를 지킨다.

- **MAGIC은 bring 안에서만 산다.** 3번이 걷어가므로 SavedVariables에도 비교자의 지속 상태에도 안
  닿는다. 두 번호 공간이 동시에 존재하는 순간이 없다.
- **내보낼 때 구워 보내지 않는다.** 상수를 알아야 하는 쪽은 정렬하는 쪽이고 그건 bring이다.
- **3번은 그 그룹이 아니라 닿은 그룹 전부다.** 한 배치는 레이어 여럿·키 여럿에 떨어진다. 하나
  빠뜨리면 그 그룹만 MAGIC을 든 채 남고, 그건 다음 편집까지 조용하다.

`seq` 자체의 결함(밴드를 넘을 때 안 따라간다)은 임포트와 무관한 기존 문제라 따로 세웠고,
`devdocs/legacy/renumbering-a-key-group.md`로 끝났다.

### 키를 빼고 보낼 때, 합성 키는 숫자다

`stripKeys`는 키를 **떼는** 것이 아니라 **바꾸는** 것이었다. **타입이 판정이다.**

- **겹칠 수 없다.** 문자열 접두사(`export#1`)는 *"안 겹칠 것 같다"*인데 숫자는 **구조적으로
  불가능**하다. 바인딩 문자열은 언제나 `[수식어-]키이름` 꼴의 문자열이다.
- **빠뜨렸을 때 조용하지 않다. 이쪽이 더 큰 값이다.** 접두사 방식은 가드를 하나 빠뜨리면 화면에
  `export#1`이 조용히 뜬다. 숫자는 `CompareKeys`가 `숫자 < 문자열`에서 던지고 `GetBindingText(3)`도
  정상이 아니다. **이 저장소가 제일 무서워하는 것이 조용히 죽는 키인데, 숫자는 그 실패를 시끄러운
  쪽으로 옮긴다.**
- `==` 비교는 안전하다. `action.key == "F"`는 숫자일 때 그냥 false다.
- **받을 때 번호를 다시 매긴다.** `1`은 그 문자열 안에서만 유일하므로 배치 둘이 동시에 기다리면
  1번이 둘이 된다. 훑는 범위는 저장 전체다. 안 보이는 레이어의 번호를 재사용하면 그 직업으로
  접속하는 날 둘이 된다.

**합성 키는 프로필에 그대로 산다. 그래서 "이 키가 진짜냐"를 묻는 자리가 생긴다.** 판정은 전부
`type(key) == "number"` 하나다.

| 자리 | 하는 일 |
|---|---|
| `CompareKeys` | **여기가 제일 먼저 터진다.** 숫자를 실키 전부의 뒤로 몬다 |
| `BuildKeyMap` | **숫자 키를 건너뛴다.** 지금은 배지가 막지만 승인하면 배지가 떨어진다. 배지와 **따로** 걸어야 한다 |
| `GetKeyDisplayText` | 행의 단축키 칸 · 툴팁 · 머리글 · 익스포트 창이 전부 이걸 지난다. 낱말을 네 군데 따로 쓰면 같은 창이 같은 것을 두 이름으로 부른다 |
| `GetMouseButtonAndPrefix` | 숫자에 `:match`를 걸어 터졌다. 호버 파생과 키 유효성이 둘 다 이 함수를 지난다 |
| 재익스포트 | 숫자 키를 든 프로필을 다시 내보내면 그대로 나간다. **그게 맞다.** 아직 키를 안 정한 키 그룹이라는 사실이 보존된다 |

**승인은 여전히 배지를 뗀다.** 숫자 키를 든 채로 승인하면 "받아들였지만 키는 아직"인 상태가
되는데, 그게 정직한 상태다.

| | |
|---|---|
| 액션 | `importGroup`, `importOrder` (+`KEYS_TO_SAVE` 두 칸) |
| 선 | `groups` 층, `group.id`, `order`, 액션의 `layer` 서술 |

### 레이어는 번역 대상이 아니다 (2026-08-14)

`DefaultDestinationLayerID(descriptor)`가 "보낸 쪽의 이 레이어가 여기서는 몇 번 레이어냐"를
답했다. 반환값이 `layerID`이고 `LayerArray`에는 지금 캐릭터의 레이어만 들어 있으니, 이 함수는
구조적으로 "내 프로필 안의 어딘가"밖에 답할 수 없고 남의 좌표를 내 번호 공간에 **밀어 넣어야**
했다. 그래서 몸통이 전부 추측이었다(마법사 세트가 "내 드루이드 전부" 자리에 앉고, 특성 번호를
직업을 안 보고 그대로 꽂았다).

**두 프로필이 같은 좌표계를 쓴다.** 다른 것은 어느 직업이냐뿐이고 그건 좌표의 **값**이지 좌표계가
아니다. **옮길 게 없다.** 진짜 번역이 필요한 건 캐릭터 하나뿐이다.

**받아들인 대가: 지금 캐릭터가 못 보는 것이 생긴다.** 마법사 문자열을 드루이드가 가져오면 그
내용은 `shared.classes.MAGE`에 앉고 드루이드 세션에서는 화면에 안 뜬다. 대안 둘이 다 성립하지
않아서 이쪽으로 갔다.

- **내 직업 레이어에 넣는다** — 보이긴 하는데 읽는 사람이 **판단할 수가 없다.** 자기가 못 배우는
  주문이라 전부 빨갛고, 그 세트가 쓸 만한지 알 방법이 없다. 답할 수 없는 질문을 물은 셈이 된다.
- **안 가져온다** — 제대로 된 자리에 두는 길이 있으면 굳이 버릴 이유가 없다.

**즉 "다른 캐릭터로 접속했을 때 resolve한다"가 설계다.** 격리가 그걸 안전하게 만든다. 안 보이는
동안에도 아무 키에도 안 걸린다. 남은 물음은 7절의 "안 보이는 레이어에 남는 배지"다.

### 교체를 뺐다 — 답은 셋 (2026-08-15, 소유자 결정)

**키 없이 도착한 키 그룹에는 교체가 없다.** 점유자를 보낼 데가 없어서 교체와 덮어쓰기가 같은 일이
된다. 교체가 실제로 서는 것은 이미 키가 있는 키 그룹을 다른 키로 옮길 때뿐인데 그건 임포트와
무관한 경우다. 처음엔 그 경우에만 버튼을 세웠고, **소유자가 화면을 보고 버튼 셋으로 잘랐다.**
답이 화면마다 둘이었다 셋이었다 하는 편보다 언제나 같은 셋인 편이 낫다.

**되살릴 근거:** 조건으로 갈린 지정을 F에서 G로 통째로 맞바꾸고 싶은 요구가 실제로 나오면. 그때는
대화상자의 넷째 버튼이 아니라 **따로 선 조작**이어야 한다. 두 키 그룹이 대등한 조작이라 "이 키
그룹을 어디로"라는 이 대화상자의 물음에 안 맞는다.

### 오버레이 둘이 똑같이 생겼다 (2026-08-15 → 08-17에 닫힘)

키 그룹 지정과 행 지정이 **같은 프레임**을 글자만 바꿔 써서, 같은 옷을 입고 ESC의 뜻이 반대였다
(행 지정은 그 행의 키를 지우고, 키 그룹 지정은 그만둔다). **비슷하게 생긴 것이 두 가지로 도는 것
자체가 문제**라는 것이 소유자 지적이었고, 문구를 더 정확히 쓰는 것으로는 안 풀린다. 읽기 전에
이미 안다고 생각하기 때문이다.

안 셋 중 **(다) 오버레이 대신 대화상자**로 갔다. (다)의 값으로 적어둔 "지정 모드의 배선을 새로
깔아야 한다"는 실제로 치렀다(`KeyCapture.lua`, `asking-for-a-key.md`). 뒤이어 소유자가 모드 쪽
그룹 갈래를 지우라고 해서, 이 문제를 만들던 두 번째 오버레이 자체가 코드에서 나갔다.

안 갔던 둘의 사유는 남긴다. **(가) 덮는 쪽을 뒤집는다**는 규칙 하나로 접히는 유일한 안이었지만
(오버레이는 대상이 아닌 쪽을 덮는다) 오른쪽 큰 목록을 덮는 그림이 어떤지는 화면을 봐야 알 수
있었다. **(나) 스트립에 상태 줄 한 줄**은 왼쪽 열이 안 덮여서 살아 있어 보이는데 클릭은 안 먹는
어긋남을 따로 처리해야 했다.

### 그룹을 1급으로 세우려던 것 — 기각 (2026-08-16)

출발점은 소유자가 짚은 진짜 결함이었다. **단축키를 해제하면서 그룹을 유지할 방법이 없다.**
`ClearActionKey`가 키와 `seq`를 같이 버린다. 거기서 "키 그룹을 1급 모델로, 그룹 = 키 스칼라"까지
갔고 죽었다.

**죽인 것:** 마법사가 R에 걸어둔 것을 T로 옮기면 드루이드가 R에 쓰던 것도 따라간다. 키를
정체성으로 삼으면 **아무것도 공유하지 않는 것들이** 키 문자열 하나로 한 그룹이 된다. 일반화하면
**레이어가 정하는 것은 폭발 반경**이고, 반경을 걸친 묶음에 조작을 붙이면 한 번의 누름이 가장 넓은
멤버만큼 닿는다. 이 저장소는 같은 판단을 이미 한 번 했다. 벌크 메뉴가 중요도를 빼는 이유가 그것이다.

**빠져나갈 길로 시도했다가 접은 것들:**

- *그룹을 레이어 안에 두기* — 키 하나에 그룹이 여럿이 되어 사용자가 키를 보면서 그룹 셋을
  관리하게 된다. 키와 그룹이 갈리는 순간 키바인딩을 생각하는 방식이 아니게 된다.
- *반경을 가장 넓은 멤버에서 유도해 고지하기* — 저장이 아니라 계산이라 관리할 것이 안 생기고
  실제로 맞기도 한데, 기능 하나를 지키려고 개념을 계속 늘리고 있었다.

**되짚어 보면 키 그룹은 애초에 누가 짠 세트가 아니다.** 몇 달에 걸쳐 서로 다른 레이어에서 하나씩
쌓인 것이고 머리글은 그걸 한 덩어리로 그릴 뿐이다. 진짜 세트인 것은 **가져온 것**뿐이고, 그래서
`SetKeyForActions`가 거기서만 쓰이고 있던 것도 우연이 아니었다.

**뒤집히는 조건:** 사용자가 **직접 골라서 만든** 묶음이 생기면. 선택이 곧 세트이고, 오른쪽 목록은
구조적으로 한 레이어라 반경이 하나다.

### 양쪽 "키 빼고"를 없앤 이유 (2026-08-16)

**받는 쪽 것**은 할 일이 없어졌다. 어차피 모든 키를 다시 매기므로 체크하든 말든 결과가 같다.

**보내는 쪽 것**은 남은 효과가 "내가 어느 키를 썼는지 안 알린다" 하나뿐이었고 소유자가 그걸
잘랐다. 설정을 남에게 건네는 사람은 자기 단축키 체계를 보여주려는 것이고, 키는 그중 보여줄
값어치가 있는 부분이다. **문자열에 실리면 안 되는 것은 이름과 서버지 키가 아니다.**

`batch.hasKeys`도 같이 갔다. 받는 쪽 체크박스가 유일한 독자였다.

> 거기서 나온 규칙 하나는 그것과 별개로 살아 있다. **`nil` / `false` / `true` 세 값을 `or nil`로
> 접지 말 것.** `hasKeys`를 `== true`로 걸었더니 그 필드가 생기기 전에 저장된 배치 전부에서
> 기능이 안 만들어진 것처럼 보였다. 없는 필드를 근거로 컨트롤을 끈 것이다.

### ★ 매크로는 이름만 나간다 (2026-08-18, 소유자 결정)

> **소유자** — *"매크로는.... 함부로 공유해서는 안되는 데이터를 들고 있을 수 있다"*

전송 포맷에서 `macro = { name, body, icon, scope }` 스냅샷이 통째로 빠지고 `MACRO`는 `value`
(= 이름)만 나간다.

- **매크로 본문은 함부로 공유해서는 안 되는 것을 들고 있을 수 있다.** 사용자가 자유롭게 쓴
  텍스트고 무엇이 들어 있는지 우리는 모른다. 그리고 **보내는 사람이 그 사실을 모른다.**
- **`MACROTEXT`는 다르고 남는다.** 그건 사용자가 이 애드온 안에서 직접 쓴 텍스트고, 그것이
  나간다는 것도 스스로 안다. 빠지는 것은 블리자드 매크로에서 본문을 떠오는 길 하나다.
- **받는 쪽이 그 이름을 모르면 이미 답이 있다.** `GetMissingMacroName`이 잡고
  `BINDING_ISSUE_MISSING_MACRO`가 붙는다. 그 액션은 `KeyMap`에서 빠지고 행이 빨개지고 툴팁이
  어느 이름이 없는지 적는다.
- **잃는 것:** 자기 백업을 자기가 복원하는데 그 사이 매크로를 지웠거나 다른 캐릭터로 옮긴 경우.
  받아들인다. **본문이 실제로 쓰이는 것은 이름이 안 맞을 때뿐이고, 그때가 바로 남의 매크로 본문이
  내 프로필에 앉는 순간이다.** 살리려는 경우와 막으려는 경우가 같은 갈래다.

같이 사라진 것: `Export.lua`의 `SnapshotMacro`와 `NormalizeAction` 매크로 갈래, `Import.lua`의
`MacroMatches` 전체와 `BuildAction`의 매크로 갈래.

**같이 죽은 옛 설계 하나.** 본문 스냅샷 + 원 이름 + 스코프를 싣고 **삼중 일치일 때만** 참조로
복구하고 아니면 `MACROTEXT`로 떨어뜨린다는 것이었다. 자기 백업 재임포트에서 참조가 살아 돌아오는
것이 그 안이 노리던 값이었고, 위 마지막 항목이 그 값과 위험이 같은 갈래라는 것을 말한다.

### 서랍은 페이로드를 저장한다 (2026-08-18, 소유자 결정)

> **소유자** — *"문자열이 필요하면 역직렬화된걸 다시 직렬화 하면 되지 않나"* /
> *"니가 논거를 대려면 문자열 저장할땐 되는데 페이로드로 저장하면 안되는 경우를 따져야지"*

`batch.text`가 없어지고 `batch.payload`가 그 자리에 앉는다.

**근거 하나만 적는다.** 문자열은 스키마가 오르는 순간 `DecodeExportString`이 통째로 거절하므로,
문자열만 든 서랍은 스키마를 한 번 올리면 **전부 죽고 옮길 방법이 없다.** 페이로드를 들고 있으면
프로필이 `dbver`로 하는 것과 같이 옮길 수 있다. 남은 차이는 디스크 크기 하나였고, **작지만 못
읽는 것을 들고 있는 쪽이 나쁘다.**

문자열을 저장할 이유로 내가 넷을 댔고 **넷 다 양쪽에 참인 것**이었다. 어떤 잣대로 넷이 한 번에
정리됐는지는 `devdocs/legacy/putting-import-back-together.md`에 있다.

- **개수는 이제 물을 때마다 센다**(`CountBatch`). 붙여넣을 때 한 번 세어 적어두던 이유가 "목록을
  그리자고 문자열을 전부 디코드할 수는 없다"였는데, 페이로드가 바로 거기 있으니 그 이유가 없어졌다.
- **`GetBatchPayload`에 디코드가 없다.** 메모리 캐시도 같이 없어졌다. 남은 것은
  `PayloadIsImpossible` 문 하나이고 그건 그대로 서 있어야 한다.

**판 번호는 안 올린다** (2026-08-19에 되돌렸다). 그 상수가 버전을 매기는 것은 **직렬화되는 내용의
모양**, 곧 페이로드의 모양이다. `text`를 `payload`로 바꾼 것은 같은 페이로드를 압축한 채로 들고
있느냐 편 채로 들고 있느냐의 차이라 그 모양은 한 칸도 안 움직였다. **상수 이름이 그 오해를
만들었다.** `STORE_VERSION`이었고 지금은 `PAYLOAD_VERSION`이다.

**올릴 때:** 페이로드 구조가 바뀌고, 그 전 구조로 저장된 서랍을 든 사람이 있을 때. 그때 다시
답해야 하는 것 둘이 여기 있다. **조용히 사라지는 것이 이 서랍이 내면 안 되는 유일한 결과**라는
것, 그리고 `LIBS_MISSING` 같은 거절은 다음 세션이면 끝나므로 한 번 적은 이유를 판결로 쓰면 안
된다는 것.

### 작업대를 접었다 (2026-08-14)

프로필 밖에서 키와 레이어를 정하고 커밋하는 작업대가 있었다. **병합은 전부 오버뷰에서 한다.**

**작업대의 기능이 오버뷰를 넘어서면 비대칭이다.** 작업대는 "그룹마다 키 하나"를 하려 했는데
오버뷰에는 그런 것이 없었다. 그러면 편집기가 둘이 된다. "왜 받은 것에만 저게 되지"가 되고, 같은
일을 하는 코드가 두 군데 선다. 그래서 **기능을 오버뷰로 옮기고 작업대에서는 뺐다.**

**전제 하나도 원래 약했다.** *"프로필에 들어가면 묶음이 사라진다"*고 적혀 있었는데, 도착한 것이
합성 키를 들면 안 사라진다. 게다가 오버뷰 왼쪽 열은 이미 키로 묶어서 그린다. 작업대가 만들려던
화면이 거기 있었다.

**예외는 커스텀 상태 이름 충돌뿐이다.** 편집 기능이 아니라 안전장치라 이 원칙 밖이다(7절).

## 7. 아직 안 만든 것

### 가져오기 전 미리보기

**포맷을 저장 구조로 맞춘 것이 노리던 것이다**(6절 "왜 저장 포맷을 닮았나"). 문자열 안에 뭐가
들었는지를 가져오기 전에 보는 것.

- 안 맞는 것은 **키 맵에서 나오는 값**(`IsUnreachableAction` 등)뿐인데, 그건 `simulated`·오프스펙이
  이미 푼 문제다. "지금 안 도는 세계의 액션을 그린다"는 기계가 서 있다.
- **어디에 두나가 안 정해졌다.** bring 대화상자 안이냐, 임포트 탭이 오버뷰처럼 두 열이 되느냐.
- **레이어 안에서 키별로 뭉쳐 낼 것인가.** 상대 순서만 지키면 되므로 필요는 없지만, 미리보기가
  키 그룹 단위로 그린다면 뭉쳐 있는 편이 읽기 쉽다.

### 커스텀 상태 이름 충돌

**격리가 못 막는 유일한 구멍이다.** 상태는 배치 소유가 아니라 전역 공유물이라, 이름이 같은데
정의가 다른 것을 조용히 덮어쓰면 **승인 전에 기존 액션의 동작이 바뀐다.** 배지를 안 뗐는데도
바뀐다.

**지금 답은 "내 정의 유지"다.** `CommitBatch`가 상태 정의를 아예 안 건드린다. 가져온 액션이
`$state3`를 부르면 읽는 사람의 `$state3`를 쓰고, 아무것도 정의하지 않은 이름은
`BINDING_ISSUE_UNDEFINED_STATE`가 빨갛게 말한다. **바꿀 수 없는 답을 골라둔 것이지 물음이
닫힌 것이 아니다.**

물어야 할 때의 모양은 이름마다 셋이다.

1. **이 이름 그대로, 내 정의를 덮는다.** 내 기존 액션이 그 상태를 쓰고 있으면 확인창이 그걸
   말해야 한다. 개수까지.
2. **내 정의 유지.** 정의는 안 건드리고 온 액션들이 내 상태에 붙는다(지금 동작).
3. **새 이름으로 받기.** 배치 안의 참조를 재작성한다. 재작성이 닿아야 하는 네 군데는
   `redesigning-custom-states.md` §3-4에 목록이 있다.

**정의 내용까지 일치하면 조용히 통과한다.** 자기 백업 재임포트가 확인창 세례를 받으면 안 된다.

### 전송 포맷에 메타데이터가 없다

문자열이 보낸 사람에 대해 나르는 것은 **`class` 하나**다. 나머지는 전부 받는 쪽이 만든 값이다
(`received`는 붙여넣은 순간, `name`은 붙여넣는 사람이 창에 친 자유 텍스트). **자기 백업을
되돌릴 때 그게 다 쓸모없다.** `received`는 오늘이 찍히고, 정작 알고 싶은 것은 "이걸 언제
만들었나"와 "이게 뭐였나"다.

- **내보낸 시각을 에폭 정수로 싣는다.** 타임존이 없는 값이라 그리는 쪽이 자기 로케일로 푼다.
  **받은 시각은 그대로 둔다.** 둘이 다른 물음에 답한다.
- **이름은 필드를 두되 익스포트가 지금은 안 채운다**(2026-08-15, 소유자 결정). 미룬 것은 값이
  아니라 **입력 UI**다. 임포트의 목적이 수고를 더는 것인데 내보내는 쪽에 수고를 새로 만들면 안
  된다. 나중에 정할 것은 "매번 적게 하기"가 아닌 모양이다. 기본값을 채워두거나, **받은 뒤
  서랍에서** 이름을 붙이게 하거나. 뒤엣것은 선을 아예 안 건드린다.
- **그래서 나머지 항목의 기준이 여기서 선다: 사용자에게 아무것도 안 시키는 것만 지금 넣는다.**
- **읽는 쪽은 지금부터 처리한다.** 우리 익스포트가 안 채운다고 그 필드가 안 온다는 뜻이 아니다.
  ⚠ **그러니 쓰는 사람이 없는 읽기 경로가 생긴다.** 헤드리스 스펙이 이름을 넣은 페이로드를 직접
  지어서 그 길을 밟게 해야 한다.
- **스키마 버전은 안 올린다.** 필드 추가는 모르는 필드를 건너뛰는 독자가 혼자 견딘다.

**⚠ 이름은 남이 준 텍스트를 화면에 그리는 첫 자리다.** 지금 서랍이 그리는 것은 받는 사람이 직접
친 것이라 이 문제가 없었다. **길이 상한과 이스케이프를 걸러야 한다.** 와우 마크업(`|c`, `|H`,
`|T`, `|n`)이 그대로 들어가면 색을 바꾸고 아이템 링크를 흉내내고 텍스처를 박고 줄을 늘린다.
서랍 한 행이 목록을 덮을 수 있다.

**딸린 두 가지.**

- **서랍 행의 제목이 아무 말도 안 한다.** `source`가 비면 "Received string"인데, 받은 문자열의
  목록에서 그건 아무것도 안 가른다. 이름이 지금 언제나 비므로 제목은 **자동으로 아는 것**으로
  세워야 한다. 차례는 이름 → 자동으로 지은 것 → 총칭이 될 것 같고, 앞이 대개 비어 있으므로
  **실질적인 제목은 가운데**다. (9절이 이 자리에 답 하나를 더 만든다.)
- **툴팁이 부실하다.** 지금 내는 셋 중 제목과 개수는 행이 이미 들고 있다. 툴팁이 실제로 더해주는
  것은 직업 한 줄뿐이다. 행은 좁고 **툴팁은 스스로 불러서 읽는 글이라 길어도 된다.**

### 승인 전에 시험해 보기

격리 중에는 빌드에 안 들어가므로 승인 전에는 아무 일도 안 일어난다. 시험할 길이 필요한데, 이건
그림이 아니라 **실제로 걸어놓고 눌러보는 것**이다.

**새 기계가 필요 없다.** `UpdateBindings`가 현재 상태 값을 읽어서 필터링하면 된다. 모드 셋.

- **배지 제외** — 지금 실제 상태
- **배지 포함** — 승인하면 어떻게 되는지. **부딪히는 것이 여기서 빨갛게 뜬다.** 가림 판정이 현재
  프로필 빌드에 붙어 있어서 넣어봐야 답이 나온다
- **배지만** — 받아온 것만 따로. "이 사람 세팅이 원래 어떻게 생겼나"

바인딩은 평소대로 실제로 올라간다. 필터만 바뀐다.

**챙길 것: 지금 그 모드에 들어와 있다는 것이 계속 보여야 한다.** 안 그러면 켜둔 채로 로그아웃하고
나중에 "왜 내 바인딩이 이상하지"가 된다. 모드 상태는 저장하지 말고 리로드하면 평소로 돌아오게.
**어디에 둘지가 안 정해졌다.**

이것이 있어야 닫히는 물음이 하나 더 있다. **부딪히는 것을 찾게 하지 말고 보여줄 것.** 49개 중
3개를 눈으로 찾게 하면 그때 배지가 안전장치가 아니라 숙제가 된다.

### 서랍이 자란다 — 쓸어내는 것이 아니라 묻는 것

**서랍은 실제로 자라고 자동 삭제가 없다.** 설계가 기각된 게 아니라 안 지어졌다.

되살릴 때의 모양을 정하는 한 줄은 그대로다. ***조용히 사라지는 것이 이 서랍이 내면 안 되는 유일한
결과다.*** 그러면 핀은 상시 컨트롤이 아니라 그 물음에 "얘는 빼고"로 답하는 방식이 될 수도 있다.
그때까지 **아무것도 판정하지 않는다.** 판정만 있고 실행이 없는 것은 둘 다 없는 것보다 나쁘다.
화면에 약속이 하나 서기 때문이다.

- 지우기는 확인을 받는다. 그 페이로드의 유일한 사본이다.

### 자동 백업 — 서랍의 한 줄로

**격리가 안 지켜주는 자리가 하나 있다.** 배지는 남의 것이 발동하는 것을 막지만, 키 그룹 조작은
**내 기존 액션의 키를 바꾼다.** 격리와 무관하게 실제로 달라지고 그 자체로는 되돌릴 방법이 없다.

→ **가져오기를 시작할 때 손댈 레이어들을 익스포트해서 그 페이로드를 서랍에 한 줄로 넣는다.**

**좋은 이유는 새로 만들 것이 없다는 것이다.** 백업은 그냥 또 하나의 배치이고, 복원은 그 줄에서
[가져오기]를 누르는 것이다. 되돌리기 화면도 스냅샷 포맷도 복원 코드도 필요 없다.

- **시점은 커밋 한 번.** 조작마다 뜨면 서랍이 백업으로 불어나고 어느 것으로 돌아갈지도 못 고른다.
- 뜨는 범위는 **그 배치가 닿는 레이어들.** 전 프로필을 뜨지 않는 이유는 크기만이 아니라, 되돌렸을
  때 무관한 레이어까지 시간을 거스르면 그게 새 사고가 되기 때문이다.
- 자동 삭제를 다시 짓게 되면 **이 줄이 그 안이 답해야 할 것 하나가 된다.** 한 달 뒤에 조용히
  만료되는 백업은 백업이 아니다.
- **9절이 같은 기계를 먼저 쓸 수도 있다.** 대화창에 붙인 링크가 가리키는 문자열도 클릭할 때까지
  살아 있어야 하고, 답이 똑같이 "서랍에 한 줄"이다. 둘 중 어느 쪽이 먼저 서든 **나가는 것도
  서랍에 남는다**는 사실이 같이 선다.

**⚠ 시점과 범위를 위에 적힌 대로 박으면 10절을 못 덮는다.** "커밋 한 번, 그 배치가 닿는
레이어들"은 커밋이 무엇을 건드리는지만 본 것이다. 10절의 둘째 답이 키를 떼는 점유자들은
**승인 시점의 열한 레이어 어디에나 있고**(`CollectKeyGroupActions`), 그중에는 배치가 안 닿은
레이어도 섞인다. 커밋 때 뜨는 백업은 그것을 못 덮는다.

→ **시점과 범위가 박힌 기능이 아니라, 부르는 쪽이 범위를 넘기는 부품으로 짠다.** 호출부가
셋이다. 임포트 커밋, 10절의 벌크 unbind, 11절의 교체. 9절도 같은 기계를 쓴다고 위에 적어 둔
방향 그대로다.

**⚠ 이건 undo가 아니다. 그렇게 부르지 말 것.** 임포트는 언제나 append라 백업을 다시 넣으면
**덮어쓰는 게 아니라 하나가 더 생긴다.** 실제 복구 절차는 "망가진 것을 지우고 백업을 다시
넣는다"이고, 그건 배지 필터와 벌크 삭제로 된다. `[되돌리기]`라고 적으면 누르면 원래대로 될 것처럼
읽힌다. **11절이 서면 이 ⚠가 사라진다.**

### 똑같은 액션 지우기 (임포트와 무관한 기능)

**[또 가져오기]가 만든 쓰레기를 치울 길.** 임포트 밖에서도 값이 있다. "복사할 곳..."이 같은 것을
만든다.

**판정은 `KEYS_TO_SAVE`를 deep equals로.**

- **필드 목록을 따로 적지 말 것.** 손으로 적으면 다음에 필드가 하나 늘 때 조용히 썩는다. 그 필드만
  다른 둘이 "동일"로 잡혀 지워지고 아무 검사도 못 잡는다. `KEYS_TO_SAVE`가 "액션이란 무엇인가"의
  유일한 목록이고 `check:export-fields`가 이미 그걸 감시하므로, 거기서 파생시키면 그 검사를
  물려받는다.
- **deep**이어야 하는 이유는 `conditions` 자체가 표이고 그 안의 `units`·`frameTypes`가 또 표라
  `==`로는 영영 안 맞기 때문이다.
- 비교에서 빼는 것은 **`seq`**(똑같은 둘은 번호만 다른 게 정상)와 **`imported`**.
- **살아남는 쪽은 받아들인 것.** "또 가져오기"의 흔한 결과가 "하나는 승인됨, 하나는 배지 달린
  똑같은 것"이라, `imported`를 비교에서 빼야 그 둘이 잡힌다. 둘 다 같은 처지면 `seq`가 작은 쪽.
- **닫히는 쪽이라 안전하다.** 배열 차례가 다르면 다르다고 본다. `false`와 nil도 다르다고 본다.
  둘 다 **중복을 놓치는** 쪽으로 틀리므로 지워선 안 될 것을 지우지는 않는다. **정규화해서 더 잡으려
  들지 말 것.** 필드마다 뜻을 판정하기 시작하면 파생의 이점이 사라진다.

**자리는 상설 버튼이 아니라 메뉴 항목.** 임포트와 무관하므로 스트립에 못 넣고, "중복이 있을 때만
뜨는 버튼"은 매 `Refresh`마다 전체를 훑어야 한다. **범위는 프로필 전체**라 화면에 안 보이는 것까지
지우고, **확인창이 개수와 함께 그걸 말해야 한다.** 거절과 달리 서랍이라는 되돌릴 길이 없다.

**검증은 헤드리스.** 순수 비교자라 `tests/`가 딱 맞는 층이다.

### 안 보이는 레이어에 남는 배지

`CollectImportedActions`는 `LayerArray`만 본다. [N개 모두 받기]가 안 보이는 것을 안 세고 안
건드린다. **그건 맞다.** 판단할 수 없는 것을 받으면 안 된다. 다만 화면에서 배지가 다 사라진
뒤에도 **계정 어딘가에 배지가 남는다**는 뜻이고, 그걸 어디서 말할지는 안 정했다.

`devdocs/showing-off-spec-actions.md`의 "안 정한 것"이 들고 있는 물음과 같은 하나다.

### 한계로 두기로 한 것

- **임시로 키 끄기.** 그룹 1급화 아래 깔린 진짜 필요였다. 옮기기는 파괴적인데 끄기는 토글이고,
  격리가 이미 "프로필에 있고 그려지고 어떤 키에도 안 닿는" 것을 하고 있어 패턴도 서 있다. 다만
  반경 문제가 여기서도 나오고(계정 레이어 액션을 끄면 모든 캐릭터에서 꺼진다), 그것을 피하려던
  "캐릭터별 꺼둔 키 목록"은 레이어 위에 두 번째 스코프를 얹는 것이라 잘렸다.
- **그룹에 이름 붙이기.** 이름이 필요한 자리는 키 없는 묶음 하나뿐인데 그건 머리글이 이미 답한다.
  나중에 필요해지면 따져둔 것이 적용된다. 이름은 **계정 전역**이어야 하고(그룹의 가시성은 가장
  넓은 멤버가 정한다), 고아 청소에는 **기한이 없다**.

## 8. 익스포트 창의 두 번째 축 — 키 그룹으로 묶어 보기 (제안, 2026-08-20)

> 상태: **제안.** 코드 미착수. `0-ROADMAP.md`에 배정 없음.

익스포트 창이 레이어로만 묶는다. **키 그룹으로 묶어 보는 축을 하나 더 준다.** 오버뷰 왼쪽 열이
그리는 그 단위다.

### 왜

**이 문서가 맨 처음 세운 어려움이 그대로 남아 있다.** 한 키의 동작은 레이어가 쌓여서 나오므로
키 그룹은 어느 레이어에 들어 있는 물건이 아니다. 레이어 축은 저장돼 있는 유일한 구조라 창의
기본이 맞지만, **의미 있는 묶음인 키 그룹은 레이어를 넘나든다.**

그래서 지금 창은 한 키에 걸린 셋이 레이어 둘에 나뉘어 있으면 **머리글 둘 밑에 나눠 그린다.**
읽는 사람에게 그 셋이 한 묶음이라는 표시가 없다. 창이 약속하는 것이 "이 레이어의 내용물"이라
틀린 그림은 아닌데, **보내는 사람이 확인하고 싶은 것은 자기가 만든 세트다.**

그리고 포맷이 그 사이에 바뀌었다. **`key`가 그룹을 나르므로**(6절), 키 축은 이제 문자열이 실제로
나르는 축이다. 레이어 뷰는 **무엇이 나가는지**를 말하고, 키 뷰는 **그것이 무엇을 하는지**를 말한다.

### 새 수집기를 안 짠다

이것이 이 기능을 싸게 만드는 성질이다.

- `CollectActionsForKey(key)`와 `CollectKeylessActionRows()`가 이미 있고, **둘 다
  `EnumerateAllProfileLayers`로 훑는다.** 그건 `BuildLayers`가 하는 그 걸음이고 페이로드가 하는
  그 걸음이다. 셋이 같은 열거자를 지나는 것이 이 창의 개수 불변식이 서는 방식이다.
- 걸러내는 것도 같은 함수 `IsExportable` 하나다. **한 키 그룹의 멤버가 전부 배지면 그 그룹은
  목록에 안 선다.** 레이어 뷰에서 레이어 하나가 통째로 빠지는 것과 같은 규칙이다.
- 키 목록의 차례는 `CompareKeys`다. 숫자 합성 키가 실키 뒤로 간다. 키 없는 것은 맨 아래 한
  덩어리이고 머리글은 `OVERVIEW_NO_KEY`.

### 그룹 안의 차례는 발동 순서다

**레이어 뷰가 못 하는 말을 이 뷰가 한다.** 메인 목록이 이름순인 근거가 *"한 레이어짜리 목록은
발동 순서를 말할 자격이 없다"*였는데, **키 그룹은 그 자격이 있는 유일한 단위다.**
`CollectActionsForKey`가 이미 `CompareActionOrder`로 정렬해서 돌려준다.

그래서 이 뷰는 보내기 전에 "이 키를 누르면 무엇이 먼저 나가나"를 확인하는 자리도 된다.

### 행이 레이어를 말해야 한다

한 키 그룹 안에서 **이름이 같은 행 둘**이 설 수 있다. 다른 레이어에 같은 주문을 조건만 갈라
걸어둔 경우이고, 그게 이 애드온의 정상 상태다. 어느 레이어 것인지가 행에 없으면 왜 둘인지를 못
읽는다.

**행의 오른쪽 끝 칸이 그 자리다.** 레이어 뷰에서 그 칸(`Key`)은 키를 적는데, 키 뷰에서는 머리글이
키를 들고 있어서 그 칸이 빈다. 거기에 레이어 이름이 선다. **머리글이 든 축의 반대쪽이 행에 선다**는
규칙 하나로 두 뷰가 같이 접힌다. 문자열은 이미 있다(`GetLayerLabel`, 행 툴팁이 이미 그걸 넘긴다).

### 선택은 축을 건넌다

`DebindExportPanel.selected`는 **액션 테이블의 집합**이라 축과 무관하다. 뷰를 바꿔도 고른 것은
그대로다.

**이것이 깨지면 두 뷰가 서로 다른 기능이 된다.** 축을 바꿨다고 선택이 날아가면 사람은 축을 안
바꾸고, 그러면 이 기능은 없는 것과 같다. 지금 선택을 그렇게 들고 있는 것은 우연이라, 이 기능이
들어오는 순간 그 성질이 **지켜야 하는 것**이 된다.

- tristate는 전체 → 키 그룹 → 액션으로 그대로 선다. `CombineState`가 액션 배열을 받으므로 손댈
  것이 없다.
- **접힘은 축마다 따로 든다.** `self.collapsed`가 지금 layerID로 키를 잡는다. 한 테이블에 두 축의
  키를 섞으면 뜻이 섞인다. 뷰마다 테이블 하나.
- **열면 전부 접혀 있는 것은 그대로.** 근거가 같다. 펼쳐 두면 축이 파묻힌다. 그리고 접힌 키
  목록이 곧 그 사람의 키보드라 그 자체로 읽을 것이 된다.

### 컨트롤

**드롭다운 하나.** [전부 선택] 체크박스가 있는 목록 위 줄의 오른쪽 끝.

- **필터 드롭다운(`WowStyle1FilterDropdownTemplate`)이 아니다.** 저건 값마다 체크가 서고 극성이
  "이것도 보여줘"인 물건이다. 여기 물음은 둘 중 하나라 **라디오**이고, 지금 무엇으로 보고 있는지가
  버튼에 적혀 있어야 한다.
- **기본은 레이어다.** 창이 약속하는 것이 "이 레이어들의 내용물"이고 그것이 문자열의 주소다.
- 고른 축은 저장하지 않는다. 창을 닫으면 선택도 접힘도 버리는 것과 같은 이유다.

**탭이 아닌 이유는 취향이 아니라 자리가 없어서다.** 2026-08-20에 소유자가 위쪽 탭을 냈고,
그래서 둘 다 따져봤다.

- **위쪽 탭**(`TabSystemTopButtonTemplate`)은 이 저장소가 이미 한 번 물리쳤다. 스펠 피커를
  그것으로 짰다가 걷어냈고, 사유가 아트가 패널 제목을 겸하는 크기라 가운데 정렬된 제목과
  자리를 다툰다는 것이었다(`SpellPicker.xml`).
- **아래쪽 탭**(`PanelTabButtonTemplate`)은 이 창의 방식이 맞는데 자리가 찼다. 익스포트
  패널의 아래 띠 50은 [문자열 만들기] 줄의 것이고 그 버튼이 BOTTOMRIGHT에 선다. `ExportUI.xml`이
  *"오버뷰의 10은 레이어 탭 자리고 이 패널엔 그런 줄이 없다"*고 적어 뒀다. 왼쪽 끝은 창의
  세 탭이 이미 쓴다.
- **되살릴 근거**: 아래 띠를 다시 나눌 일이 생기면.

**낱말은 축 이름 그대로다.** 앞에 동사를 달면 폭만 먹고 아는 것이 안 는다.

| | |
|---|---|
| enUS | `By layer` / `By key` |
| koKR | `레이어별` / `단축키별` |

- "레이어"는 이미 사용자 문구에 있고(`IMPORT_COMMITTED_SKIPPED`, 마이그레이션 안내문),
  "단축키"는 클라이언트 낱말이다. 새로 만드는 낱말이 없다.

  "단축키별"로 충분하다.

### 이 기능이 조용히 틀릴 수 있는 자리는 하나다

**두 뷰의 총계가 같아야 한다.** 같은 집합을 다르게 묶은 것뿐이므로 [전부 선택]의 숫자도, 전부
고르고 만든 문자열이 나르는 액션 수도 축과 무관해야 한다. 한쪽 뷰가 무엇을 빠뜨리면 창은 아무
말도 안 하고, 사용자는 자기가 보낸 줄 아는 것을 안 보낸다.

- **헤드리스가 못 본다.** 창이라서다.
- `/debtest`에 하나. **축을 바꿔가며 센 수가 같고, 그 수가 문자열이 나르는 수와 같다.** 지금 있는
  `Export: the window's count is what the string carries`가 그 절반을 이미 하고 있으니 그 옆에
  선다.

### 안 정한 것

- 키 뷰에서 머리글에 **무엇을 요약해 보여줄 것인가.** 오버뷰 머리글은 접힌 채로 안에 무엇이
  있는지 말한다(`UpdateSummary`). 여기서도 그게 필요한지는 화면을 봐야 안다. **오버뷰 머리글을
  그대로 가져오지는 않는다.** 저쪽은 요약·색·메뉴·폴드를 달고 있고 여기서 머리글이 하는 일은
  체크박스와 접기 둘뿐이다. 익스포트 창의 `ListHeaderThreeSliceTemplate`을 그대로 쓴다.
- 오프스펙 액션이 키 뷰에서 어떻게 서는가. 레이어 뷰에서는 자기 레이어 밑에 서서 저절로 갈리는데,
  키 뷰에서는 지금 특성 것과 한 머리글 밑에 섞인다. **그건 맞다**(같은 키니까). 다만 행이
  레이어를 말하는 것으로 충분한지는 화면을 봐야 안다.

## 9. 인게임 공유 — 대화창에 링크를 붙인다 (제안, 2026-08-20)

> 상태: **제안.** 코드 미착수. `0-ROADMAP.md`에 배정 없음.
>
> **모양은 소유자가 정했다** (2026-08-20): *"대화창에 링크를 만들고 그걸 클릭하면 다운로드
> 하지. 블리자드도 위크오라도 이런식이었어."*

### 방향이 반대다. 밀어 넣는 것이 아니라 당겨 가는 것

내가 먼저 낸 안은 밀어 넣기였다. 대상을 지목하고, 오퍼 한 줄을 보내고, 상대가 수락하면 본문을
흘리는 것. **그 안은 없다.**

**밀어 넣기가 만들던 물음이 통째로 사라진다.** 오퍼를 어떻게 안 귀찮게 하나, 무시 목록을
존중하나, 오퍼를 아예 안 받는 옵션을 두나, 파티 밖에서 온 것을 다르게 대하나. **클릭이 곧
동의라서** 물을 것이 없다. 그리고 이 모양은 사용자가 이미 아는 것이라 가르칠 것도 없다.

덤으로 **한 번 붙이면 여럿이 각자 가져간다.** 밀어 넣기는 대상마다 한 번씩이었다.

### 흐름

```
보내는 쪽   [공유]  →  대화창에 평문 한 줄        →  파티 / 공격대 / 길드 / 귓속말
받는 쪽     채팅 필터가 그 줄을 알아보고 링크로 그린다   (애드온 없는 사람은 평문을 본다)
클릭        SetItemRef 훅 → 보낸 사람에게 "그거 줘"     (애드온 채널)
보낸 쪽     조각을 귓속말 애드온 채널로 흘린다
받는 쪽     조립 → AddBatch → 서랍
```

**링크는 전송되지 않는다. 받는 쪽에서 만들어진다.** 클라이언트가 플레이어 메시지의 하이퍼링크를
걸러내므로 `|H...|h`를 채팅으로 보낼 수 없다. 나가는 것은 평문이고, 그것을 링크로 바꾸는 것은
**받는 사람의 채팅 필터**(`ChatFrame_AddMessageEventFilter`)다. 애드온 없는 사람에게 평문이
보이는 것도 같은 사실의 다른 면이다. **부작용이 아니라 이 설계가 서는 방식이다.**

⚠ **게임에서 잴 것.** 아래는 기억이지 잰 것이 아니다. `CopyToClipboard`를 프로브로 잰 것과 같은
방식으로 재고 그 결과를 여기 적는다.

- 플레이어 메시지에서 하이퍼링크가 실제로 걸러지는지, 그리고 **어느 링크 타입이 `SetItemRef`까지
  살아 오는지.** `garrmission:`을 빌려 쓰는 것이 관행이다.
- 애드온이 `SendChatMessage`를 직접 부를 수 있는지, 아니면 편집창에 넣고 사람이 엔터를 쳐야 하는지.
- 애드온 메시지가 `SAY`/`YELL`/`CHANNEL`에서 막혀 있는지, 교차 서버 귓속말이 `이름-서버` 전체
  이름을 요구하는지, 다른 진영에 닿는지.

### 클릭할 때 그 문자열이 아직 있어야 한다

**이 모양이 새로 만드는 유일한 문제다.** 밀어 넣기는 보내는 순간 문자열이 손에 있었다. 당겨
가기는 **붙인 시각과 클릭한 시각이 갈린다.** 몇 분 뒤일 수도 있고 다음 접속일 수도 있다. 그런데
링크가 가리키는 것은 붙일 때의 **선택**이고, 선택은 창을 닫으면 버린다(2절).

→ **붙이는 순간 문자열을 만들어 서랍에 한 줄로 남긴다.** 7절 자동 백업이 쓰려던 그 기계이고,
여기가 그 기계의 첫 사용처가 된다. 링크는 그 배치를 가리킨다.

- 그러면 링크가 리로그를 건넌다.
- **서랍 행이 두 종류가 된다.** 받은 것과 내가 붙인 것. 화면에서 어떻게 가를지는 안 정했다.
- **지운 뒤에 누가 클릭하면 없다고 답해야 한다.** 아무 답도 안 하면 클릭한 사람은 애드온이 고장
  났다고 읽는다.

### 요청과 응답

요청은 애드온 메시지 한 줄이고 배치를 가리키는 id 하나면 된다. 응답은 조각들이다.

**요청은 위조할 수 있고 그래도 된다.** 채팅에 붙인 것은 그 채널의 모두가 본 것이라 감출 것이
없고, 값은 몇 KB다. 다만 상한을 둔다. **한 요청자당 하나, 진행 중인 것이 있으면 새 요청은
거절.** 없으면 한 사람이 반복 요청으로 내 대역폭을 쓴다.

id는 링크마다 유일하면 되고 추측 불가일 필요가 없다.

### 애드온 경계가 오히려 더 깨끗해진다

**Debind에 남는 것은 셋뿐이다.** 접두사 등록
(`C_ChatInfo.RegisterAddonMessagePrefix`, 16자 상한), 채팅 필터, `SetItemRef` 훅. 전부 작고
로그인에 선다.

- **받는 쪽**은 클릭이 `EnsureStore()`를 부른다. 조립도 `AddBatch`도 그다음이다.
- **보내는 쪽**은 요청이 왔을 때 부른다. 붙일 때는 이미 켜져 있고(익스포트 탭을 열어야 붙일 수
  있다), 리로그 뒤에 요청이 오면 그때 켠다.

**Storage를 상시 로드하지 않는다는 선이 그대로 산다**(5절). 밀어 넣기 안에서는 오퍼 리스너가 그
선을 지고 있었는데, 지금은 클릭과 요청이라는 **사람이 만든 순간**이 그 자리를 대신한다. 더 늦게
켜도 되는 만큼 더 낫다.

### 방향과 무관하게 그대로인 것

밀어 넣기 안에서 정한 것 중 **전송 자체에 관한 것**은 살아 있다.

- **새 입구일 뿐이고 새 신뢰 경로가 아니다.** 도착한 것은 `AddBatch`를 지나 서랍에 앉고
  프로필에는 아무것도 안 들어간다. `DecodeExportString` · `BringPayloadForward` ·
  `PayloadIsImpossible` · 격리 · 배지가 전부 그대로 선다. 임포트는 어차피 **아무 문자열에나
  안전해야 하고**, 채널은 그 "아무"에 하나를 더할 뿐이다.
- **나가는 것은 `IsExportable`이 정한다.** 배지 달린 것은 채널로도 안 나간다.
- **봉투를 안 바꾼다.** `EncodeForPrint`가 내는 알파벳은 `[a-zA-Z0-9()]`뿐이라 공백도 제어문자도
  `|`도 NUL도 없고, 애드온 채널에 그대로 실린다. `EncodeForWoWAddonChannel`로 다시 인코딩하면
  25%쯤 작아지는데 **봉투가 둘이 되고 받은 것이 붙여넣은 것과 다른 바이트가 된다.** 액션 300개가
  1363자다. 크기는 문제가 아니다.
- **조립기.** 조각은 `<전송id> <n>/<total> <조각>`이고 상태는 보낸 사람마다 하나다. **상한
  셋**(조각 수 · 총 바이트 · 시간)이 없으면 남이 내 메모리를 채운다. **조각이 순서대로 온다고
  가정하지 않는다.** 번호를 보고 자리에 넣고, 빠진 것이 있으면 완성으로 치지 않는다.
- **완성되면 `AddBatch(text, name)`이고 `name`은 보낸 사람 이름이다.** "문자열은 캐릭터 이름을
  안 나른다"와 안 부딪히는 이유는 축이 다르기 때문이다. 그건 **보내는 쪽이 페이로드에 싣는
  것**이고 이쪽은 **받는 쪽이 채널에서 아는 것**이다. 페이로드는 손을 건너 계속 돌아다니지만
  채널이 말해준 이름은 그 한 번의 전달에만 붙는다. 그리고 이 자리가 7절 "서랍 행의 제목이 아무
  말도 안 한다"에 답 하나를 만든다.
- **속도.** 채널에는 전역 상한이 있고 넘으면 연결이 끊긴다. **라이브러리를 하나 더 벤더링하지
  않는다.** 조각 예닐곱이라 큐 하나와 간격이면 되고, `C_ChatInfo.SendAddonMessage`의 반환값을
  보고 밀린 것은 다시 큐에 넣는다.

### 안 정한 것

- **붙는 줄의 문구.** **애드온 없는 사람도 읽는 유일한 우리 문자열이다.** 위크오라의
  `[WeakAuras: 이름]`은 이름에 기대는데 **우리에게 그 이름이 없다**(7절대로 언제나 빈다). 지금
  자동으로 아는 것은 보낸 쪽 직업과 액션 수뿐이다.
- **어디서 시작하나.** 익스포트 창의 복사 다이얼로그 옆 [공유]인가 슬래시 명령인가. 그리고
  **어느 채널에 붙일지를 어떻게 고르나.**
- 서랍에서 "내가 붙인 것"을 받은 것과 어떻게 가르나. 붙인 것에 만료를 둘 것인가(자동 삭제가
  아직 없다, 7절).
- 클릭했는데 그 사람이 오프라인이거나 그 배치를 지웠을 때 무엇을 말하나.

### 검사

- **조립기는 순수 함수라 헤드리스가 본다.** 순서 뒤바뀜, 조각 빠짐, 상한 초과, 두 사람 동시,
  같은 전송 id가 두 번.
- **채팅 필터도 헤드리스가 본다.** 평문 한 줄이 들어가 링크가 나오는 순수 변환이고,
  **애드온 없는 사람이 보는 그 평문을 우리가 다시 알아볼 수 있는지**가 이 층에서 잡힌다.
- **채널 자체는 `/debtest`도 못 본다.** 계정이 둘 있어야 하고 그건 이 저장소가 가진 검증 층
  밖이다. 그래서 조립기와 채널의 선을 최대한 위로 올린다.

## 10. 보내온 단축키에 그대로 걸기 (제안, 2026-08-20)

>
> **7절 자동 백업이 이 절 앞에 서야 한다** (아래 "둘째 답이 실제로 무엇을 지우나").

### 지금 받기는 바인딩을 하나도 안 만든다

`KeyMapper`가 도착하는 키를 전부 합성 번호로 바꾸고(`Import.lua`), `BuildKeyMap`은 숫자 키를
안 받고(`Debind.lua`), `ApproveImportedActions`는 `imported`만 지운다. 셋을 이어 보면
**[N개 모두 받기]를 눌러도 아무것도 안 걸린다.**

3절이 적어둔 "흔한 경우는 버튼 두 번"의 끝이 그래서 파란 점만 사라진 목록이다. 스무 개짜리
세트를 받은 사람은 그 뒤에 [단축키 지정]을 스무 번 눌러, **문자열이 이미 들고 있는 키를 손으로
다시 친다.**

⚠ **`APPROVE_ALL_IMPORT_DESC`가 이 사실을 정면으로 뒤집고 있었다.** *"받는 즉시 그 키들이
동작합니다"* / *"Their keys start working straight away."* 3.2에 그대로 나갔고, 2026-08-20에
문장 쪽을 고쳤다. 지금 그 문구는 받아도 아무 키도 안 움직인다는 것과 받은 것이 어디로 가는지를
말한다.

**이 절이 서면 그 문구가 다시 바뀐다.** 항목이 둘이 되어 하나는 키를 주고 하나는 안 주므로,
각자 무엇을 하는지를 갈라 말해야 한다.

### 받기를 바꾸지 않고 항목을 하나 세운다

- 받기는 지금 **살아 있는 것에 더하기만 한다.** 확인창을 안 두는 근거(*"승인은 임포트의 정상적인
  끝이라 라벨의 숫자가 경고 전부"*)가 그 사실 위에 서 있다. 받기가 내 키를 쓰기 시작하면 그
  근거가 같이 무너진다.
- 스스로 이름을 달고 선 항목은 그 규칙 밖이라 확인창을 달 수 있다. [모두 거절]이 이미 그 자리다.

### ⚠ 두 항목의 순서가 한쪽으로만 열린다

[모두 받기]가 `imported`를 지우고, **`from`은 거기 말고 아무 데도 없다.** 4절이 2026-08-19에
안 남기기로 정했으니 되찾을 데도 없다.

- 새 항목 먼저 → 남은 것을 받기가 정리한다. 정상.
- 받기 먼저 → **새 항목이 대상 0이 되어 메뉴에서 사라진다.** 사용자는 자기가 무엇을 버렸는지
  모른다.

→ 새 항목이 [모두 받기] **위**에 선다. 그리고 위의 그 문장을 고칠 때 **보내온 단축키가 어떻게
되는지가 거기 들어가야 한다.**

### 대상과 세는 수

`imported`가 **문자열**인 것만이다. `true`(키 없이 온 것)는 앉을 데가 없다.

- 그런 것이 하나도 없으면 항목을 안 세운다. `CreateApproveImportMenuItem`이 이미 그 규칙으로 선다.
- **라벨의 수가 [모두 받기]의 수와 다를 수 있고, 그게 맞다.** 그 차이가 곧 "키 없이 온 것이
  몇 개"라 읽는 사람에게 정보다.
- 수집 범위는 `CollectImportedActions` 그대로다. 안 보이는 레이어는 여기서도 안 건드린다.
- **`IsKeyInvalidForAction`을 그대로 태운다.** 보낸 사람의 게임 메뉴 키가 내 것과 다를 수 있고,
  그래서 빠지는 몇 개는 조용히 빠지면 안 된다.

### 충돌은 한 번만 묻는다

키마다 물으면 상자가 열 번 뜬다. 한 상자에 모아서 답 셋.

- **[안 부딪히는 것만 걸기]** (기본)
- **[전부 걸고 기존 지정은 키를 뗀다]**
- **[취소]**

**기본이 첫째인 이유는 부딪힌 것들이 배지째 남아서 `from`을 안 잃기 때문이다.** 사용자가 자기 키를
정리한 뒤 같은 항목을 다시 누르면 되고, 라벨의 수가 그만큼 줄어 있어서 남은 것이 몇인지가 저절로
보인다.

둘째 답의 문구는 `KEY_GROUP_CONFLICT`에서 가져온다. 같은 일을 하는 두 자리가 다른 낱말을 쓰면
읽는 사람은 둘이라고 생각한다. 공유 레이어 줄(`KEY_GROUP_CONFLICT_SHARED`)도 같이 온다.

### 둘째 답이 실제로 무엇을 지우나

액션은 안 지워진다(`KEY_GROUP_CONFLICT_UNBIND_DESC`가 맞는 말을 한다). 지워지는 것은 **어느
키였는지**이고 그건 안 남는다(4절). 한 그룹 경로에서는 사용자가 그 키를 보면서 답한 것이라 감수할
수 있는데, **열두 그룹이 한 번에 가면 다르다.**

→ 그래서 7절 자동 백업이 이 답 앞에 선다.

### 낱개 그룹 메뉴에도 같은 항목

`CreateApproveImportMenuItem` 옆 형제로 하나. **여기가 오히려 더 쓸모 있다.** 머리글이 이미
`importedFrom`을 들고 있어서 **라벨이 키를 부를 수 있다.**

```
받기
SHIFT-G에 걸고 받기      ← 새 항목
버리기
```

### 낱말

둘 다 "받기"로 시작하면 차이가 안 보인다. **동사를 가른다.**

| | |
|---|---|
| enUS | `Accept all (%d)` / `Bind all %d to the keys they came on` |
| koKR | `%d개 모두 받기` / `%d개를 보내온 단축키에 걸기` |

`Bind` / `Unbind`는 `KEY_GROUP_CONFLICT`의 버튼이 이미 쓰는 클라이언트 낱말이라 새로 만드는
낱말이 없다.

### 새로 짜는 것

`SetKeyForActions`가 정렬과 배지 떼기와 renumber를 다 한다. `PlaceImportedActions`가 도착 순번
더하기 보낸 쪽 `seq`로 이미 넣어 뒀으므로 **보낸 사람의 순서는 저절로 지켜진다.**

새로 짜는 것은 둘뿐이다.

1. 합성 키별로 묶어 그 그룹의 `from`을 꺼내는 것.
2. 충돌 집계. `CollectKeyGroupActions`를 키마다 부르고 합치는 것이라 새 수집기가 아니다.

### 안 정한 것

- **같은 `from`을 든 배치가 둘일 때.** 한 키에 합쳐지는데, 그것이 맞는지와 상자가 그 사실을
  말해야 하는지.
- 부딪혀서 남긴 것을 화면이 어디서 말하나. 라벨의 수 말고.

### 검사

- **헤드리스**: 합성 키별 묶기와 `seq` 보존. `tests/keygroup_spec.lua` 옆에 선다.
- **`/debtest`**: 항목이 서는 조건, 상자가 세는 수, 둘째 답 뒤에 점유자가 키를 잃고 액션은 남는 것.

## 11. 가져오기가 레이어를 통째로 바꾸는 모드 (제안, 2026-08-20)

> 상태: **제안.** 코드 미착수. `0-ROADMAP.md`에 배정 없음.
>
> **앞에 서야 하는 것이 둘이다**: 7절 자동 백업, 그리고 10절.

### 왜

7절 자동 백업이 ⚠로 적어둔 것이 이것이다. **임포트는 언제나 append라 백업을 다시 넣으면
덮어쓰는 게 아니라 하나가 더 생긴다.** 교체가 있으면 복원이 한 번 누르는 것이 된다.
**백업 한 줄과 교체는 따로 있으면 각자 반쪽이다.**

용도는 남의 것을 받는 쪽이 아니라 **자기 백업을 되돌리는 쪽**이다.

### 지우는 범위는 페이로드가 아니라 체크박스다

"이 문자열에 든 레이어"가 아니라 "내가 체크한 줄"이다. 페이로드 내용으로 정하면 **빈 레이어를
복원할 수 없다.**

여기서 포맷 구멍이 하나 드러난다. **지금 문자열은 "이 레이어는 비어 있었다"와 "이 레이어는 안
내보냈다"를 구별 못 한다.** `CollectImportLines`가 놓일 수 있는 줄만 세우므로, 백업 시점에 비어
있던 레이어는 줄이 아예 안 서고, 체크할 수 없고, 비울 수도 없다. 복원했는데 거기 옛것이 남는다.
게다가 익스포트는 액션 단위로 고를 수 있어서 **내용물로는 원래 유도가 안 된다.**

→ 익스포트가 **훑은 레이어 목록**을 필드로 싣는다. 7절 규칙대로 필드 추가는 `SCHEMA_VERSION`을
안 올린다.

### 배지는 그대로 두고, 옛것은 커밋 때 지운다

교체가 배지를 건너뛰면 붙여넣는 순간 살아 있는 바인딩이 바뀌고, 그것은 4절 전체가 서 있는
전제를 깬다. 그러니 배지는 유지한다.

커밋 직후 그 레이어들은 파란 점 달린 행으로 가득하고 아무것도 안 걸린 상태가 되는데,
**그건 모든 임포트의 정상 상태와 같은 그림**이라 새로 설명할 것이 없다. 그 사이의 안전망이
백업 줄이다.

**안 간 안 — 승인 시점에 지우기.** 커밋과 승인 사이에 "이 배치는 교체였다"를 어딘가 저장해야
하는데, 그것은 2026-08-16에 행에서 걷어낸 그 모드가 이름만 바꿔 돌아오는 것이다.

### 컨트롤은 대화상자 안이다

행이 아니라 [가져오기] 대화상자다. 근거는 08-16에 행의 `[ ] 단축키는 빼고`를 걷어낸 그 근거
그대로다. **이 답도 딱 한 번의 press만큼 값이 있고**, 저장되면 일주일 뒤 돌아온 사람이 자기가
안 고른 모드로 복원한다.

- **기본은 더하기.** 흔한 경우가 남의 것 받기다.
- 교체를 고르면 **네 줄의 라벨이 무엇이 지워지는지로 바뀐다**, 개수까지. 같은 체크박스가 두 뜻을
  갖는 것이 아니라, 고른 모드가 줄의 뜻을 정한다.

### 교체해도 충돌은 남는다

체크 안 한 레이어가 그 키를 쥐고 있을 수 있다. **그것은 사용자가 바꿔 달라고 한 적 없는
레이어**라 조용히 뺏으면 안 된다. 10절의 상자가 여기서도 선다.

### 커스텀 상태 물음을 강제로 연다

7절 "커스텀 상태 이름 충돌"의 지금 답인 **"내 정의 유지"가 여기서는 반쪽 복원이다.** 상태 정의를
바꿔서 망가뜨린 사람이 복원하는 것인데 정의가 안 돌아온다. 게다가 페이로드는 **참조된 상태만**
싣는다.

이 모드에서는 덮어쓰는 쪽이 맞아 보이는데, **그 답이 `redesigning-custom-states.md`가 이름
규칙을 갈고 난 뒤에 달라진다.** 먼저 만들면 같은 물음에 답을 두 번 쓴다.

### 안 정한 것

- 그 레이어에 **다른 문자열에서 온 배지 달린 것**이 있으면 그것도 지워지나. 지워도 그 문자열은
  서랍에 있지만, 사용자가 그걸 알고 있나.
- 다른 캐릭터에서 만든 백업을 여기에 복원하는 것. `char`는 guid를 떼므로 "이 캐릭터"가 되어
  그냥 되는데, 그것이 원하는 결과인지.
- 익스포트 쪽에서 "이건 백업이다"를 말할 자리가 필요한가. 7절 메타데이터 항목과 같은 물음이다.

### 검사

- **헤드리스**: 체크한 줄만 비워지는지, 안 체크한 줄이 그대로인지, **빈 레이어가 실제로
  비워지는지**(새 필드가 있어야 성립한다).
- **`/debtest`**: 커밋 직후 그 레이어가 배지로 가득하고 아무 키도 안 걸린 것, 받은 뒤에 백업과
  같아지는 것.
