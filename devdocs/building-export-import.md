## 구현된 것 (2026-08-13) — 익스포트, **별개 애드온으로**

### 왜 애드온을 갈랐나

작업대는 한 번 쓰고 잊는 곳이 아니라 **받아둔 것을 쌓아두는 서랍**이라 그 SavedVariables가
시간이 지나면 커진다. 그런데 SavedVariables는 애드온이 로드될 때 통째로 읽힌다 — 본체에 두면
**공유를 한 번도 안 하는 사람의 로그인마다** 그 파일을 읽는다. 압축 라이브러리 5,500줄도
마찬가지다.

→ `DebindStorage`. `LoadOnDemand: 1`, `Dependencies: Debind`, `SavedVariables: DebindStorageVars`.
창을 실제로 열기 전까지 아무것도 안 읽힌다. **안 정한 것 4번(대기 영역을 어디에 저장할지)이
이걸로 닫힌다** — 이 애드온의 자기 SavedVariables다.

```
DebindStorage/
  DebindStorage.toc
  DebindStorage.lua      LoadAddOn이 도는 동안 _G.DebindPrivate을 받아 챙기고,
                         같은 순간에 자기 테이블을 DebindPrivate.Store로 걸어준다
  Export.lua             페이로드 + 문자열
  Import.lua             그 역
  Workbench.lua          서랍
  Libs/                  LibDeflate, LibSerialize
```

> ⚠ **창은 여기 없다.** `ShareUI.*`와 `WorkbenchUI.*`는 2026-08-15에 `Debind/`로 갔다
> (아래 네 번째 ★). 이 절의 나머지는 그때까지의 기록이라 창 이야기가 섞여 있다.

내부 접근은 `DebindCliqueFake`와 같은 방식이다 — 본체가 `LoadAddOn` 앞뒤로 `_G.DebindPrivate`을
잠깐 세웠다 지우고, 저쪽 첫 파일이 그때 받아 챙긴다(`Public.lua`의 CliqueFake 로드와 같은 모양).
`Constants.DEBUG`에서만 노출되는 그 전역을 **비-DEBUG 빌드에서도 이 한 순간만** 세운다.

익스포트 API는 `DebindPrivate`이 아니라 **`DebindStorage` 테이블**에 앉는다. 호스트 테이블을
안 건드린다.

```
DebindStorage.BuildExportPayload(selection, options)  -- 선택 -> 페이로드 테이블
DebindStorage.EncodeExportPayload(payload)            -- 페이로드 -> "DEB1:..."
DebindStorage.DecodeExportString(str)                 -- 그 역(왕복 검증용). 액션은 안 만든다
DebindStorage.ExportSelection(selection, options)     -- 창이 부를 것
```

- `selection`은 **액션 테이블의 집합**(nil이면 전부). 창이 액션을 체크하므로 창이 손에 쥐는
  것이 그것이고, 레이어는 여기서 훑는다 — 그래서 출력 순서가 정해지고 창은 필터만 한다.
- `options.stripKeys` = "키 빼고 내보내기". 그룹의 `key`만 떨구고 `id`는 남는다.
- 직렬화는 **LibSerialize + LibDeflate**, `.pkgmeta`의 `externals:`가 아니라
  `DebindStorage/Libs/`에 **벤더링**했다. 외부 참조로 두면 작업 트리에 파일이 없어서 헤드리스
  스펙도 로컬 빌드도 라이브러리를 못 본다(기존 LibStub/CallbackHandler와 같은 자리).
  → `findings.md:701`의 "두 줄이면 됨"은 그 점에서 틀렸다. LibStub은 본체 것을 쓴다.
- 크기 감각: 액션 5개 289자, 30개 464자, 100개 709자, 300개 1363자.
- 검증: `tests/export_spec.lua`, `tools/check-export-fields.js`, `tools/check-xml-methods.js`.
  ⚠ **LibDeflate는 fengari에서 압축을 못 푼다** — 실제 lua 5.1(luajit)·5.4에서는 왕복하는데
  `node tests/run.js`에서만 실패한다. 라이브러리도 우리 코드도 아니고 와우는 5.1이라
  게임에서는 안 닿는다. 스펙이 두 겹으로 갈라져 있고 어느 쪽이 돌았는지 매번 찍는다.

### 공유 창 (`DebindStorage/ShareUI.lua`, `ShareUI.xml`)

메인 창 오른쪽 위 [+] 옆 버튼이 연다. 버튼이 `LoadAddOn`을 하고, 실패하면 조용히 지나가지 않고
메시지를 낸다(`EXPORT_ADDON_MISSING`).

**메인 창에 수명이 안 묶여 있다.** 주문 선택 창과 갈리는 지점이다 — 익스포트한 창을 닫았다고
복사하려던 문자열이 같이 사라지면 안 된다. ESC는 `UISpecialFrames`로 자기가 처리한다.
프레임 이름도 `DebindStorageFrame`이다(export가 아니라) — 임포트가 같은 창을 쓸 것이라서.

- 레이어가 그룹 머리글, 그 안이 액션.
- **머리글은 블리자드의 `ListHeaderVisualTemplate`**(퀘스트 로그가 쓰는 그것). 바 아트와
  오른쪽 `+`/`−`가 템플릿에 이미 있다. 영역이 갈린다: **왼쪽 체크박스 = 선택**(자기 클릭을
  자기가 먹는다), **나머지 바 = 접기/펴기**.
- **열면 전부 접혀 있다.** 펼쳐 두면 액션이 한 줄로 길게 늘어져 이 창의 축인 레이어가 파묻힌다.
  접기는 보기 상태일 뿐이라 **접힌 레이어도 그대로 내보내진다** — 그래서 목록이 둘이다
  (`self.layers`가 "무엇이 선택됐나", `BuildDisplayList`가 "무엇을 그리나").
- **선택은 전부 선택으로 시작한다.** 그리기 **전에** 선택한다 — 목록을 먼저 깔면 그 사이에
  만들어진 행이 빈 선택을 보고 그려지고, 뒤이은 갱신은 그때 존재하는 프레임에만 닿는다.
- **행에는 체크박스가 없다.** 선택된 행을 메인 창과 같은 아트로 밝힌다
  (`auctionhouse-ui-row-select`). 상자를 세 단으로 늘어놓으니 레이어의 상자와 액션의 상자를
  눈으로 가를 수가 없었다.
- tristate 중간 상태는 **체크가 아니라 대시**(`common-icon-minus`). 흐린 체크는 한눈에
  "전부"로 읽히는데 그게 이 상태가 절대 말하면 안 되는 것이다. → 안 정한 것 6번이 닫힌다.
- 목록은 이름순이되 **한 키의 액션은 붙여 놓는다.** 둘이 서로 당기는데 둘 다 필요하다 —
  이름순은 메인 목록이 정한 규칙이고(한 레이어짜리 목록은 발동 순서를 말할 자격이 없다),
  그룹은 이 창이 실제로 보내는 단위라 한 덩어리로 보여야 한다. 그룹을 **그 그룹 첫 액션의
  이름**으로 정렬해서 둘을 같이 만족시켰다. 그룹 사이는 머리글이 아니라 경계선.
- 비활성 스펙 레이어도 목록에 선다.
- **클립보드에 직접 넣는 길이 막혀 있어서 이 창이 있다.** 블리자드가 특성·편집 모드·청사진에서
  쓰는 `CopyToClipboard`를 애드온 코드에서 부르면 `ADDON_ACTION_FORBIDDEN`이다("블리자드 UI에만
  있는 기능"). 프로브로 재봤다 — 12.1.0.69299, 2026-08-15.
- **문자열은 창 안이 아니라 별도 다이얼로그**(`DebindStorageCopyFrame`, `/debtest` 복사 창과
  같은 모양). 문자열은 한 번 읽고 복사하고 다시 안 보는 물건이라, 붙박이 상자는 대부분의
  시간 동안 빈 채로 높이만 먹는다 — 목록이 모자라던 그 높이다. 뜨면 이미 전체 선택 + 포커스라
  Ctrl-C만 누르면 된다. 편집은 막혀 있다(반쯤 지워진 문자열의 사고는 **남의 컴퓨터에서** 난다).
- **선택이 바뀌면 떠 있는 복사 창을 닫는다.** 접기/펴기로는 안 닫는다 — 그건 선택을 안 바꾼다.
- 선택도 접힘도 창을 닫을 때 버린다. 액션 테이블 참조라 닫혀 있는 동안 지워질 수 있다.

### 이번에 정한 것

- **레이어는 그룹 필드다. 그룹은 레이어를 안 넘는다.** (안 정한 것 1번의 익스포트 쪽 절반)
  한 키가 두 레이어에 걸쳐 있으면 그룹 둘로 나간다. 충실도를 잃는 게 아니라 이 창이 하는
  약속의 정직한 모양이다 — "이 레이어들의 내용물"을 보내는 것이지 "이 키의 동작"이 아니고,
  동작은 어느 레이어도 안 들고 있는 계산 결과다.
- **버전이 둘이다.** 봉투 버전(`DEB1:`, 바이트를 어떻게 쌌나)과 스키마 버전(`payload.v`).
  압축기를 갈면 옛 문자열이 죽어야 하고, 필드를 더하면 안 죽어야 한다. 한 숫자로 두면
  읽는 쪽이 그 둘을 같은 사건으로 다뤄야 한다.
- **액션 필드 명단을 Export.lua가 따로 들고 있다.** `KEYS_TO_SAVE`는 로컬이고 익스포트는
  Profile.lua에 안 붙이기로 했으므로 명단이 두 군데 있다. 어긋나면
  `tools/check-export-fields.js`가 빌드를 깬다 — 한쪽에만 필드를 더하면 아무도 오류를
  안 보고 받는 쪽에서 **조건 하나가 빠진 액션**으로 나타난다(= 더 자주 발동한다).
- **`seq`는 안 싣는다.** 받는 레이어가 이미 나눠준 번호와 부딪힌다. 배열 순서가 같은 것을
  말하므로 그룹과 액션을 `seq` 순으로 내보내고 번호 자체는 두고 온다.
- **커스텀 상태 매니페스트를 v1에 넣었다.** 문서가 "재설계 1단계 뒤"로 미뤄둔 근거는
  SETSTATE `value`가 `mode|index` 비트팩이라 포맷을 굳히면 §9-1을 미리 정하는 셈이라는
  것이었는데, **전송 포맷에서만 이름 축으로 정규화하면** 풀린다 —
  `{mode="toggle", state="$state3"}`. `$state1~5`는 개명 뒤에도 유효한 이름이라 스키마를
  안 올리고 살아남고, 저장 표현에 대해서는 아무것도 안 정한다.

### 전송 포맷 v1 — 실제로 나오는 모양

**임포트를 짜는 사람이 볼 것은 이것이다.** 아래는 지금 코드가 내는 실물이다 — 손으로 쓴 것이
아니라 프로필을 세워 `BuildExportPayload`를 돌려 찍었다.

> ⚠ **v1 안에서 두 번 바뀌었고 번호는 안 올렸다** (2026-08-14에 `layer`가 액션으로 내려갔고,
> 08-15에 그룹 층이 없어졌다). **손에 든 옛 문자열은 `v = 1`이 맞아떨어져 디코드는 되고 뜻만
> 어긋난다** — 마이그레이션도 방어 코드도 안 짓고 소유자가 지운다. 왜 번호를 안 올렸고 언제 이
> 예외가 닫히는지는 아래 "★ 전송 포맷의 근거가 무너졌다"의 머리말에 있다.

```lua
{
  v = 1,                        -- 스키마 버전. 다르면 DecodeExportString이 거절한다
  class = "DRUID",              -- 보내는 쪽 클래스. shared.classes를 읽으려면 필요
  states = {                    -- 참조된 것만. 하나도 없으면 이 필드 자체가 없다
    ["$state3"] = { mode = 0, initialValue = true, displayMessage = "Burst" },
  },

  -- 여기서부터는 **저장 구조 그대로**다. 경로가 곧 주소이고, 서술 테이블이 없다.
  shared = {
    GENERAL = {
      { type = "spell", value = 774, key = "F", seq = 3, combat = true, priority = 2,
        checkedUnits = { target = {} } },
      { type = "spell", value = 8936, key = "F", seq = 7, ["$state3"] = true },
      { type = "setstate", key = "CTRL-9", seq = 1,
        setstate = { mode = "toggle", state = "$state3" } },
      { type = "macro", value = "Kick+Pet", key = "SHIFT-G", seq = 1,
        macro = { name = "Kick+Pet", body = "/cast Kick\n/petattack",
                  icon = 132219, scope = "account" } },
      { type = "spell", value = 5176 },           -- 키가 없다 = 아무 그룹에도 안 속한다
    },
    classes = {
      DRUID = {
        [0] = { { type = "spell", value = 8921, key = "F", seq = 2, forms = 6 } },
      },
    },
  },
  char = {                      -- guid를 뗀다. "이 캐릭터"라는 뜻
    [0] = { { type = "spell", value = 22812, key = "SHIFT-G", seq = 1 } },
  },
}
```

읽는 쪽이 알아야 할 것:

- **경로가 주소다.** `shared.GENERAL` / `shared.classes[직업][특성]` / `char[특성]`, 즉 프로필이
  저장하는 그 모양이다. 서술 테이블도 레이어 **번호**도 안 나간다(2~6이 "내 클래스"라 안 통한다).
  `spec = 0`은 "그 직업 전체", 상한은 `MAX_SPEC`. `char`에서 guid를 뗀 것이 유일한 번역이다.
- **`key`가 액션에 있고, 그것이 곧 그룹이다.** 같은 `key`면 한 묶음이고, 그것을 선언하는 층이
  없다. 한 키가 레이어 둘에 걸쳐도 갈리지 않는다 — 주소가 둘일 뿐이다.
- **키를 빼고 보내면 문자열 대신 숫자가 실린다.** `type(key) == "number"` 하나로 갈린다.
  받는 쪽은 그 번호를 자기 프로필 안에서 다시 매긴다(문자열 안에서만 유일하므로).
  **원래 키가 없던 액션은 키 없이 나간다** — 아무와도 같은 그룹이 아니라는 뜻이다.
- **`seq`는 보낸 쪽 번호 그대로다.** 저장할 값이 아니라 **이 문자열 안에서만 뜻이 있는 차례**이고,
  받는 쪽이 `MAGIC + seq`를 거쳐 자기 번호로 바꾼다. 배열 차례에 안 기대는 이유는 그것이
  암묵적이어서다 — 디코드부터 배치까지 아무도 다시 담지 않아야 성립한다.
- **`macro`가 붙은 것만 스냅샷이 있다.** `type`/`value`는 그대로라 삼중 일치(이름·스코프·내용)를
  볼 수 있다. 송신 시점에 이미 댕글링이면 `macro`가 없다.
- **`setstate`가 붙으면 `value`는 없다.** 비트팩 대신 이름 축이다. `setcustom`은 손 안 댄
  `value` 그대로다(커스텀 **대상**이라 인덱스가 구조적).
- 조건은 걸린 것만 실린다. 안 건드린 축은 필드 자체가 없다.
- **배지 달린 액션은 안 나간다.** 아직 받아들이지 않은 남의 것이라 보내는 사람의 세팅이 아니다.
- 액션 필드 명단은 `Export.lua`의 `ACTION_FIELDS`이고 `KEYS_TO_SAVE`와 동기화가 강제된다
  (`imported` 하나만 뺀 전부).

`DecodeExportString(str)`은 페이로드 또는 `nil, 사유`를 준다. 사유:
`NOT_A_STRING` / `NOT_A_DEBIND_STRING` / `UNSUPPORTED_ENVELOPE` / `LIBS_MISSING` /
`BAD_ENCODING` / `BAD_COMPRESSION` / `BAD_PAYLOAD` / `UNSUPPORTED_SCHEMA`.
**붙여넣기는 남이 준 입력이라 전부 실패할 수 있고 어느 것도 오류를 던지지 않는다.**

⚠ **스펙은 액션 타입 다섯 개만 왕복시킨다**(SPELL·MACRO·MACROTEXT·SETSTATE·SETCUSTOM).
나머지 열 개는 위 실물로 한 번 확인했을 뿐 `tests/export_spec.lua`에 안 걸려 있다 —
깨져도 검사가 통과한다. 임포트 착수 전에 굳혀두는 편이 낫다.

### 닫힘 — LibSerialize v1.2.2와 `0` (결론: 우리 문제도 라이브러리 문제도 아니었다)

**결론부터: 라이브러리는 잘못이 없고, 라이브에도 영향이 없다. 핀은 유지하되 이유가 달랐고,
2026-08-14에 그 이유마저 사라져 v1.2.2로 올렸다 — 아래 "핀을 풀고 v1.2.2로 올렸다".**

v1.2.2가 음수 0을 보존하려고 넣은 검사(`LibSerialize.lua:1562`, `_WriterTable["number"]`의
첫 실행문. 앞에 다른 분기가 없어 숫자를 쓸 때마다 반드시 지난다):

```lua
if num == 0 and 1 / num < 0 then
```

`and`가 단락 평가라 `1 / num`은 `num`이 정확히 0일 때만 돈다. **IEEE 754대로면 이 코드는
옳다** — `1/0`은 `inf`, `1/(-0.0)`은 `-inf`라 `-0.0`만 정확히 걸린다.

실제로 재어본 것:

| | `1/0` | 이 검사 |
|---|---|---|
| `_retail_` | `inf` | 의도대로 |
| 데스크톱 Lua 5.1(luajit) / 5.4 | `inf` | 의도대로 |
| `_ptr_` (여기서 테스트하는 클라이언트) | **`Division by zero` 오류** | 모든 0에서 터짐 |
| `_ptr_`, 2026-08-14 다시 재어봄 | `inf` | 의도대로 |

**리테일 빌드 번호가 그 PTR보다 높다.** 그러니 "12.1이 앞으로 이렇게 바꾼다"가 아니다 —
더 새 빌드가 정상이다. 옛 빌드의 버그였거나, PTR 빌드에 진단 옵션이 켜져 있어서일 것이다.
어느 쪽인지는 안 밝혔고, 밝힐 필요도 없어졌다.

- **업스트림에 올릴 것 없음.** 남의 라이브러리에 블리자드 클라이언트 사정을 신고하는 꼴이 된다.
  (저자는 #16에서 테스트를 보강하며 "PUC 5.1.4 / 5.4 / LuaJIT 2.1에서 검증"이라고 적었다.
  셋 다 `inf`를 내므로 이 코드는 그 셋에서 영원히 통과한다. 그게 문제가 아니었던 것.)
- **우리 코드에 0 나누기가 닿는 자리 없음.** `SecureBindings.lua`의 `update_hit_bounds`가
  프레임 폭/높이로 나누지만 `w > 0 and h > 0` 가드가 이미 있다. 나머지는 상수 나누기다.
- **핀은 유지한다 — 이유는 "라이브러리가 깨져서"가 아니라 "우리 테스트 클라이언트에서 안 돌아서"다.**
  계정 결제가 없어 인게임 검증이 전부 그 PTR에서 이뤄지므로, v1.2.2를 넣으면 개발 중에
  익스포트를 한 번도 못 돌린다. PTR 설치본이 따라잡으면 올려도 된다.

#### 핀을 풀고 v1.2.2로 올렸다 (2026-08-14)

같은 PTR 설치본에서 `/print 1/0`이 이제 `inf`를 낸다. **핀을 붙잡고 있던 조건은 그것 하나였고,
그것이 사라졌다.** 업스트림 태그 `v1.2.2`(최신)를 그대로 받아 넣었다 — 우리 사본은 교체 전에
업스트림 v1.2.1과 바이트 단위로 같았으므로 버릴 로컬 수정은 없었다.

**이미 나가 있는 문자열은 그대로 읽힌다.** v1.2.1이 쓴 것을 v1.2.2로 읽으면 트리가 완전히
같다(아래 주의 하나 제외). 반대 방향 — 새 버전이 쓴 것을 옛 Debind가 읽는 경우 — 은 배포 중에
실제로 생기는 조합인데, 우리 페이로드에 담기는 것으로는 문제가 없다.

| 쓴 쪽 → 읽는 쪽 | 결과 |
|---|---|
| v1.2.1 → v1.2.1 | 기준 |
| v1.2.1 → **v1.2.2** | 기준과 동일 |
| **v1.2.2** → v1.2.2 | 음수 0과 비정규수를 보존한다(v1.2.1은 둘 다 0으로 뭉갰다) |
| **v1.2.2** → v1.2.1 | 음수 0은 읽힌다. **비정규수(denormal)는 조용히 다른 값으로 읽힌다** |

마지막 칸이 유일한 비호환이고 **우리에게는 닿지 않는다.** 페이로드의 수는 주문/아이템 ID,
`spec`, 조건 마스크, `seq`/`order`, 아이콘 ID뿐이라 `2.2e-308`보다 작은 값이 나올 자리가 없다.
그래도 적어두는 이유는, 나중에 실수(측정치, 비율)를 페이로드에 실으면 그때 살아나는 칸이기 때문이다.

**인게임 왕복까지 확인됐다.** 갱신된 PTR에서 정상으로 돈다 — 핀을 붙잡고 있던 `1 / num < 0`이
그 클라이언트에서 더는 터지지 않는다는 뜻이고, **이 항목은 이걸로 닫힌다.**

헤드리스가 그 확인을 대신 못 한 이유는 남겨둔다. `npm test`(fengari)는 압축을 못 풀어 왕복의
절반만 보고, 데스크톱 lua로는 전체 왕복이 돌지만 **여기 깔린 것은 5.4.6이라 와우의 5.1이
아니다**(5.1 확인은 CI가 한다). 라이브러리를 올릴 때 마지막 한 칸은 매번 인게임이다.

여기서 남은 교훈은 이 문서 밖으로 옮겼다 — `testing-a-change.md` §4. 원래는 "인게임 실패를 읽을
때 PTR 빌드를 후보에 넣는다" 하나였는데, 하루 만에 그 차이가 사라지면서 **"그 차이에 기대어
핀·우회를 걸었으면 다시 재봐야 한다"**가 붙었다. 둘 다 익스포트/임포트에 국한된 이야기가 아니고,
이 문서가 닫히면 묻힌다. 위 측정표와 핀 결정은 그 규칙의 근거이므로 여기 남는다.

## 전제부터 틀렸던 것

이슈에 "가장 쓸모 있는 익스포트가 가장 파괴적인 임포트"라고 썼는데 **절반은 틀렸다.**

`actions`는 레이어당 순서 있는 리스트고 액션에 고유 키가 없다(`Profile.lua`의 `AddAction`).
그래서 임포트는 **언제나 append**다. 액션이 액션을 덮어쓰는 일은 구조적으로 없다.

- 파괴적인 것은 **키뿐**이다.
- 액션 쪽 문제는 파괴가 아니라 **중복**이다(같은 걸 두 번 넣으면 둘이 된다).

그리고 "키 충돌"도 실은 충돌이 아니다. 한 키에 액션 여럿이 조건으로 갈리는 것이 이 애드온의
정상 상태다. 남의 `F`가 내 `F` 옆에 붙으면 후보가 느는 것이지 덮어쓰는 것이 아니다.
실제로 나빠질 수 있는 것은 **가림**(앞선 무조건 액션이 뒤를 도달 불가로 만드는 것)이고,
그건 이미 판정과 빨간 글씨가 있다(`GetBindingIssue`, `DebindUI.lua`의 도달 불가).

## 아직 안 풀린 진짜 어려움 — 그룹이 레이어를 가로지른다

한 키의 동작은 레이어가 쌓여서 나온다. 그래서 "그룹"은 어느 레이어에 들어 있는 물건이 아니라
**계산 결과**다. 담을 그릇이 없다.

- 레이아웃 축은 레이어여야 한다. 실제로 저장돼 있는 유일한 구조고, 체크해서 목적지를 정하는
  단위이기도 하다.
- 그런데 의미 있는 묶음인 키 그룹은 레이어를 넘나든다. 둘 다 중첩 축으로 쓸 수 없다.
- 조각을 다 보내도 받는 쪽 레이어 배치가 한 칸 다르면 **같은 액션 같은 키인데 다르게 동작**한다.
  빠진 것도 덮어쓴 것도 없는데 결과가 다르다.

그래서 창이 약속하는 것은 "이 동작을 보낸다"가 아니라 **"이 레이어의 내용물을 보낸다"**이고,
그 차이를 창이 스스로 말해야 한다.

키 경계에 "이 키는 다른 레이어에도 있음" 표식을 붙이는 선까지는 이야기했다. 선택을 막지도,
자동으로 딸려오게 하지도 않는다 — 자동으로 딸려오면 레이어 체크박스가 거짓말이 된다.

## 익스포트 창

- **크다.** 체크박스 다섯 줄로는 안 된다. 내 Spec 레이어에 뭐가 들었는지 나도 다 기억 못 한다.
- 레이어가 그룹(머리글), 그 안에 액션. **액션이 체크 대상**이다.
- 기본값 **전부 선택**. 그냥 다 보내기는 열고 확인만 하면 끝난다.
- tristate 3단: 전체 → 레이어 → 액션.
- **비활성 스펙도 연다.** 데이터는 이미 있다 — 클래스 레이어가 `classes[클래스]` 밑에
  스펙별로 앉아 있어서 발라스로 접속해 있어도 페럴 레이어를 읽는 데 문제없다.
- **잘못된 액션도 그냥 싣는다.** 검사하지 않는다. 받는 쪽에서 빨간 글씨로 보이고 지우면 된다.
  이것 하나로 "보내는 쪽 클래스 주문을 받는 쪽이 못 가졌을 때" 류의 질문이 전부 사라진다.
  레이어 매핑(발라스 → 페럴)도 같은 결로 풀린다. 받는 쪽이 고르면 된다.
  단, 빨간 글씨가 **원리적으로 못 잡는** 부류가 하나 있다 — 송신자 로컬 참조(블리자드 매크로,
  커스텀 상태). 잘못된 게 아니라 "성공"해서 엉뚱한 걸 가리키는 참조다. 전송 포맷 절에서 막는다.

이슈에 물었던 "키 하나냐 / 탭 하나냐 / 캐릭터 전체냐"는 **없어진다.** 셋 다 같은 창에서
나온다. 액션 하나만 찍으면 키 하나, 그룹 헤더 찍으면 탭 하나, 다 찍으면 전체.
별개 기능 셋이 아니라 선택 단위 하나였다.

## 전송 포맷

> ⚠ **이 절은 무효다** (2026-08-15, 세 번째 ★). 그룹 층도 `group.id`도 없어졌고 키가 곧 그룹이다.
> **남겨두는 이유는 기각 사유 때문이다** — 별도 id를 둔 이유 셋은 전부 참이었고, 합성 키가 그

```
group { id, key = "F" | nil, layer = <서술>, actions = { ... } }
```

(`layer`는 08-13에 그룹 필드로 정해져 들어갔다 — "구현된 것". 레이어는 **아이디가 아니라
뜻으로** 나간다: `{scope="general"}` / `{scope="class", class="DRUID", spec=2}` /
`{scope="character", spec=0}`. 레이어 번호 2~6은 "내 클래스"라 보내는 쪽 번호가 받는 쪽에서
같은 것을 안 가리킨다.)

그룹 정체성을 `key`에 얹지 않고 **별도 id**로 둔다. 그래서:

- "키 빼고 내보내기"는 전 그룹의 `key`를 nil로 떨구는 것뿐이고 `id`는 남아 **묶음이 살아남는다.**
  조건부 바인딩이 여러 액션으로 쪼개져 있는데 키를 떼면 액션 더미가 되는 문제 — 답변자가 말한
  "키 빼고 액션만" 옵션의 실제 결함 — 이 여기서 막힌다.
- 가짜 키(`export_key_1` 같은 것)가 프로필로 흘러들어갈 일이 없다. 솔버도 `SetBindingClick`도
  안 건드리고 이름공간 충돌도 없다. 애초에 임포트 확정 전까지는 그냥 데이터라 솔버가 볼 일이 없다.
- 임포트 UI에서 그룹을 가리킬 이름이 생긴다. `key`는 nil일 수도 중복일 수도 있어 못 쓴다.

그 외 포맷에 적을 것 둘:

- **버전 필드를 v1부터 박는다.** 결정할 것은 없고, 첫 문자열에 없으면 나중에 구분할 길이
  없어지는 one-way door라 잊지만 않으면 된다.
- 레이어가 포맷 어디에 붙는지(그룹 필드냐 액션 필드냐 = 그룹이 레이어 안 물건이냐)는
  안 정한 것 1번과 같은 결정이라 거기서 같이 정한다.

직렬화 자체는 새로 설계할 것이 없다 — `KEYS_TO_SAVE`(`Profile.lua`)가 이미 저장 시점에
비등록 필드를 걷어내는 화이트리스트라 익스포트가 그대로 물려받으면 된다.

### MACRO — 본문을 실어 보내고, 복구는 삼중 일치일 때만 참조로

`Constants.MACRO` 액션은 `value`에 매크로 **이름**만 들고, 본문은 빌드 시점에
`GetMacroInfo`로 블리자드 매크로 저장소에서 읽는다(`Misc.lua`의 `ConvertToMacroText`).
이름은 송신자 로컬 참조라 "잘못된 것도 싣는다 → 빨간 글씨" 안전망이 못 잡는 부류다 —
받는 쪽에 같은 이름의 **다른** 매크로가 있으면 참조가 "성공"해서 조용히 그걸 실행한다.

→ 익스포트 시 MACRO는 type을 유지한 채 **본문 스냅샷 + 원 매크로 이름 + 스코프(공유/캐릭터)**를
같이 싣는다. 임포트에서 받는 쪽에 이름·스코프·내용이 **전부 일치**하는 매크로가 있으면
MACRO(살아 있는 참조)로 복구하고, 아니면 스냅샷을 본문으로 MACROTEXT로 떨어뜨린다.

- 같은-이름-다른-내용은 내용 비교에서 걸러져 MACROTEXT로 가므로 엉뚱한 매크로를 쏠 일이 없다.
- 자기 백업 재임포트는 삼중 일치가 성립해 **참조가 살아 돌아온다** — 익스포트 시점에 플랫하게
  MACROTEXT로 구워버리는 안이 잃던 것.
- 스냅샷·스코프는 전송 포맷과 대기 영역까지만 산다. 프로필에는 MACRO 또는 MACROTEXT로 확정돼
  들어가고, 남는 필드는 `KEYS_TO_SAVE` 정리가 어차피 걷어낸다.
- 판정 시점은 **커밋.** 커밋 뒤에 받는 쪽이 매크로를 만들어도 재판정하지 않는다 —
  MACROTEXT로 남을 뿐 틀리지는 않는다.
- **다른 타입은 안 굽는다.** `CanConvertToMacroText`가 받는 SPELL·ITEM·MOUNT 등은 ID가
  전역이라 받는 쪽에서도 올바르게 해석되고, 모르는 것은 빨간 글씨가 잡는다. 매크로텍스트로
  구우면 타입 정보가 사라져 커버리지 **밖으로** 나간다(`/cast 모르는주문`은 조용한 no-op).
- 송신 시점에 이미 댕글링이면 `GetMacroInfo`가 nil이라 스냅샷 없이 나간다. 그대로 싣고 기존
  규칙("잘못된 것도 싣는다")에 태운다. → "없는 매크로가 받는 쪽에서 실제로 빨갛게 뜨는지"
  확인이 안 정한 것 7번에 들어간다.

### 커스텀 상태 — 이름 재설계 뒤에, manifest로 싣는다

MACRO를 풀어도 커스텀 상태는 남는다. 액션의 상태 참조는 **인덱스**라
(SETSTATE의 `mode|index` 비트팩, `$state1..5`, `MACROTEXT_ARG_CUSTOM_STATE`) 매크로텍스트로
구워도 받는 쪽 상태 3을 가리키는 건 똑같고, 인덱스는 항상 "성공"하는 참조라 빨간 글씨 밖이다.

> 정정(08-13): 여기 `/click DebindCustom3`이 예로 적혀 있었는데 **그건 상태가 아니다.**
> `SETCUSTOM`은 이름과 달리 커스텀 **대상**(포커스 같은 유닛 슬롯)을 잡는 액션이고
> (`UnitWatch.lua`, `L["TYPE_SETCUSTOM_DESC"]`), 그 인덱스는 구조적이라 어느 설치본에서나
> 같은 뜻이다. 그래서 매니페스트 대상이 아니고 손대지 않고 그대로 나간다.

선행 작업은 이미 별도로 설계가 끝나 있다 — **[custom-states-redesign.md](custom-states-redesign.md)**
(설계 확정, 코드 미착수). 이름(`$anyname`)이 그 문서 1단계고, `$state1~5`는 유효한 이름으로
남아 조건 저장 쪽 마이그레이션이 없다. 익스포트 포맷도 그 문서 §8이 이미 못 박았다:
**세트가 참조하는 상태 목록(manifest)을 이름·정의째 명시적으로 싣는다** — 정의가 나중에
레이어 오버라이드(§4-6)를 얻어도 포맷이 안 흔들리게.

- 이름이 되면 댕글링이 **보인다.** 없는 이름은 잡을 수 있다 — 늘 붙어버려서 못 잡던 인덱스와
  다른 점. `BINDING_ISSUE_UNDEFINED_STATE`(그 문서 ⚑2, 0단계)가 정확히 그 빨간 글씨다.
- 임포트에서 없는 이름은 만든다. **있는 이름은 작업대에서 확인창으로 푼다** (2026-08-13).
  키를 그룹마다 한 줄로 정리하는 것과 같은 무늬 — 배치가 싣고 온 상태 이름마다 줄을 주고,
  손댈 게 필요한(충돌 나는) 것만 위로 올린다. 줄마다 셋:
  1. **이 이름 그대로 — 내 정의를 덮어쓴다.** 내 기존 액션이 그 상태를 쓰고 있으면 확인창이
     그걸 말해야 한다(개수까지).
  2. **내 정의 유지** — 정의는 안 건드리고, 온 액션들이 내 상태에 붙는다.
  3. **새 이름으로 받기** — 배치 안의 참조를 재작성한다. 재작성이 닿아야 하는 네 군데는
     재설계 문서 §3-4에 이미 목록이 있다(조건 키 / 매크로 본문 / SETSTATE / 다른 상태의
     expr). 작업대 물건은 아직 전송 포맷 데이터라 프로필 개명보다 오히려 범위가 좁다.
- **정의 내용까지 일치하면 조용히 통과.** 자기 백업 재임포트가 확인창 세례를 받으면 안 된다 —
  MACRO의 삼중 일치와 같은 결. 이름이 같은데 내용이 다를 때만 줄이 위로 온다.
- 이 확인창이 격리 원칙의 구멍도 막는다. 상태는 배치 소유가 아니라 전역 공유물이라, 조용한
  덮어쓰기는 승인 전에 **기존** 액션의 동작을 바꾸는 뒷문이었다. 덮어쓰기가 명시적 선택이
  되면 그 선택이 곧 승인이다. 적용 시점은 커밋.
- 순서: SETSTATE `action.value`가 지금 `mode | index` 비트팩이라(그 문서 §9-1) 이름 축으로
  문자열화되기 전에 익스포트 포맷을 굳히면 그 결정을 미리 못 박는 셈이 된다. 커스텀 상태를
  싣는 부분은 재설계 1단계(이름)·§9-1 결정 **뒤**가 맞다.

### 레이어 매핑 — 레이어 대 레이어

> ⚠ **이 절은 무효다.** 여기 적힌 셋은 전부 지웠고, 아래 "★ 레이어는 번역 대상이 아니다"가
> 이긴다. **남겨두는 이유는 기각 사유 때문이다** — 남의 특성 번호를 그대로 옮기지 않는다는
> 판단 자체는 맞았고, 틀린 것은 *그러니 내 자리로 밀어 넣는다*는 결론이었다. 그 좌표는 옮길
> 필요가 없다.

`DebindStorage.LayerKey(descriptor)` / `.DefaultDestinationLayerID(descriptor)` /
`.CollectSourceLayers(payload)`.

- **키를 값에서 만든다.** 보내는 쪽은 한 레이어의 그룹들이 descriptor 테이블 하나를 공유하지만
  그건 **보내는 쪽 메모리에서만** 참이다. 직렬화-역직렬화가 그룹마다 다른 테이블을 줘도 되므로
  "같은 레이어에서 왔다"를 참조 동일성으로 말할 수 없다. → `"class:DRUID:2"` 같은 문자열.
- **남의 직업 레이어는 스코프를 지키고 특성을 버린다.** 특성 번호는 직업을 건너면 뜻이 다르다
  (드루이드 2 = 야성, 마법사 2 = 화염). 번호를 옮기면 매핑처럼 생긴 추측이 되므로, 참인 부분만
  남겨 **내 직업/공용**으로 간다.
- **우리에게 없는 특성은 공용으로.** 특성이 더 많은 직업에서 온 문자열이 정상 입력이다.
  그래서 목적지를 `GetLayerID`로 계산하지 않고 레이어를 훑어서 찾는다 — 그쪽은 범위 밖 spec에
  **assert로 죽는다.** 훑는 편이 레이어 ID 산수를 `LAYER_INFOS` 한 자리에 두는 효과도 있다.
- 매핑 줄은 일반 → 직업 → 캐릭터 차례고, 직업 중에서는 내 직업이 앞선다(진짜 매핑이 있는
  것이 그것뿐이라서). 줄마다 그룹 수·액션 수를 달고 나온다.

### 서랍

`AddBatch` / `GetBatches` / `GetBatch` / `DeleteBatch` / `GetBatchPayload` /
`GetSecondsUntilExpiry` / `IsExpiringSoon`.

- **저장하는 것은 문자열이고 페이로드가 아니다.** 문자열은 이미 압축돼 있고(300액션 ≈ 1.4KB)
  페이로드는 같은 데이터를 펼쳐 놓은 것이다. 페이로드를 저장하면 애드온을 가른 이유가 없어진다.
  덤으로, 나중 버전이 그 문자열을 못 읽게 돼도 **사용자가 도로 복사해 갈 원본은 남는다.**
  디코드는 열 때 하고 결과는 메모리에만 둔다.
- **못 읽는 문자열은 서랍에 안 들어간다.** 붙여넣는 자리에서 거절한다 — 열 때마다 실패하는
  줄이 서랍에 앉아 있으면 안 된다.
- **지운 id는 재활용 안 한다.** 커밋된 액션에 `imported = <batch id>`가 남으므로(아래 "배지"),
  번호를 다시 쓰면 그 배지가 남의 배치를 가리킨다.
- ~~만료는 **판정만 하고 실행하지 않는다.** 목록이 받은 날짜와 임박을 보여주고, 핀을 꽂으면
  만료가 미뤄지는 게 아니라 아예 없어진다.~~ → **판정도 핀도 걷어냈다** (2026-08-15, 소유자:
  *"자동 삭제가 지금 없으니까 핀도 보여주지마"*). 실행이 없는 판정은 화면에 **아무 일도 안
  일어나는 날짜**를 띄우는 것이고, 핀은 일어나지 않는 일에서 빼주는 컨트롤이었다. 남은 것은
  받은 날짜 한 줄뿐이고 그건 사실이다.

  **설계가 기각된 게 아니라 안 지어졌다.** 서랍은 실제로 자란다. 다만 *"조용히 사라지는 것이
  이 서랍이 내면 안 되는 유일한 결과"*는 그대로라, 되살릴 때는 쓸어내는 쪽이 아니라 **묻는**
  쪽으로 짓는다. 그때까지 아무것도 판정하지 않는다 — 판정만 있고 실행이 없는 것은 둘 다 없는
  것보다 나쁘다. 화면에 약속이 하나 서기 때문이다.
- 배치가 들고 있는 것: `id`, `received`, `text`, `source`, `pinned`, 그리고 작업 넷 —
  `layers`(소스 레이어 키 → 목적지 layerID), `keys`, `excluded`, `states`.
  전부 저장 가능한 평범한 값이라 `/reload`를 건넌다(스펙이 그걸 검사한다).

### 아직 안 정한 것 (데이터 층이 비워둔 자리)

`keys` / `excluded` / `states`는 **모양만 잡아두고 뜻은 UI가 정한다.** 특히 `keys[groupID]`가
"안 정했다"와 "원래 키 그대로"를 같은 nil로 쓸지, 셋을 명시적으로 적을지는 2창을 짤 때 결정.

## 임포트 — **작업대를 접었다** (2026-08-14)

> 이 절 아래는 전부 2026-08-14에 뒤집힌 것이다. 앞 판(대기 영역 / 1창 / 2창 / 프로필 밖에서
> 키를 정하는 작업대)은 **더 이상 설계가 아니다.** 왜 접었는지가 여기 있고, 되살리려면
> 아래 "왜 접었나"를 먼저 반박해야 한다.

### 새 모양

```
Import 탭 = 서랍            받아서 쌓아두는 곳. 병합은 여기서 안 한다
  배치 행 → [가져오기 시작]
       → 커스텀 상태 이름 충돌만 묻고
       → 기본 레이어 매핑으로 프로필에 넣는다, 배지 달아서 (= 격리)

Overview = 병합하는 곳
  [가져온 것만] 필터
  묶는 축: 단축키 | 가져온 그룹
  키 그룹 조작: 병합 / 교체 / 덮어쓰기
  [전부 승인] → 배지 제거 → 끝
```

흔한 경우는 **버튼 두 번**이다 — [가져오기 시작] → [전부 승인].

### 왜 접었나

**작업대의 기능이 오버뷰를 넘어서면 비대칭이다.** 작업대는 "그룹마다 키 하나"를 하려 했는데
오버뷰에는 그런 것이 없다 — `DebindKeyHeaderMixin`은 라벨일 뿐이고(`Init`이 글자를 쓰고
`Update`는 빈 함수다), 키를 거는 길은 `SetActionKey(action, key)` 하나짜리며, 지정 모드도
커서 밑의 행 하나를 본다. 조건으로 넷으로 갈린 지정을 F에서 G로 옮기려면 지금도 네 번 해야
하고 하나 빠뜨리면 세트가 조용히 갈라진다.

그러면 편집기가 둘이 된다. "왜 받은 것에만 저게 되지"가 되고, 같은 일을 하는 코드가 두 군데
선다. 그래서 **기능을 오버뷰로 옮기고 작업대에서는 뺐다.**

**그리고 앞 판의 전제 하나가 원래 약했다.** *"프로필에 들어가면 묶음이 사라진다"*고 적혀
있었는데, 배지가 배치 번호와 **그룹 번호**를 들고 있으면 안 사라진다. 게다가 오버뷰 왼쪽
열은 이미 키로 묶어서 그린다 — 작업대가 만들려던 화면이 거기 있었다.

### 서랍은 남는다 (역할만 좁다)

**아직 병합을 시작하지 않은 것**을 담는다. 원문 문자열, 출처, 받은 날짜. ~~핀, 만료 판정.~~
(둘은 2026-08-15에 빠졌다 — 위 "서랍" 절.) 지금 코드가 그대로 그것이다
(`DebindStorage/Workbench.lua`, `WorkbenchUI.*`).

- **커밋해도 서랍에서 안 지운다** (앞 "안 정한 것" 3번이 여기서 닫힌다). 승인 전에 배치째
  지우고 다시 시작할 수 있어야 하고, 그러려면 원문이 남아 있어야 한다. 행에 "이미 가져옴"
  표시만 붙는다.
- `DebindStorage`를 가른 이유 둘(압축 라이브러리, 서랍의 SavedVariables)이 **둘 다 그대로**다.

### 액션에 붙는 것 — 숫자 둘

```
imported     = <배치 번호>
importGroup  = <그 배치 안의 그룹 번호>
```

**키로는 그룹을 복원할 수 없다.** 배치 안에서 그룹은 (레이어, 키)인데 `stripKeys`로 온
문자열은 전 그룹이 키가 없어서 그 둘로 구별이 안 된다. 포맷이 `group.id`를 따로 둔 이유가
정확히 그것이다(앞 "전송 포맷" 절).

둘 다 `KEYS_TO_SAVE`에 등록해야 저장된다. `groups`는 이미 파티 그룹 조건이 쓰고 있으니
이름 충돌 주의.

### 오버뷰가 새로 가져야 하는 것 넷

1. **키 그룹 조작 — 병합 / 교체 / 덮어쓰기.** 셋이 한 동작으로 접힌다: 전부 "이 그룹에 키 X를
   준다"이고, X가 이미 차 있을 때 무엇을 하느냐만 다르다.
   - X가 비어 있으면 그냥 옮긴다(물을 것 없음)
   - X가 차 있으면 셋 중 하나를 묻는다 — **병합**(둘이 한 키에), **교체**(서로 맞바꿈),
     **덮어쓰기**(원래 X에 있던 것은 키를 잃고, 이 그룹이 X를 갖는다)

   상대 키는 긴 서브메뉴로 고르지 말고 **눌러서 지목한다** — 지정 모드의 키 캡처를 그대로
   쓴다. 셋 다 `SetKeyForActions(액션들, 키)` 하나 위에 선다.

   #### → **만들었고 화면으로 확인했다** (2026-08-15)

   확인한 것: 충돌 대화상자(버튼 셋, 개수, 합치기/덮어쓰기/취소·ESC) · 옮긴 뒤 키 그룹을 따라가는
   스크롤과 강조 · 도착 그룹에 키 주기(머리글이 진짜 키로 바뀌고 배지가 같이 떨어지고 **보낸
   사람 순서가 유지된다**) · 이미 키가 있는 키 그룹을 통째로 옮기기(오프스펙 섞인 키 포함).

   **남은 것은 오버레이 하나**(아래 ⚠).

   - **데이터 층** (`Profile.lua` + `tests/keygroup_spec.lua`): `SetKeyForActions`,
     `ClearKeyForActions`, `MoveKeyGroupToKey`, 수집 함수 둘
     (`CollectImportGroupActions` / `CollectKeyGroupActions`).
   - **UI** (`DebindUI.lua` + `DropDownMenus.lua`): 왼쪽 열 우클릭 메뉴의
     [여기 있는 것 전부에 키 지정] → 지정 모드의 키 캡처 → 차 있으면 질문.

   아래가 그 자리에서 정해진 것들이다.

   **목적은 그룹 전원에게 주는 것이다.** 대상은 화면이 아니라 **이 캐릭터의 열한 레이어**를
   `importGroup`으로 훑어 모은다(`EnumerateAllProfileLayers`). 이유가 둘이다:

   - 그려진 것에서 모으면 [모두 거절]이 물렸던 구멍에 다시 빠진다
     (`FindElementDataByActionInfo`는 열린 탭의, 필터를 통과한 행만 안다).
   - **그룹은 도착할 때부터 레이어를 가로지른다.** 그룹이 키 하나이고 자리는 액션마다다
     (`PlanImport`). 도착 이후에도 `MoveAction`이 갈래를 늘린다 — 아래 "키 없는 것들" 절 참고.

   **점유자 쪽도 같은 함수 위에 선다.** 한쪽만 모자라면 교체가 반만 일어나고, 덮어쓰기는 "X는
   이제 이 그룹 것"이라 해놓고 다른 자리에 그대로 남긴다.

   **다른 직업의 레이어는 범위 밖이다.** 여기 한때 "프로필 전체"라고 적혀 있었는데
   (`ForEachStoredActionList`), 그건 오프스펙이 화면에 없던 때의 말이다. 지금 열한 레이어 밖에
   남는 것은 **다른 직업 레이어뿐**이고, 그건 안 훑는 편이 맞다:

   - **키는 키보드의 것이고, 그쪽은 다른 키보드다.** "이 키는 이제 이 그룹 것"은 지금 도는 열한
     레이어에 대한 말이다. 그 말을 접속한 적 없는 직업까지 끌고 가면, 보여준 적 없는 충돌을 놓고
     본 적 없는 바인딩을 고쳐 쓴다 — 배지가 막으려는 바로 그것이다(`CollectImportedActions`가
     같은 이유로 같은 자리에 선다).
   - **두고 온 멤버는 아무것도 안 잃는다.** 배지·그룹·순서를 그대로 들고 있어서, 그 직업으로
     접속하는 날 그것들은 여전히 한 묶음이고 **그 키보드의 점유 상황을 보고** 키를 받는다. 그
     물음에 답할 수 있는 자리가 거기뿐이다.
   - 대신 그룹이 반만 처리되는 상태가 실재한다. 그건 이 절이 만든 것이 아니라
     `devdocs/showing-off-spec-actions.md`의 "안 정한 것"이 이미 들고 있는 물음 — **다른 직업
     레이어에 남은 배지를 어디서 말하나** — 과 같은 하나다.

   **그 대가는 화면 밖에서 바뀔 수 있다는 것이고, 그건 숫자로 갚는다.** `ApproveAllImported`가
   같은 처지였고 답은 "전부 손대되 누르기 전에 숫자를 화면에 둔다"였다. 여기서 그 자리는
   **충돌 질문**이다.

   **질문이 왜 여전히 숫자를 말해야 하나 — 전제가 바뀌었다.** 예전 근거는 "오프스펙 점유자는
   화면에 없다"였고 그건 없어졌다(오프스펙 행이 왼쪽 열에 선다). 남은 근거는 **필터**다:
   [가져온 것만]이 켜져 있으면 X를 들고 있는 *내* 키 그룹은 통째로 숨어 있고, 그게 하필
   임포트의 정상 경로다. 그러니 질문은 오프스펙 개수를 따로 세지 말고 **점유자 수 하나**를
   말하면 된다 — 세는 집합과 (필터를 끄면) 보이는 집합이 이제 같다. 실제로 같은 걸음이다:
   `BuildKeyboardElements`도 `EnumerateAllProfileLayers`로 키와 키 없는 그룹을 세운다.

   ~~**제일 날카로운 경우:** X의 점유자가 전부 오프스펙이면 화면에서 X는 비어 있는데 질문이
   뜬다.~~ → **없어졌다**(2026-08-14, 오프스펙 행). 그 자리를 위의 필터가 물려받았고, 이쪽이
   더 순하다 — 필터는 사용자가 켠 것이라 끄면 보인다.

   **`seq`는 `importOrder` 차례대로 발급한다.** 한 액션씩 주면 만진 차례대로 번호가 붙어서 보낸
   사람의 순서가 사라진다. 그래서 이 조작은 편의가 아니라 순서를 지키는 유일한 길이다.
   `tests/keygroup_spec.lua`가 그것부터 세운다 — 저장 배열의 차례와 `importOrder`를 어긋나게
   해두고, 순진한 구현에서 실제로 빨갛게 뜨는 것을 보고 넣었다.

   - **자리를 읽는 규칙은 `MakeRow`와 같다**(`PlacementRank`): 키가 있으면 `seq`, 없으면
     `importOrder`. 키를 떼도 `seq`는 남으므로(`SetActionKey`), 잠깐 걸었다 뗀 멤버가 그 남은
     번호로 자기 그룹을 앞지르는 것을 막는 자리가 이것이다.
   - **각자 자기 레이어의 맨 뒤에 선다.** 새로 오는 것에 `PlaceLast`가 하는 일과 같고, 병합의
     뜻과도 맞는다 — 방금 옮겨온 키 그룹이 원래 있던 키 그룹 뒤에 선다. 번호는 레이어 안에서만 뜻이
     있으므로(`GetNextSeq`) 레이어를 가로지르는 키 그룹은 레이어마다 자기 안에서 줄을 선다.
   - **셋은 같이 지운다**(`imported`/`importGroup`/`importOrder`). 키를 정하는 것이 곧 승인이다 —
     자기 키보드에 직접 올려놓은 것에 더 승인할 것이 없다. 그리고 놓이고 나면 `importGroup`은
     없는 키 그룹의 머리글이고 `importOrder`는 `seq`가 든 자리를 가리킨다.

   **재빌드는 다 쓰고 나서 한 번.** `SetActionKey`는 액션마다 `UpdateBindings` + `Refresh`를
   부른다([모두 거절]에서 같은 값을 치렀다). 그래서 `SetKeyForActions`는 **재빌드를 안 한다** —
   `Profile.lua`는 액션을 놓기만 하고 바인딩이 언제 올라가는지는 안 정한다
   (`PlaceImportedActions`가 같다). 부르는 쪽이 다 쓰고 한 번 올린다.

   **키를 잃은 액션은 안 지운다.** `key = nil`이면 바인딩까지 못 가고 회색으로 남는다
   (아래 "이미 되어 있는 것"). 되돌릴 수 있는 상태다.

   낫다.

   #### 어디서 시작하나 — 왼쪽 열 행의 우클릭 메뉴

   문서가 "상대 키는 눌러서 지목한다"까지만 정해놨고, **키 그룹을 고르는 입구**는 안 정해져 있었다.

   | | | |
   |---|---|---|
   | 왼쪽 열 행의 우클릭 메뉴(`SetupOrderDropdownMenu`) | **채택** | 이 열이 이미 가르치고 있는 손짓이고(행 툴팁이 우클릭 줄을 들고 있다), 새 프레임도 새 아트도 필요 없다. 배지 행에서는 [받기]/[버리기] 옆에 서는데 그게 맞다 — **같은 물음의 세 번째 답**이다(키를 정하는 것이 곧 승인이라 배지도 같이 떨어진다) |
   | 키 머리글에 버튼 | **기각** | 머리글은 마우스를 안 먹는 라벨이고, 거기에 컨트롤을 얹는 것은 폴드 화살표를 기각할 때 이미 답이 난 물음이다("컨트롤은 눈을 끈다", 아래 "폴드는 안 한다") |
   | 키 머리글의 우클릭 | **기각** | 컨트롤은 안 늘지만 아무 표시가 없어서 아무도 못 찾는다. 행 우클릭은 적어도 툴팁이 가리키고 있다 |
   | 스트립에 버튼 | **기각** | 대상이 하나로 안 정해진다. 스트립의 버튼은 전부 "배치째"인데 이건 키 그룹 하나에 대한 것이다 |

   **대상은 이 행이 아니라 이 행이 속한 키 그룹이다**(`CollectKeyGroupForAction`). 무엇이 한 묶음인지는
   왼쪽 열이 머리글 하나 밑에 그리는 것 — 같은 키에 걸린 전부이거나, 키 없이 온 것이면 도착
   그룹이다. `BuildKeyboardElements`가 그 두 물음으로만 열을 가르므로 세 번째 경우가 없다.
   키도 그룹도 없는 액션에는 항목을 안 세운다: 아무 키 그룹도 아니고, 액션 하나에 키를 거는 것은 지정
   모드가 예전부터 하던 일이다.

   #### 질문의 문구 (`KEY_GROUP_CONFLICT`)

   > `F`에는 이 캐릭터의 모든 전문화를 통틀어 이미 `3`개가 걸려 있습니다.
   > `키를 모름 #2`이(가) 그 키로 가면 그것들은 어떻게 할까요?

   - **"이 캐릭터의 모든 전문화를 통틀어"가 수집 범위를 그대로 말한다.** 다른 직업은 안 세고
     안 건드리므로 입에 올리지 않는다.
   - 키 그룹의 이름은 **머리글의 낱말 그대로**다(`KeyGroupLabel`). 머리글과 이 문장이 같은 키 그룹을 두
     이름으로 부르면 읽는 사람은 둘이라고 생각한다 — 그래서 머리글도 이 함수를 지난다.
   - 버튼은 **합치기 / 덮어쓰기 / 취소**. "합치기"에 경고를 안 다는 이유: 한 키에 조건으로
     갈린 액션 여럿이 이 애드온의 정상 상태다. "덮어쓰기"는 말이 실제보다 세지만 — 지워지지
     않고 키만 잃는다 — 그걸 바로잡는 것은 버튼이 아니라 위의 문장이다.
   - 버려진 짝: **둘 다 두기 / 기존 것 지정 해제.** 정확했지만 두 버튼이 서로 다른 물음에
     답하고 있었다 — 앞은 "이 키 그룹이 어떻게 되나", 뒤는 "저것들이 어떻게 되나". 나란히 선 버튼
     둘은 같은 물음의 두 답이어야 한다.

   #### 키 그룹이 어디로 갔는지 보여준다

   키가 바뀌면 왼쪽 열에서 자리가 통째로 옮겨간다(키로 묶어 정렬하므로). 새 자리가 화면 밖이면
   **조작이 아무 일도 안 한 것처럼 보인다.** `SetActionKey`가 액션 하나에 하던 일과 같은 것이고,
   여기서는 키 그룹의 첫 줄이 대상이다 — 발동 순서로 첫 줄이라 머리글 바로 아래이고, 거기가 보이면
   키 그룹이 보인다.

   고르는 것과 스크롤이 **둘 다** 필요하다. 선택은 왼쪽 열을 자기 자리로 굴리고
   (`RefreshKeyboard`가 `isCurrent`를 찾아간다) 강조로 어느 줄인지 짚어주며, 오른쪽 목록은 그
   열을 안 보므로 `ScrollActionIntoView`가 따로 굴린다.

   #### 겨눔은 한 번 쓰면 끝난다

   지정 모드는 원래 **누른 그 순간의 커서 밑 행**을 겨눈다. 키 그룹을 겨눈 동안에는 커서를 아예 안
   본다 — 대상은 메뉴에서 이미 골랐고, 그 키 그룹의 행들은 오버레이 밑이라 가리킬 수도 없다.

   - 키 하나를 받으면 **모드를 끈다.** 켜둔 채로 겨눔만 비우면 다음에 누르는 키가 말없이 커서
     밑의 행으로 간다 — 사용자가 연 적 없는 지정 모드가 열려 있는 셈이다.
   - **ESC는 지우개가 아니라 그만두기다.** 그 갈래가 지우는 것은 커서 밑의 행인데 지금 커서
     밑에 있는 것은 오버레이다. 그리고 아직 아무것도 안 걸었으므로 지울 것도 없다.
   - 오버레이의 두 줄이 그 둘을 말한다(`BIND_MODE_KEY_GROUP`, `..._HINT`).

   #### ⚠ 안 정한 것 — 오버레이 둘이 똑같이 생겼다 (2026-08-15, 화면 보고 나온 것)

   > 상태: **문제만 확인됨. 고치는 안은 아래 셋 중 안 골랐다.** 지금 코드는 아래 "지금 모양"
   > 그대로 서 있다.

   글자만 바꿔 쓴다. 그래서 같은 옷을 입고 규칙이 다르다:

   두 가지로 도는 것 자체가 문제**라는 것이 소유자 지적이고, 문구를 더 정확히 쓰는 것으로는 안

### 수고를 줄이려던 것이 수고를 늘리지 않게

임포트의 목적이 일일이 액션을 만드는 수고를 더는 것인데, 배지가 **액션마다 처리해야 할
목록**이 되면 목적을 배반한다. 그래서:

- **벌크가 기본, 개별이 예외.** 내 백업 복원·친구 세팅 통째로 받기에서 드는 값은 클릭 하나다.
- **병합/교체/덮어쓰기는 흔한 경우에 안 나온다.** 내가 이미 쓰던 키와 부딪힐 때만 나오고,
  그건 임포트가 만든 일이 아니라 드러낸 일이다 — 임포트가 없어도 해야 하는 결정이다.
- **부딪히는 것을 찾게 하지 말고 보여줄 것.** 49개 중 3개를 눈으로 찾게 하면 그때 배지가
  안전장치가 아니라 숙제가 된다. "배지 포함" 시험 모드가 그 답을 실물로 낸다(아래).

**그래도 그 클릭 한 번이 아깝다고 판명되면** 배지를 옵션으로 내리면 된다(붙여넣으면 바로
적용). 격리 기계는 그대로 두고 기본값만 뒤집는 것이라 되돌리기 쉽다. 반대 방향 — 격리 없이
만들었다가 나중에 넣기 — 은 어렵다.

### 커밋 시점에 정해지는 것

프로필에 넣을 때 자동으로 되는 것들. **물어보지 않는다.**

- **레이어 매핑은 기본값을 적용한다.** `DefaultDestinationLayerID`(`Workbench.lua`)가 이미
  그 답을 낸다 — 레이어 대 레이어, 남의 직업 것은 스코프만 지키고 특성은 버린다. 틀렸으면
  배지로 찾아 오버뷰에서 옮긴다.
- **MACRO는 삼중 일치일 때만 참조로 복구**, 아니면 스냅샷을 본문으로 MACROTEXT
  (앞 "전송 포맷 → MACRO").
- **키는 온 대로.** 부딪혀도 그대로 넣는다 — 한 키에 액션 여럿이 조건으로 갈리는 것이 이
  애드온의 정상 상태고, 격리 중이라 아무것도 안 건드린다.

### 커밋 시점에 **물어야** 하는 것 — 커스텀 상태 이름 충돌뿐

**격리가 못 막는 유일한 구멍이다.** 상태는 배치 소유가 아니라 전역 공유물이라, 이름이 같은데
정의가 다른 것을 조용히 덮어쓰면 **승인 전에 기존 액션의 동작이 바뀐다.** 배지를 안 뗐는데도
바뀐다.

이름마다 셋: **그대로 덮기 / 내 정의 유지 / 새 이름으로 받기**(배치 안의 참조를 재작성).
**내용까지 같으면 안 묻는다** — 자기 백업 재임포트가 확인창 세례를 받으면 안 된다.
자세한 것은 앞 "전송 포맷 → 커스텀 상태".

편집 기능이 아니라 안전장치라 "작업대는 오버뷰를 안 넘는다" 원칙 밖이다.

## 배지 = 격리. 바인딩에 안 들어간다 ★

**배지를 달고 있는 동안은 바인딩 빌드에 넣지 않는다.** 사용자가 배지를 제거해야(하나씩이든
벌크로든) 비로소 실제로 동작한다. 이 컨셉 전체가 이것 위에 서 있다 — 없으면 붙여넣는 순간
남의 키가 실제로 걸리고, 뭐가 달라졌는지도 모른 채 되돌릴 방법도 없다.

- 임포트 → 프로필에는 들어갔지만 **격리 상태.** 회색으로 보이고 아무것도 안 건드린다.
- 배지 제거 = **활성화.**
- 그래서 임포트가 내 바인딩을 바꾸는 순간이 임포트할 때가 아니라 **내가 승인할 때**가 된다.

막는 자리는 `BuildKeyMap`(`Debind.lua`)의 `if (action.key)` **바깥**이다. 빌드 시점이라
핫패스가 아니다.

⚠ **여기서 이 문서가 틀렸었다(08-14에 코드로 확인).** "`IsInactiveAction`이 알아서 회색으로
그려주니 공짜"라고 적혀 있었는데, `ActiveActions[action]`은 **이슈가 있어 `KeyMap`에서 빠진
액션에도** 붙는다 — 그 필드의 뜻은 "빌드에 들어감"이 아니라 **"키가 있음"**이다. 그래서 격리를
안쪽(`KeyMap`에 넣는 자리)에 걸면 회색이 안 된다. 바깥에 걸어야 키 없는 액션과 같은 대접이
되고, 그때 비로소 공짜다.

### 배지는 어디에 그리나

**액션이 그려지는 모든 자리.** 임포트된 액션은 어느 화면에서도 뭉쳐 있지 않다 — 이름순인
곳(오버뷰, 오른쪽 패널)에서는 알파벳 자리대로 흩어지고, 키로 모으는 곳(상세 패널 단축키 탭,
`CollectActionsForKey`)에서는 이미 그 키에 있던 액션들 사이에 끼어든다. 그래서 특정 뷰의
보조가 아니라 어디서든 알아볼 수 있어야 한다.

- ~~자리는 이름 색이 아니다~~ → **이름 색과 아이콘 위 점, 둘 다 쓴다**(08-14 구현).
  회색이 두 뜻을 갖는 것이 실제 문제였다 — 격리된 액션은 어차피 회색이 되는데 "키 없음"과
  구별이 안 됐다. 밝은 파랑(`BRIGHTBLUE_FONT_COLOR`)이 그 자리를 가져가서 "안 나간다"와 "왜"를
  한 색이 같이 말하고, 같은 파랑의 점(`NewDot`)이 아이콘 위 모서리를 걸친다.
  **뜻이 하나다 — 색을 갈아 두 번째 뜻을 얹지 말 것.**
- 배치 번호를 들고 있으니 툴팁이 출처와 받은 날짜를 말할 수 있다. 배치가 서랍에서 사라져도
  출처 없는 표시로 남을 뿐 깨지는 것이 없다.
- 편집했다고 자동으로 떼지 않는다. "내가 넣은 거였나" 추적이 끊긴다.

#### 승인 전에 시험하기 — 그려서 보여주는 게 아니라 **직접 눌러본다**

격리 중에는 빌드에 안 들어가므로 승인 전에는 아무 일도 안 일어난다. 그래서 시험할 길이
필요한데, 이건 그림(시뮬레이션)이 아니라 **실제로 걸어놓고 눌러보는 것**이다.

**새 기계가 필요 없다.** `UpdateBindings`가 현재 상태 값을 읽어서 필터링하면 된다. 모드 셋:

- **배지 제외** — 지금 실제 상태
- **배지 포함** — 승인하면 어떻게 되는지. **부딪히는 것이 여기서 빨갛게 뜬다**(가림 판정이
  현재 프로필 빌드에 붙어 있어서, 넣어봐야 답이 나온다)
- **배지만** — 받아온 것만 따로. "이 사람 세팅이 원래 어떻게 생겼나"

바인딩은 **평소대로 실제로 올라간다.** `SetOverrideBinding`을 막을 일도, `UpdateBindings`를
계산 전용으로 가를 일도 없다. 필터만 바뀐다.

챙길 것: **지금 그 모드에 들어와 있다는 것이 계속 보여야 한다.** 안 그러면 켜둔 채로
로그아웃하고 나중에 "왜 내 바인딩이 이상하지"가 된다. 모드 상태는 저장하지 말고 리로드하면
평소로 돌아오게.

  정한다. 쓸어내는 것이 아니라 **묻는** 것이어야 하고, 그러면 핀은 그 물음에 "얘는 빼고"로
  답하는 방식이 되지 상시 컨트롤이 아닐 수도 있다.

### 자동 백업 — 서랍의 한 줄로 (추가 UI 없음)

**격리가 안 지켜주는 자리가 하나 있다.** 배지는 *남의 것이 발동하는 것*을 막지만,
병합·교체·덮어쓰기는 **내 기존 액션의 키를 바꾼다.** 덮어쓰기는 내 그룹의 키를 떼고 교체는
맞바꾼다. 격리와 무관하게 실제로 달라지고, 그 자체로는 되돌릴 방법이 없다.

→ **가져오기를 시작할 때, 손댈 레이어들을 익스포트해서 그 문자열을 서랍에 한 줄로 넣는다.**
`[자동백업]` 라벨을 달고.

**이게 좋은 이유는 새로 만들 것이 없다는 것이다.** 백업은 그냥 또 하나의 배치이고, 복원은
그 줄에서 [가져오기 시작]을 누르는 것이다 — 이미 있는 길이다. 되돌리기 화면도, 스냅샷
포맷도, 복원 코드도 필요 없다.

- **시점은 커밋 한 번.** 조작마다 뜨면 서랍이 백업으로 불어나고 어느 것으로 돌아갈지도 못 고른다.
  "이 가져오기를 시작하기 직전"이 사람이 가리킬 수 있는 유일한 지점이다.
- 뜨는 범위는 **그 배치가 닿는 레이어들**. 기본 매핑이 목적지를 이미 알고 있으므로 계산할 것이
  없다. 전 프로필을 뜨지 않는 이유는 크기만이 아니라, 되돌렸을 때 무관한 레이어까지 시간을
  거스르면 그게 새 사고가 되기 때문이다.
- 자동백업 줄은 **자동 삭제에서 빠져 있어야 한다.** 한 달 뒤에 조용히 만료되는 백업은 백업이
  아니다. (한때 "핀이 기본"이라고 적혀 있었다. 핀은 2026-08-15에 빠졌으므로 **지금 조건은 그냥
  참이고**, 자동 삭제를 다시 지을 때 이 줄이 그 안이 답해야 할 것 하나가 된다.)

**⚠ 이건 undo가 아니다. 그렇게 부르지 말 것.** 임포트는 언제나 append라
(`Profile.lua`의 `AddAction` — 액션에 고유 키가 없다) 백업을 다시 넣으면 **덮어쓰는 게 아니라
하나가 더 생긴다.** 실제 복구 절차는 "망가진 것을 지우고 백업을 다시 넣는다"이고, 그건
배지 필터 + 벌크 삭제로 된다. 라벨이 `[자동백업]`인 이유가 그것이다 — `[되돌리기]`라고 적으면
누르면 원래대로 될 것처럼 읽힌다.

진짜 undo를 원하면 임포트에 "교체" 모드가 필요하고, 그건 앞 "안 정한 것" 2번이다. 그때 이
백업 줄이 그 기능의 첫 사용처가 된다.


## 이미 되어 있는 것

- **키 없는 액션은 바인딩까지 못 간다.** `key == nil`이면 `seq`도 안 받는다
  (`Profile.lua`의 `PlaceLast`, `KEYS_TO_SAVE` 정리 구간). 새로 막을 것이 없다.
- **오버뷰가 그걸 숨기지 않고 회색으로 보여준다**(`ColoredNameAndIconForAction`).
  "보이되 도달 안 함"이 공짜다.
- 키 없는 액션을 모으는 자리도 있다 — `CollectActionsForKey(nil, ...)`.

## 배지 행이 순서에서 빠졌다 (2026-08-14, 워킹트리)

**순서는 나가는 것들 사이에서만 뜻이 있다.** 배지 달린 행이 순서 계산에 끼어 있어서 셋이 틀렸다:
↓를 누르면 자리가 바뀌는데 그 키가 하는 일은 그대로였고(누른 사람은 뭔가 정했다고 믿는다),
`seq`는 실제로 쓰였고, 사유 칸이 겨루지도 않는 행을 상대로 계산됐다. 뿌리가 하나라 한꺼번에 뺐다 —
`BuildKeyMap`이 배지를 빌드에서 빼니 **순서에도 없는 게 같은 규칙이다.**

- 행 레코드에 `imported`를 실었다(`CollectActionsForKey`). `Ordering.lua`가 `.action`으로 되짚지
  않는 규칙을 지키려고 필드로 넘긴다.
- `ComputeOrderSwap`이 배지 이웃을 건너뛴다. 사유 칸도 같은 상대를 본다. `#rows < 2` 가드는
  **살아있는 행** 기준으로 바뀌었다.
- 배지 행에는 화살표 대신 **[받기] 버튼**이 선다. **선택 여부와 무관하게 모든 배지 행에** — 버튼이
  있다는 것 자체가 "아직 안 받았다"는 말이라, 그걸 다시 말하는 라벨은 안 넣었다. 우클릭 메뉴도 같은
  교체(순서 항목 둘 대신 받기/거절).
- 툴팁 제목이 목록 색을 안 따라간다. 색은 **훑는 눈**을 위한 것인데 툴팁은 한 개고 이미 읽기로 한
  것이라 정렬해줄 게 없고, 파란 제목은 이 게임에서 **아이템 등급**으로 읽힌다. 대신 키 줄 밑에 한
  줄이 말로 한다.

**낱말은 accept / reject.** keep/discard와 섞지 않는다. **keep을 안 쓰는 이유는 "이미 동작 중"이라고
말하기 때문이다** — 격리가 세우려는 사실을 버튼이 정면으로 뒤집는다. 한국어는 받기/버리기가 그 자체로
짝이라 그대로 둔다. 근거는 `REJECT_ALL_IMPORT` 위 주석에.

## ★ 레이어는 번역 대상이 아니다 — `DefaultDestinationLayerID`를 지운다 (2026-08-14, **만들었다**)

**앞의 여러 절을 무효로 만든다.** 아래 "레이어 매핑 — 레이어 대 레이어"와 그때의 `Workbench.lua`
매핑 코드는 이 절이 이깁니다.

### 무엇이 잘못됐나

`DefaultDestinationLayerID(descriptor)`는 "보낸 쪽의 이 레이어가 **여기서는 몇 번 레이어냐**"를
답한다. 반환값이 `layerID`이고, 그건 `LayerArray`의 색인이며, **`LayerArray`에는 지금 캐릭터의
레이어만 들어 있다.** 그러니 이 함수는 구조적으로 "내 프로필 안의 어딘가"밖에 답할 수 없고,
남의 좌표를 내 번호 공간에 **밀어 넣어야** 한다. 그래서 몸통이 전부 추측이다:

- 다른 직업의 `class` 레이어 → 내 직업 레이어 (마법사 세트가 "내 드루이드 전부" 자리에 앉는다)
- `character` + 특성 → 직업을 안 보고 특성 번호를 그대로 꽂는다 (마법사 특성 2 → 드루이드 특성 2)
- 없는 특성 → 한 단계 넓은 레이어로 폴백

각 줄에 그럴듯한 주석이 붙어 있지만 **전부 없어도 되는 문제를 푸는 중이었다.**

### 왜 없어도 되나

**두 프로필이 같은 좌표계를 쓴다.** 구조가 같다 — 일반 / 직업×특성 / 캐릭터×특성. 다른 것은 *어느
직업이냐*뿐이고 그건 좌표의 **값**이지 좌표계가 아니다. 마법사의 직업·특성2 레이어는 어느
계정에서든 마법사의 직업·특성2다. **옮길 게 없다.**

그리고 저장은 원래부터 스코프 주소로 되어 있다:

```
db.shared.GENERAL
db.shared.classes[직업]        ← 직업 이름이 열쇠다
db.characters[guid].layers
```

`LayerArray`는 **지금 캐릭터가 보는 뷰**일 뿐이다. 임포트가 뷰를 통해서만 프로필에 쓸 수 있었던
것이 문제의 뿌리다.

### 어디로 가나

| 보낸 쪽 | 받는 쪽 |
|---|---|
| `general` | `shared.GENERAL` — 그대로 |
| `class / MAGE / spec N` | `shared.classes.MAGE`의 spec N — **그대로. 내 직업으로 바꾸지 않는다** |
| `character / spec N` | 이 캐릭터의 spec N |

**진짜 번역이 필요한 건 캐릭터 하나뿐이다.** "그 사람의 캐릭터"는 여기서 뜻이 없으니까. 나머지는
문자 그대로 옮겨진다. 폴백도, 특성 버리기도, 직업 바꿔치기도 전부 사라진다.

### 받아들인 대가 — 지금 캐릭터가 못 보는 것이 생긴다

마법사 문자열을 드루이드가 가져오면 그 내용은 `shared.classes.MAGE`에 앉고, **드루이드 세션에서는
그 레이어가 `LayerArray`에 없어서 화면에 안 뜬다.** 배지도 안 보이고 받거나 거절할 수도 없다.

**그래도 이쪽이 맞다.** 대안 둘이 다 성립하지 않기 때문이다:

- **내 직업 레이어에 넣는다** — 보이긴 하는데 마법사 주문이 "내 드루이드 전부" 자리에 앉는다.
  그리고 읽는 사람이 **판단할 수가 없다**: 자기가 못 배우는 주문이라 전부 빨갛고, 그 세트가 쓸
  만한지 알 방법이 없다. 답할 수 없는 질문을 물은 셈이 된다
- **안 가져온다** — 한때 이걸로 갔다. 서랍이 안 지워지니 그 직업으로 접속해 다시 가져오면 된다는
  근거였는데, 제대로 된 자리에 두는 길이 있으면 굳이 버릴 이유가 없다

**즉 "다른 캐릭터로 접속했을 때 resolve한다"가 설계다.** 격리가 그걸 안전하게 만든다 — 안 보이는
동안에도 아무 키에도 안 걸린다.

### 딸려 오는 것 (전부 `LayerArray`만 보는 코드들)

- **`NextImportGroupID`** — `LayerArray`를 훑어 최대 번호를 찾는다. `classes.MAGE`의 번호를 못 보니
  드루이드로 또 임포트하면 **살아 있는 번호를 재사용한다.** 마법사로 접속하면 `키를 모름 #3`이
  둘이 되고 그룹 단위 조작이 둘 다 쓸어간다. 프로필 전체 유일 번호로 바꾼 이유가 정확히 이거였다.
  → `DebindVars` 전체를 훑어야 한다
- **`PlaceImportedActions`** — `{ layerID, action }`을 받는다. 로드되지 않은 레이어에는 layerID가
  없다. **주소가 `(scope, class, spec)`가 되어야 한다**
- **`CollectImportedActions`** — 역시 `LayerArray`만 본다. [N개 모두 받기]가 안 보이는 것을 안 세고
  안 건드린다. **그건 맞다**(판단할 수 없는 것을 받으면 안 된다). 다만 스트립이 사라진 뒤에도 계정
  어딘가에 배지가 남는다는 뜻이라, 그걸 어디서 말할지는 안 정했다
- `FindLayerID`, `CollectSourceLayers`의 매핑 부분도 같이 정리 대상

### 먼저 쓸 테스트

이 세션에서 썼다가 **포맷이 아직 그 모양이 아니라 빨간 채로 남아서 되돌린 것**이 하나 있다:

> `한 키가 레이어 여럿에 걸쳐도 그룹 하나로 들어온다` — 한 그룹의 액션들이 서로 다른 `layer`
> descriptor를 들고 있을 때, 같은 `importGroup`을 받고 **서로 다른 자리에** 놓이는지.

이게 다음 세션의 첫 실패여야 한다.

### 실제로 한 것 (2026-08-14)

**첫 실패는 그 테스트였고, 그것을 초록으로 만들려면 전송 포맷이 같이 움직여야 했다.** 그때
포맷은 그룹이 `(레이어, 키)`라 익스포트가 레이어를 절대 안 넘겼다 — 위 테스트가 넣는 페이로드를
만들 수 있는 곳이 없었다. 그래서 **익스포트까지 바꿨다(소유자 결정).**

#### 포맷 — `layer`가 그룹에서 액션으로 내려갔다

```lua
groups = {
  { id = 11, key = "F", actions = {
      { type = "spell", value = 8921, order = 1, layer = { scope="class", class="DRUID", spec=0 } },
      { type = "spell", value = 774,  order = 2, layer = { scope="general" } },
  } },
}
```

- **그룹은 이제 키 하나다.** 레이어를 넘는다. `키 = nil`인 액션은 여전히 혼자 그룹이고 `id`가 없다.
- **그룹 안 차례는 (레이어 순위, `seq`)다.** 레이어 순위는 발동 순서 그대로 — 캐릭터/특성 →
  캐릭터/공용 → 직업/특성 → 직업/공용 → 일반. 나머지 축(중요도·hover·조건)은 액션에 실려 가므로
  받는 쪽이 스스로 다시 계산할 수 있고, `order`가 나를 것은 **안 실려 가는 것뿐**이다.
  `sort`가 안정 정렬이 아니라 훑은 차례를 마지막 tiebreak으로 둔다(같은 순위 레이어가 둘 있다).
- **`v`는 1 그대로다.** 필드가 뜻을 바꿨으니 원칙대로면 올려야 하지만, **v1 문자열이 이 repo 밖으로
  나간 적이 없다**(공유는 3.1.6에 안 실렸다). 읽을 사람이 없는 모양에 번호를 태우지 않는다.
  다음번 같은 변화는 올린다. 근거는 `SCHEMA_VERSION` 주석에.

**왜 이게 그냥 테스트 하나가 아니었나:** 키를 빼고 보낸 문자열에서 한 키가 둘로 갈려 도착하면,
읽는 사람은 머리글 둘을 보고 **키 둘**을 준다. 그러면 둘 다 발동한다. 이 문서가 "조용히 틀린다"고
적어둔 바로 그 경우이고, 도착한 뒤에는 문자열에 그걸 바로잡을 근거가 하나도 안 남는다.

#### 자리 — `(scope, class, spec)`

- `DebindStorage.ImportAddress(descriptor)` → `scope, class, spec` 또는 nil. `DefaultDestinationLayerID`와
  그 밑의 `FindLayerID`는 지웠다.
- `PlaceImportedActions(placements)`의 원소가 `{ scope, class, spec, action }`이 됐다.
  `Profile.lua`의 `StoredActionsAt`이 저장 테이블을 직접 짚는다(없으면 만든다).
  **넣는 규칙은 안 갈랐다** — 로드 안 된 레이어에는 씌울 레이어 객체가 없어서 `ProfileLayerProto`를
  저장 테이블에 씌운 스크래치 하나를 돌려 쓰고, `Insert`/`PlaceLast`는 그대로 쓴다.
- **캐릭터 자리는 `db.char`에서 받는다.** `characters[guid]`는 아직 안 붙어 있을 수 있고
  (`InitDB`의 지연 생성), 그때 거기 쓰면 `CleanUpDB`가 나중에 붙일 그 테이블이 아니다.

#### 자리가 없는 하나 — 이 캐릭터에 없는 특성

| 보낸 쪽 | 받는 쪽 |
|---|---|
| `class / MAGE / spec 4` | `classes.MAGE[4]`. 이 계정이 마법사를 해본 적 없어도 만들어 넣는다 |
| `class / NOSUCHCLASS` | **자리 없음.** 직업 이름은 저장의 열쇠라 아무 문자열이나 받으면 **어느 화면도 못 닿고 `CleanUpDB`도 못 치우는** 테이블이 붙여넣을 때마다 하나씩 는다(그쪽은 로드된 열한 레이어만 훑는다). `C_CreatureInfo.GetClassInfo`로 만든 명단에 있는 것만 받는다 |
| `character / spec 4` (3특성 직업이 받음) | **자리 없음. 세어서 뺀다** |

앞 절이 "폴백은 사라진다"고 했으므로 예전의 *캐릭터 공용으로 떨어뜨리기*는 안 한다. 그렇다고
`layers[4]`에 그냥 쓸 수도 없다 — 캐릭터는 직업이 안 바뀌니 **영원히 아무도 안 읽고 아무도 안
치우는** 테이블이 된다(`CleanUpDB`는 `LayerArray`만 훑고, `HasCharContent`는 그걸 내용으로 세어서
엔트리를 계속 살려둔다). 직업 쪽은 다르다 — 그 좌표는 언젠가 그 직업으로 접속하면 열린다.

#### `skipped`의 뜻이 바뀌었다 — 그룹 수 → 액션 수

주소가 액션마다라 세는 단위도 액션이다.

**"안 고른 줄"은 skip이 아니다.** 둘 다 안 들어오지만 하나는 읽는 사람이 준 답이고 하나는 이 버전이
놓을 데가 없는 것이다. 안 고른 것까지 세면 자기가 뺀 줄을 두고 "놓을 자리가 없었다"고 말하게 된다.

**단, 줄이 아예 없는 것은 "안 고른" 것이 아니다.** 모르는 scope는 애초에 체크박스로 물은 적이 없으니
필터에서 조용히 빠지면 안 된다 — 그리고 창은 언제나 필터를 켜고 부르므로, 여기서 새면 그 수는
**테스트에서만 맞는다.** 처음에 그렇게 짰다가 리뷰에서 잡혔다.

**`IMPORT_COMMITTED_SKIPPED`도 같이 고쳤다.** "이 버전이 모르는 레이어에서 와서"였는데, 실제로
자주 닿는 쪽은 **이 캐릭터에 없는 전문화**다. 둘 다 적는다.

#### 딸려 온 것들

- **`NextImportGroupID`가 저장 전체를 훑는다**(`ForEachStoredActionList`). `LayerArray`만 보면 안
  보이는 레이어의 살아 있는 번호를 재사용한다 — 이 절이 그 레이어에 진짜로 쓰기 시작했으니 이제
  실제로 일어난다. 같은 테이블은 한 번만 세고(붙은 캐릭터 엔트리가 양쪽에서 잡힌다), 아직 안 붙은
  `db.char`도 따로 넣는다.
- **`CollectImportedActions`는 `LayerArray`에 그대로 둔다.** 앞 절의 판단대로다 — 판단할 수 없는
  것을 [N개 모두 받기]가 받으면 안 된다. **대가는 그대로 남아 있다**: 스트립이 사라진 뒤에도
  계정 어딘가에 배지가 남는다. 어디서 말할지는 여전히 안 정했다.
- `LayerKey` / `CollectSourceLayers`는 지웠다. 대신 `ImportLineFor` / `CollectImportLines`가
  들어왔다 — bring 모달이 물을 네 줄(아래 절)이고, 값에서 문자열을 만드는 이유는 `LayerKey`와
  같다(역직렬화가 액션마다 다른 테이블을 줘도 된다).
- `BuildAction`의 블랙리스트에 `layer`를 넣었다. 블랙리스트라 안 넣으면 그대로 프로필에 꽂히는데,
  그건 **보내는 쪽이 액션들 사이에 공유하는 테이블 하나**라 여러 액션이 한 테이블을 물게 된다.

~~핀(`pinned`)은 배치의 속성이라 체크박스가 맞다.~~ 이건 아니다. (핀은 2026-08-15에 빠졌다 —

### 모양

[가져오기]를 누르면 모달이 뜬다. **결정이 press와 같은 순간에 일어나니 모드가 사라진다.**

```
가져오기 — <배치 이름>

[x] 공유 / 일반
[x] 공유 / <직업명>
[x] 캐릭터 / 일반
[x] 캐릭터 / <직업명>
```

`GetLayerLabel(layerID)` / `GetSideTabaLabel`을 그냥 부르면 안 된다. **전부 지금 캐릭터 기준으로
짓는다:**

```lua
scope = tab == 2 and UnitName("player") or LLL["SHARED_BINDINGS"]   -- 내 캐릭터 이름
GetSideTabaLabel: UnitClass("player")                                -- 내 직업
                  C_SpecializationInfo.GetSpecializationInfo(i)      -- 내 특성
```

그러니 다른 직업 문자열이면 **마법사 레이어에 "드루이드"라고 적힌다.** 같은 직업이어도 캐릭터
탭에는 **내** 캐릭터 이름이 붙는데 그건 보낸 사람이 아니다.

모달은 descriptor를 읽는 **자기 이름 짓기**가 필요하다:

- 직업 이름 — `payload.class`에서. 서랍이 이미 `batch.class`를 들고 있고 `IMPORT_BATCH_FROM_CLASS`도
  있다
- 특성 이름 — `GetSpecializationInfoForClassID(classID, index)`. `GetSpecializationInfo(i)`는 플레이어
  상대라 못 쓴다
- **캐릭터 이름은 문자열에 없다.** 일부러 안 싣는다(공개 채널에 붙일 것이 캐릭터 이름을 나르면
  안 된다). 그래서 캐릭터 줄은 이름 없이 "캐릭터 / …"로만 부를 수 있다 — 창의 어휘를 그대로 못
  쓰는 유일한 자리다

| | | |
|---|---|---|
| 행에 체크박스 (지금 것) | **기각** | 위 |

### 실제로 한 것 (2026-08-14)

`DebindStorageBringFrame`(`WorkbenchUI.xml` / `.lua`). 행의 [가져오기]가 이걸 연다.

- **줄은 실제로 놓일 수 있는 것만 선다**(`CollectImportLines`). 없는 레이어와 **갈 데가 없는
  레이어**는 읽는 사람에게 같은 것이다 — 켜도 꺼도 아무 일이 없는 체크박스이고, 둘을 구별할
  방법이 없다. 그래서 줄이 하나도 없으면 대화상자를 안 열고 `IMPORT_NOTHING_PLACED`로 답한다.
  넷 다 **기본 켜짐** — 다 가져오는 것이 온 목적이고, 덜 가져오려는 사람을 위한 상자다.
  넷을 켜게 만들면 대화상자가 통행료가 된다.
- **줄 이름은 문자열 안의 것을 부른다**(`IMPORT_BRING_LINE_*`). 목적지가 아니다. 캐릭터 줄은 이름
  없이 "캐릭터 / …"다 — 문자열이 캐릭터 이름을 안 나른다. 기존
  `GetLayerLabel`/`GetSideTabaLabel`은 전부 **지금 캐릭터**로 짓기 때문에 못 쓴다(위).
  - **직업 줄의 이름은 `payload.class`가 아니라 descriptor에서 온다.** 우리가 만드는 문자열에서는
    둘이 같지만 손으로 만든 것은 갈릴 수 있고, 그러면 **남의 레이어 위에 보낸 사람 직업**이 적힌다.
    한 줄에 직업이 둘이면 고를 이름이 없으니 `payload.class`로 물러선다. 특성 줄은 descriptor에
    직업이 없어서 원래 `payload.class`다.
- **체크박스는 배치에 아무것도 안 남긴다.** `batch.stripKeys`를 지웠고, 접힌 작업대가 남겨둔 빈
  테이블 넷(`layers`/`keys`/`excluded`/`states`)도 같이 지웠다. **옛 배치에 남은 값은 안 지운다** —
  읽는 데가 없으니 store 버전을 올려 마이그레이션할 값이 아니다.
- `CommitBatch(batch, options)`로 바뀌었다. options는 대화상자에서 온다.
- **구분선은 뺐다**(모형의 `---`). `Options_HorizontalDivider`를 Lua로 배치하려다 두 번 어긋났고,
  가를 것이 둘뿐이고 아래쪽이 마지막 한 줄이라 **간격이면 된다.** 되살릴 근거: 아래쪽이 여러 줄로
  늘어나면 간격만으로는 두 덩어리가 안 갈린다.
- **ESC는 `UISpecialFrames`에 안 넣는다.** `CloseSpecialWindows`가 목록에 있는 **떠 있는 프레임을
  전부** 닫아서, 한 번 누르면 뒤의 창까지 같이 닫힌다. `OnKeyDown`에서 ESCAPE만 잡고 나머지는
  `SetPropagateKeyboardInput(true)`로 흘려보낸다. (붙여넣기 창은 아직 목록 쪽이다.)

**딸려서 고친 것 둘 (안 고쳤으면 조용히 틀렸다):**

- **하나도 안 고르고 누르면** placements가 0이라 `NOTHING_TO_PLACE`가 나오는데, 그 사유에 문자열이
  없어서 "손상된 문자열입니다"가 떴다. 버튼을 **끄고**(`UpdateAcceptButton`), 사유에는
  `IMPORT_NOTHING_PLACED`를 달았다.
- **`IMPORT_COMMIT_DESC`가 거짓이 됐다.** "지정에 넣습니다"였는데 이제 먼저 묻는다. 같은 편집에서
  고쳤다.

## 키 빼고 가져오기 (2026-08-14, 만들었다)

드로어 행의 [가져오기] 옆 체크박스. **격리가 하는 약속과 다른 약속이다** — 격리는 "받아들이기
전까지 안 바뀐다"이고 이건 "받아들인 뒤에도 네 키는 안 건드린다"다. 남의 액션은 갖고 싶고 남의 키
배치는 싫은 경우가 흔한데, 지금까지는 **보내는 사람에게 체크를 부탁해야** 얻을 수 있었다.

`key`만 빠진다. `importGroup`과 `importOrder`는 그대로 — 키를 빼면서 묶음을 지키는 것이 요점이다.

**라벨은 `EXPORT_STRIP_KEYS`를 그대로 쓴다.** 양 끝에서 같은 한 가지를 말하니 재활용의 규칙이
맞는다. 설명은 따로(`IMPORT_STRIP_KEYS_DESC`) — 저쪽은 "보냅니다"로 시작해서 이쪽에 안 맞는다.

### `hasKeys`는 세 값이다 (nil / false / true)

붙여넣는 시점에 배치에 적는다(`groupCount`와 같은 자리, 같은 이유 — 행 하나 그리려고 문자열을 풀
수는 없다).

**`or nil`로 접지 말 것.** 서랍이 가려야 하는 상태가 셋이다:

| | | |
|---|---|---|
| `true` | 키가 있다 | 체크박스를 보여준다 |
| `false` | 키 없이 왔다 | **숨긴다** — 켤 게 없고, 있으면 "키가 아직 들어 있다"로 읽힌다 |
| `nil` | 이 필드가 생기기 전에 저장된 배치 | **보여준다** |

세 번째가 실제로 물렸다. 처음엔 `hasKeys == true`로 걸어서 **서랍에 이미 있던 모든 행에서 기능이
안 만들어진 것처럼 보였다.** 없는 필드를 근거로 컨트롤을 끈 것이다. 키 없는 배치에 체크박스가 하나
서는 값은 0이지만(`stripKeys`가 뺄 키가 없다), 키 있는 배치에서 숨는 값은 기능 전체다.

`false`를 nil로 접으면 두 번째와 세 번째가 구별되지 않는다.

## 묶인 적 없는 액션에는 그룹을 주지 않는다 (2026-08-14)

**받는 사람에게 없는 숙제를 만들지 않기 위한 규칙이다.**

내보내는 사람은 레이어를 통째로 내보내므로, **자기가 만들어놓고 키를 안 준 액션**도 같이 나간다.
그것에 그룹 번호를 붙이면 받는 쪽 화면에서 `키를 모름 #N`으로 서는데, 그 머리글이 하는 말은
"이건 설계의 일부였고 키만 안 왔다, 어떤 키를 줄지 정해라"다. **아니었다.** 읽는 사람은 보낸
사람도 안 쓰는 것을 놓고 "이게 뭐지, 나도 써야 하나"를 따지게 된다.

그래서:

- **`id`는 키에 같이 걸려 있던 그룹에만 붙인다**(`Export.lua`). `id`의 뜻이 "이것들은 한 묶음이다"인데,
  묶인 적 없는 액션은 아무와도 같은 키 그룹이 아니다 — 형식이 그룹의 목록이라 혼자 그룹이 됐을 뿐이다.
- **`id`가 없으면 `importGroup`도 없다**(`PlanImport`). 여기서 번호를 발급하면 위의 일이 그대로
  일어난다.
- 그러면 그것들은 왼쪽 열의 **`NOT_BOUND` 덩어리**로 간다. 임포트라는 사실은 **배지와 색**이
  이미 말하고 있으므로 머리글까지 나설 일이 아니다.

**보내는 쪽만 알 수 있다.** 키를 빼고 내보내면 *액션 하나짜리 키*와 *키가 없던 액션*이 선 위에서
같은 테이블이 된다. 받는 쪽에 판단 근거가 없다.

### 멤버 하나짜리 머리글이 잔뜩 생기는 것 — 보류 (2026-08-14, 확인함)

액션 하나짜리 키가 많은 프로필을 키 빼고 내보내면 `키를 모름 #N` 머리글이 잔뜩 선다. **실제로
그렇게 되는 것을 화면에서 확인했다.** 규칙상으로는 맞다 — 그것들은 진짜로 키에 걸려 있었다.

**지금 안 고친다.** 위 규칙을 방금 세웠는데 눈에 보이는 소음 때문에 바로 흔들면, 다음 세션이 어느
쪽이 결론인지 모른다. **기능이 다 선 뒤 다듬기 세션에서 본다** — 그때는 "머리글을 언제 세우나"를
한 번에 정할 수 있고, 그룹째 키 주기가 들어와 있으면 머리글의 값도 그때 제대로 재진다.

되살릴 때의 근거: 멤버가 하나인 그룹은 "이것들이 한 묶음"이라고 말할 것이 없으니, 그때는 앞서 기각한
"멤버 하나면 합치기"가 다시 후보가 된다 — 그 기각 사유("한 묶음에 속한다는 사실이 지워진다")가
멤버가 하나일 때는 성립하지 않는다.

**뒤집어 말하면, 키를 빼든 안 빼든 "원래 묶여 있었나"는 반드시 실려야 한다.** 조건으로 갈리는 한
키의 액션들이 한 묶음이라는 것이 설계의 핵심이고, 키가 빠진 문자열에서는 그게 유일한 잔존물이다.

**[가져온 것만] 필터와의 관계.** 배지는 달렸는데 그룹이 없는 액션이 `NOT_BOUND` 덩어리에 살게
되므로, 필터를 켤 때 그 덩어리를 통째로 빼면 안 된다. 대신 **행 단위로 좁힌다** — 키 그룹을 통째로
남기는 이유(각 행의 사유가 아래 행을 가리킨다)가 여기엔 없어서, 그렇게 해도 깨질 문장이 없다.

## 키 없는 것들을 왼쪽 열 맨 아래에 (제안, 2026-08-14)

**지금 나 있는 구멍.** `BuildKeyboardElements`는 `if (key and not keySeen[key])`로 그룹을 세우므로
**키 없는 액션은 왼쪽 열에 아예 안 들어간다.** 임포트 전부터 그랬고 `OVERVIEW_DESC`가 그렇게 적어놨다.
그 위에 임포트가 둘을 얹었다:

- `CollectImportedActions`는 키를 안 보므로 **[N개 모두 받기]의 N이 키 없는 것까지 센다.** [가져온
  것만]을 켜면 왼쪽이 N보다 적게 보이고, 배치가 통째로 키 없이 오면 **아무것도 안 보인다.**
- 그때 뜨는 `OVERVIEW_EMPTY_IMPORTED_ONLY`가 **거짓말이다** — "오른쪽의 다른 탭을 봐 주세요"인데
  다른 탭에도 없다. 없는 걸 찾으러 보낸다.
- **변두리 경우가 아니다.** `EXPORT_STRIP_KEYS`("키 빼고 내보내기")가 있으니, 남에게 세팅을
  공유하는 흔한 방식이 정확히 키 없는 배치다. 그리고 방금 만든 행의 [받기] 버튼은 왼쪽 열에만
  있어서 그 배치에는 하나도 안 뜬다.

**고치는 모양: 키 그룹이 다 끝난 뒤 맨 아래에 키 없는 것들.** 배지 달린 것은 도착 그룹대로 갈라
서고, 나머지는 `KEY_GROUP_UNBOUND` 한 덩어리. 앞의 1번과 2번이 따로가 아니라 **한 기능이다.**

**이 그룹은 반드시 보여야 한다.** 한 키에 조건으로 갈리는 액션 여럿이 이 애드온의 정상 상태라,
"이 셋이 한 키였고 우선순위까지 이렇게 잡혀 있었다"는 것은 부가 정보가 아니라 **보낸 사람이 만든
설계 그 자체**다. 키가 빠진 문자열에서는 그게 설계의 유일한 잔존물이고, 화면에서 지우면 읽는
사람이 평평한 목록에서 어느 것들이 한 묶음이었는지 추측해야 한다. 틀리면 조용히 틀린다 — 같이 있어야
할 둘이 다른 키로 갈리면 양쪽 다 발동한다.

- **머리글 글자는 `키를 모름 #N` / `Key unknown #N`.**
  - `지정 안 됨`(NOT_BOUND)과 뜻이 갈린다 — 저건 *안 준* 것, 이건 *못 받은* 것.
  - **"그룹"이라는 낱말은 못 쓴다.** `CONDITION_GROUP`이 파티/공격대를 가리키고
    `ORDER_FLAG_GROUPS_NONE_SELECTED`("그룹 선택 안 됨")가 **바로 이 왼쪽 열의 사유 칸**에 뜬다.
  - "이것들이 한 묶음"이라는 말은 안 넣는다. 머리글이 아래 줄들을 거느린다는 것은 이 열 전체가 이미
    가르치고 있으므로, 머리글은 **키 자리에 무엇이 대신 서 있는지**만 말하면 된다.
  - 괄호가 아니라 `#`인 이유: 이 창에서 `(3)`은 이미 개수다(탭 라벨).
- **번호는 프로필 전체에서 유일해야 하고, 가져올 때 매긴다.** 지금 `importGroup`은 payload의
  `group.id`라 **배치 안의 번호**다 — 배치 둘이 동시에 기다리면 1번이 둘이 된다. 가져오는 시점에
  프로필 전체의 `importGroup` **최대값 + 1**부터 새로 매긴다. 카운터를 따로 저장하지 않는 것은
  `GetNextSeq`와 같은 방식이고 같은 이유다("번호에 구멍이 나는 것은 괜찮다"). 하나도 안 남으면 다시
  1부터 — 옛 번호를 참조하는 곳이 없으니 재사용은 무해하다.
  - **그러면 `importGroup`의 뜻이 바뀐다.** `Profile.lua`의 주석이 "그 배치 안의 그룹"이라고 적고
    있으므로 **같은 편집에서 다시 쓴다.** 지금 이 필드를 읽는 곳은 없다(설정·승인 시 삭제뿐)이라
    바꿀 수 있는 것은 지금뿐이다.
- **그룹 이름을 따로 저장하지는 않는다.** `importGroup`은 승인하는 순간 `imported`와 같이 지워진다 —
  그룹은 배지가 붙어 있는 동안만 사는 물건이라, 저장한 이름은 자기가 가리키던 것보다 오래 산다.
  이름을 저장하면 "고칠 수 있나 / 중복 검사 / 승인 시 정리"가 줄줄이 따라오는데 그게 작업대를 접은
  이유다. 번호는 파생 라벨로 충분하다.
- **멤버가 하나뿐인 그룹도 `NOT_BOUND` 덩어리에 합치지 말 것.** 합치면 하필 **한 묶음에 속한다는
  사실**이 지워진다. 그게 여기서 지키려는 바로 그 정보다. (액션 하나짜리 키를 키 빼고 보내면
  실제로 그렇게 온다 — 아래 "멤버 하나짜리 머리글" 보류 항목.)

### 순서 — 선에 명시적으로 싣는다 (`order` → `importOrder`)

**그룹 안의 순서는 우선순위와 같은 급의 설계 정보다.** 지금은 배열 차례에만 실려 있고
(`Export.lua`: "groups and actions are emitted in `seq` order"), 암묵적이라 명시적으로 바꾼다.

- **선의 이름은 `order`** — 그룹 안 1..n. 보낼 때 `seq`로 정렬한 뒤 그 자리 번호를 적는다.
- **`seq`라는 이름으로는 절대 안 보낸다.** `BuildAction`이 **블랙리스트**라
  (`macro`/`setstate`만 거르고 나머지는 `pairs`로 통째 복사) 선에 `seq`가 실리면 아무도 안
  시켜도 액션에 꽂힌다. 그러면 Export 주석이 경고한 충돌이 자동으로 일어난다 — 보낸 쪽 번호가
  받는 레이어가 이미 나눠준 번호와 섞인다.
- **액션에는 `importOrder`로 들어간다.** `BuildAction`이 `macro`/`setstate`에 하는 처리와 같다:
  읽어서 쓰고 **선의 이름은 액션에 안 남긴다**. 남기면 `CleanUpDB`가 걷어낼 이름이 잠깐 액션에
  붙어 있게 된다("the action is briefly a shape nothing else expects").
- `KEYS_TO_SAVE`에 넣고, `imported`/`importGroup`과 **같이 승인 시 지운다.** 그룹이 사라지면
  순서도 뜻이 없다.

**`PlaceLast`는 안 건드린다.** "키가 없으면 번호도 없다"는 규칙에는 이유가 적혀 있고(`seq`의 뜻이
"이 키를 눌렀을 때 몇 번째로 나가는가"), 임포트 전용 필드를 쓰면 그 불변식을 깰 이유가 없다 —
`seq`는 끝까지 키가 있을 때만 존재하고, 잠깐 필요한 순서는 잠깐 사는 필드가 든다.

**그룹째 키를 줄 때**(위 1번) `importOrder` 차례대로 `seq`를 발급한다. 그때 배지와 함께 셋이 같이
사라진다. 한 액션씩 키를 주면 `SetActionKey`가 만진 차례대로 번호를 주므로 순서가 사라지는데,
그래서 **그룹째 주는 조작은 편의가 아니라 순서를 지키는 유일한 길이다.**

**`check:export-fields`에 칸 하나 열어야 한다.** 그 검사는 지금 한 방향만 본다 — "저장되는데 안
나가는 것". `order`는 반대다: **나가는데 저장 필드가 아니다**(보낼 때 계산한다). 예외 칸을
의도적으로 열어두면 다음 것도 조용히 안 샌다.
- **그룹은 레이어를 가로지른다 — 도착할 때부터.** (여기 한때 "도착할 때는 안 갈라진다"고 적혀
  있었다. 그때는 참이었다 — 그룹이 `(레이어, 키)`였고 `PlanImport`이 그룹마다 `layerID`를 한 번
  정했다. **2026-08-14에 그 전제가 없어졌다**: 그룹은 키 하나이고 자리는 액션마다다. 아래 ★ 절.)

  그리고 도착 이후에도 **바뀐다.** `MoveAction`이 액션을 다른 레이어로 옮기면서
  `imported`/`importGroup`을 안 지우므로, 읽는 사람이 한 줄만 옮겨도 갈래가 하나 더 는다.
  복사는 한술 더 떠서 **같은 그룹 번호를 든 액션을 하나 더** 만든다.

  그래서 **왼쪽 열이 그룹을 반만 보여주는 상태가 실재한다.** 그룹을 대상으로 삼는 조작은 화면이나
  살아있는 레이어가 아니라 **프로필 전체를 `importGroup`으로** 훑어야 한다.

  (한때 "그런 경우는 없다"고까지 적혀 있었다. `PlanImport`만 읽고 불변식이라고 단정한 것이다 —
  도착 이후의 경로를 안 따라갔다. 지금은 도착 시점부터 성립하지도 않는다.)
- **같은 편집에서 챙길 것 둘:** `OVERVIEW_DESC`가 정반대를 약속하고 있다("키가 없는 행동은 아예
  나오지 않습니다"). 그리고 **키 없는 그룹에는 순서 화살표가 없어야 한다** — 키가 없으면 겨룰 일이
  없다. 배지 행에 한 것과 같은 처리이고 사유 칸도 같이 빈다.
- 덤: `DebindKeyHeaderMixin:Init`의 nil-키 갈래(`KEY_GROUP_UNBOUND`)가 **드디어 실행된다.** 지금은
  그 헤더를 만드는 곳이 `BuildKeyboardElements` 하나뿐이고 거기서 nil 키를 안 만들어서, 한 번도 안
  돌아본 코드다.

### 고른 것과 버린 것 (2026-08-14 대화)

기각에 **이유를 적어두는 것이 요점이다.** 이유 없는 "기각"은 벽이라 다음 사람이 왜 막혔는지
모르는 채로 다시 제안하거나, 반대로 물어보지도 못한다. 이유가 적혀 있으면 둘 다 열린다 — 그
전제가 아직 서 있으면 다시 꺼내지 말라는 뜻이고, **전제가 무너졌으면 그게 다시 꺼낼 근거가
된다.** 아래 표에서 뒤집힌 것 셋(안 가르기, 멤버 하나 합치기, `PlaceLast` 넓히기)은 전부 이
세션 안에서 전제가 무너져 뒤집힌 것들이다.

**키 없는 것들을 어떻게 놓을까**

| | | |
|---|---|---|
| 아예 안 가르고 `NOT_BOUND` 한 덩어리 | **기각** | 처음엔 이걸 골랐다 — "그룹을 알아도 읽는 사람이 할 수 있는 일이 없다". 거꾸로였다: **그룹을 알아야 키를 준다.** 평평한 목록에서 한 묶음을 추측하게 되고, 틀리면 조용히 틀린다(같이 있어야 할 둘이 다른 키로 갈리면 양쪽 다 발동) |
| 머리글 없이 간격만 | **기각** | "붙어 있음"과 "한 덩어리임"이 구별 안 됨 |
| 머리글을 세워 가른다 | **채택** | |
| 멤버가 하나면 `NOT_BOUND`에 합치기 | **기각** | 내가 제안했다가 뒤집었다. 그룹이 레이어에 흩어져 하나만 보일 때 합치면 하필 **한 묶음에 속한다는 사실**이 지워진다 |

**머리글 글자**

| | | |
|---|---|---|
| `키를 모름 #N` / `Key unknown #N` | **채택** | `NOT_BOUND`("지정 안 됨")와 뜻이 갈린다 — 저건 *안 준* 것, 이건 *못 받은* 것. 짧아서 키 이름 자리에 앉고, 그룹째 키를 주면 진짜 키 이름으로 바뀌는 게 자연스럽다 |
| `가져온 키그룹 #1` | **기각** | **"그룹"이 이 창에서 이미 파티/공격대다**(`CONDITION_GROUP`). `ORDER_FLAG_GROUPS_NONE_SELECTED`가 **바로 이 왼쪽 열**에 뜬다. `#N`은 이 안에서 채택 |
| `같은 키였던 것들` / `Shared one key` | **기각** | 사실은 맞는데 과거를 적는다. 키 그룹인데 키만 없는 것으로 읽히는 편이 낫다 |
| `보낸 쪽에선 한 키` / `One key where it came from` | **기각** | 정확하지만 문장이다. 머리글이 행보다 세게 읽히면 안 된다는 이 열의 규칙에 걸린다 |
| `%d개가 한 키에 있었음` | **기각** | 개수는 아래 줄을 세면 나온다. 머리글이 보이는 것을 말하는 셈 |
| 괄호 번호 `(2)` | **기각** | 이 창에서 `(3)`은 이미 **개수**다(탭 라벨). `#2`는 인덱스로 읽힌다 |
| 번호 없이 같은 머리글 반복 | **기각** | 배치 둘이 동시에 기다리면 구별할 길이 없다 |

**그룹 번호를 어디서 얻나**

| | | |
|---|---|---|
| 프로필 전체 `importGroup` 최대값 + 1 | **채택** | `GetNextSeq`와 같은 방식이고 같은 이유("번호에 구멍이 나는 것은 괜찮다"). 저장할 필드가 안 는다 |
| 카운터를 따로 저장 | **기각** | 위와 결과가 같은데 상태가 하나 더 는다. 하나도 안 남으면 1부터 다시 쓰는 것은 무해하다 — 옛 번호를 참조하는 곳이 없다 |
| payload의 `group.id` 그대로 (현행) | **기각** | **배치 안의 번호**라 배치 둘이 동시에 기다리면 1번이 둘이 된다 |

**순서를 어떻게 나르나**

| | | |
|---|---|---|
| 선에 `order`, 액션에 `importOrder` | **채택** | 위 절 |
| 배열 차례에만 (현행) | **기각** | 암묵적이다. 버텨야 하는 구간은 짧지만(`PlanImport`의 `ipairs` 하나), 우선순위와 같은 급의 설계 정보를 암묵에 맡길 이유가 없다 |
| ~~`seq`라는 이름으로 그대로 보내기~~ | **사유가 거짓이었다** (2026-08-15) | 적혀 있던 사유: *"`BuildAction`이 블랙리스트라 아무도 안 시켜도 액션에 꽂히고, 받는 레이어 번호와 섞인다."* **섞일 구간이 없다** — `PlaceLast`가 `action.seq = nil`로 열고 임포트가 프로필에 쓰는 길은 그 함수뿐이다. 아래 세 번째 ★ 절에서 다시 연다 |
| `PlaceLast`를 넓혀 키 없어도 `seq` 발급 | **기각** | 내가 제안했다가 뒤집었다. "키가 없으면 번호도 없다"에는 이유가 적혀 있고, 임포트 전용 필드를 쓰면 그 불변식을 깰 이유가 없다 |

### 폴드는 안 한다

익스포트 창에 접히는 헤더가 있지만 그쪽은 **고르는 화면**이라 도드라진 게 맞고, 여기는 읽는
화면이다. 이 목록은 자식이 하나둘인 그룹이 대부분이라 한 줄짜리를 접는 컨트롤은 의식일 뿐이다.

그리고 이 헤더는 일부러 조용하게 만들어져 있다 — XML 주석이 "금색이 아니라 흰색"인 이유를 적어놨다
("머리글이 그 색이면 키 이름이 행보다 세게 읽혀서... 세야 할 것은 키가 아니라 그 밑에 몇 줄이
달렸는가다"). 폴드 화살표는 컨트롤이고 컨트롤은 눈을 끈다. 블리자드에서 빌려온 형태에
(`ClickBindingHeaderTemplate`) 저쪽에 없는 기능을 얹는 것이기도 하다.

**예외 하나만 열어둔다:** 위를 넣고 나서 맨 아래 "키 지정 안 됨" 덩어리가 실제로 커지면 — 액션을
잔뜩 만들어두고 나중에 거는 사람이 있다 — **그룹마다가 아니라 그 섹션 하나만** 접는 것은 값이
있다. 넣어보고 정한다.

## 똑같은 액션 지우기 — 임포트와 무관한 기능 (제안, 2026-08-14)

**[또 가져오기]가 만든 쓰레기를 치울 길.** `IMPORT_COMMIT_AGAIN`은 일부러 하나를 더 넣는다
("두 번째 누를 때는 반복이 아니다"). 그러면 치울 길도 있어야 하는데 지금은 한 행씩 지우는 것뿐이다.
임포트 밖에서도 값이 있다 — "복사할 곳..."이 같은 것을 만든다.

**판정은 `KEYS_TO_SAVE`를 deep equals로.**

- **필드 목록을 따로 적지 말 것.** 손으로 적으면 다음에 필드가 하나 늘 때 조용히 썩는다. 그
  필드만 다른 둘이 "동일"로 잡혀 지워지고, 아무 검사도 못 잡는다. `KEYS_TO_SAVE`가 "액션이란
  무엇인가"의 유일한 목록이고 `check:export-fields`가 이미 그걸 감시하므로, 거기서 파생시키면
  그 검사를 물려받는다.
- **deep**이어야 하는 이유: `checkedUnits`, `frameTypes`, `groups`, `forms`, `bonusbars`가
  테이블이다. `==`로는 정체성 비교라 영영 안 맞는다.
- 비교에서 빼는 것: **`seq`**(똑같은 둘은 번호만 다른 게 정상), **`imported`/`importGroup`**
  (아래).

**살아남는 쪽.**

- **받아들인 것 > 배지 달린 것.** "또 가져오기"의 흔한 결과가 "하나는 승인됨, 하나는 배지
  달린 똑같은 것"이라, `imported`를 비교에서 빼야 그 둘이 잡히고 이 기능이 제 일을 한다.
  비교에 넣으면 정작 있어야 할 이유가 안 잡힌다.
- 둘 다 같은 처지면 **`seq`가 작은 쪽**. 사용자가 ↑↓로 정해둔 자리를 지킨다.

**닫히는 쪽(fail closed)이라 안전하다.** 배열 차례가 다르면(같은 뜻이어도) 다르다고 본다.
`false`와 nil도 다르다고 본다 — 옵션을 껐다 켠 액션과 손댄 적 없는 액션은 뜻이 같아도 값이
다르다("옵션을 끄면 값은 남긴다"). 둘 다 **중복을 놓치는** 쪽으로 틀리므로 지워선 안 될 것을
지우지는 않는다. 정규화해서 더 잡으려 들지 말 것 — 필드마다 뜻을 판정하기 시작하면 위의
"파생" 이점이 사라진다.

**자리는 상설 버튼이 아니라 메뉴 항목.**

- 임포트와 무관하므로 스트립에 못 넣는다(배지가 없으면 사라진다).
- "중복이 있을 때만 뜨는 버튼"은 매 `Refresh`마다 전체를 훑어야 한다. 메뉴면 누를 때 한 번만
  센다.
- **범위는 프로필 전체**(뒷정리의 뜻이 그거고, 한 배치가 레이어 여럿에 흩어진다). 그래서 화면에
  안 보이는 것까지 지우고, **확인창이 개수와 함께 그걸 말해야 한다.** 리젝트와 달리 서랍이라는
  되돌릴 길이 없다.

**검증은 헤드리스.** 순수 비교자라 `tests/`가 딱 맞는 층이다.

### 왜 저장 포맷을 닮았나 — **그리는 코드를 재사용하려고** (소유자가 말해줌)

**이게 의도이고, 이 문서에 한 번도 안 적혀 있었다.** 적혀 있던 것은 전부 결과(왜 `seq`를 안 보내나,
왜 `id`를 따로 두나)였다. 의도가 없는 자리에서 뒤늦게 읽는 사람은 결과를 보고 이유를 지어내게 되고,
2026-08-15 대화에서 실제로 그렇게 여섯 개가 지어졌다.

페이로드가 프로필과 같은 모양이면 **프로필을 그리는 UI가 페이로드도 그린다.** 그래서 노리는 것:

- 임포트 창에서 그 문자열의 **레이어-그룹-액션 목록**을 보여주기
- 임포트 창 오른쪽에 **레이어 패널**(지금은 오버뷰에만 있다)을 세워, 가져오기 전에 레이어마다 뭐가
  들었는지 **미리 보기**

즉 저장을 닮아야 하는 이유는 우아함이 아니라 **번역 없이 먹히게 하려는 것**이다.

**이미 되는 부분이 많다.** 맨 액션 목록에 레이어 껍데기를 씌워 쓰는 것은 확립된 수법이다 —
`PlaceImportedActions`가 `setmetatable({}, { __index = ProfileLayerProto })`로 로드도 안 된 저장
목록을 다룬다. 그러면 `BuildSortedElements(layer, layerID)`가 그대로 먹는다. 액션 쪽도 `ACTION_FIELDS`가
`KEYS_TO_SAVE` 마이너스 둘이라 페이로드의 액션은 사실상 액션 테이블이고, `NameAndIconForAction`·
`GetBindingIssue`·`GetBindingInfoForAction`이 다 산다. 빨간 글씨는 미리보기에서 **오히려 있어야 하는**
값이다.

안 맞는 것은 **키 맵에서 나오는 값**(`IsUnreachableAction` 등)뿐인데, 그건 `simulated`/오프스펙이 이미
푼 문제다 — "지금 안 도는 세계의 액션을 그린다"는 기계가 서 있다.

**그리고 이 의도가 아래 항목의 결론을 바꾼다.** 저장과 갈라지는 자리가 **정확히 최상위 하나**이므로,
지금 모양은 그 목적에서 제일 먼 모양이다. 레이어 패널을 그리려면 페이로드를 다시 레이어로 버킷팅해야
한다 — 그리기 재사용을 위해 고른 shape인데 그리려면 shape을 바꿔야 하는 상태다.

**미리보기를 어디에 두느냐**(bring 대화상자 안이냐, 임포트 탭이 오버뷰처럼 두 열이 되느냐)는 아직
안 정했다. **포맷 결론은 그것과 무관하다** — 어느 쪽이든 레이어 최상위를 원한다.

### 최상위가 그룹인 것은 논증된 적이 없다 — 물려받은 것이다

이력을 따라가면 이렇다:

- **v1(08-13)**: 최상위 = 그룹, `layer`는 **그룹 필드**. 근거가 "그룹은 레이어를 안 넘는다"였다.
  그 전제 아래서는 그룹 ≡ (레이어, 키)라 **최상위를 뭘로 하든 정보량이 같았다.**
- **08-14**: 그 전제가 무너졌다(그룹이 레이어를 넘는다). `layer`를 액션으로 내렸다.
  **최상위는 손 안 댔다.**

그래서 지금 모양은 결정의 결과가 아니라 **전제가 사라진 구조에서 남은 것**이다. 이 문서 어디에도
"최상위가 그룹이어야 한다"를 세운 자리가 없다. 그리고 위의 의도(그리기 재사용)를 놓고 보면 **바꿀
적극적 이유까지 있다** — 없는 것이 근거가 아니라, 있는 근거가 반대쪽을 가리킨다.

### `key`가 그룹을 나른다 — 선언이 필요 없다

**같은 `key`면 같은 그룹.** `stripKeys`는 키를 떼는 것이 아니라 **합성 키로 바꾸는** 것이다.
그러면 `group.id`라는 개념 자체가 안 생긴다. (합성 키가 무엇이냐는 아래 "키를 빼고 보낼 때"에서
정한다 — **숫자**다.)

무너지는 것들:

- 최상위 `groups`와 `group.id`
- "그룹 정체성을 `key`에 얹지 않고 별도 id로 둔다"는 결정과 그 밑의 세 항목
- `stripKeys`가 "`key`는 떨구고 `id`는 남긴다"인 것 → 그냥 개명
- "묶인 적 없는 액션에는 `id`를 안 붙인다" → **키 없이 나간다**로 저절로 표현된다
- 액션의 `importGroup`(+`KEYS_TO_SAVE`, `NextImportGroupID`) → 번호가 키 이름 안에 있다
- `CollectImportGroupActions` / `CollectKeyGroupActions` → **하나로**. `CollectKeylessActionRows`와
  `BuildKeyboardElements`의 별도 키 없는 패스도 그냥 키 그룹 하나가 된다

**구조가 "한 그룹에 키 하나"를 강제한다는 점에서 지금보다 강하기도 하다** — 같은 키가 곧 같은
그룹이라 정의상 두 키를 가질 수 없다.

**대가는 "이 키가 진짜냐"를 아는 자리가 생긴다는 것.** 지금은 가짜 키가 프로필에 없어서 물을 일이
없었다. 그 자리 목록은 아래 "합성 키는 프로필에 그대로 산다"의 표에 있다.

*"가짜 키가 프로필로 흘러들어갈 일이 없다"*는 옛 항목은 이 안에 대한 반박이 아니었다 — **가짜 키를
저장하자**는 안에 대한 반박인데 그건 아무도 제안한 적이 없다. `PlanImport`이 이미 번역 계층이다
(`setstate` 이름→인덱스, macro 스냅샷→MACRO/MACROTEXT, 주소→`(scope, class, spec)`).

### 레이어는 이미 저장 주소 그대로다

`StoredActionsAt(scope, class, spec)`가 짚는 것이 정확히 선의 서술이다. 번역이 필요했던 것은 둘뿐:

1. **레이어 번호 1..11** — `LAYER_INFOS`가 2~6에 `PLAYER_CLASS`를 구워 넣는다. 주소가 아니라 **뷰
   인덱스**다. 저장은 애초에 이름으로 키를 잡는다
2. **character에서 guid를 뗀다** — `ImportAddress` 주석의 "The one real translation is the character"

`spec = 0`이 "그 직업 전체"인 것도, 상한이 `MAX_SPEC`인 것도 그대로 넘어간다. 중첩이 저장 모양을
따라가면 **서술 테이블이라는 물건이 사라지고 경로가 곧 주소가 된다.**

### `order`라는 이름의 근거가 거짓이다 ⚠ 코드에 박혀 있음

기각 사유가 *"`BuildAction`이 블랙리스트라 `seq`가 실리면 아무도 안 시켜도 액션에 꽂히고, 받는
레이어가 이미 나눠준 번호와 섞인다"*였다. **섞일 구간이 없다.**

`PlaceImportedActions`가 놓는 액션마다 `PlaceLast`를 부르고, 그 첫 줄이 `action.seq = nil`이다.
임포트가 프로필에 쓰는 길은 그 함수 하나뿐이고(주소가 없으면 아예 안 넣는다), `BuildAction`과
그 사이에 `seq`를 읽는 코드도 없다. 실려온 번호는 **착지하면서 지워진다.**

같은 거짓이 세 군데 있었다. **셋 다 고쳤다**(2026-08-15, 재부여 작업과 같이):

- `DebindStorage/Import.lua`의 `BuildAction` 주석 — *"...with nothing in the way."* 가로막는 것이
  바로 밑에 있다
- `DebindStorage/Export.lua`의 `ACTION_FIELDS` 주석 — `seq`를 안 보내는 이유로 같은 말을 든다
- 이 문서 "순서를 어떻게 나르나" 표의 `seq`라는 이름으로 그대로 보내기 행

가로막는 것의 이름이 바뀌었다. `PlaceLast`가 아니라 `PlaceImportedActions`가 도착 번호를 얹고
그 그룹을 재부여하는 것이고, 실려온 번호는 그 자리에서 덮인다.

**남는 진짜 이유는 하나뿐이다:** 비대칭. 내보내는 쪽 `ACTION_FIELDS`는 화이트리스트인데 받는 쪽
`BuildAction`은 블랙리스트다. 그걸 화이트리스트로 맞추면 이름으로 피해 갈 일이 없다.

### `seq`를 그대로 싣고, bring이 우리 공간으로 옮긴다

**선의 이름은 `seq`다.** `order`도 `importOrder`도 없다. 이름을 피할 이유였던 충돌이 없었으므로
(위 절), 선과 저장이 같은 이름을 쓰는 것이 "저장 포맷을 닮게"에도 맞다.

**그 값은 저장되는 값이 아니다.** 보낸 사람 레이어의 번호라 받는 레이어에서는 아무 뜻이 없다 —
가져온 액션들끼리, 같은 밴드 안에서만 차례를 말한다. 그래서 bring이 **우리 공간의 번호로 바꾼다.**

```
1. 들어온 액션 전부에  seq = MAGIC + 실려온 seq
2. 목적지 레이어에 넣는다
3. 닿은 (레이어, 키) 그룹을 재부여 → 1..n
```

1번이 하는 일이 **"어느 것이 새로 온 것인가"를 숫자의 성질로 만드는 것**이다. 그러고 나면 비교자도
재부여도 특별한 갈래가 필요 없다 — MAGIC이 지배하니 도착한 것들은 자기 밴드에서 기존 것들 뒤에
서고, 낮은 자리가 보낸 쪽 차례를 지킨다.

**MAGIC은 bring 안에서만 산다.** 3번이 걷어가므로 SavedVariables에도, 비교자의 지속 상태에도 안
닿는다. 두 번호 공간이 동시에 존재하는 순간이 없다.

- **내보낼 때 구워 보내지 않는다.** 상수를 알아야 하는 쪽은 정렬하는 쪽이고 그건 bring이다.
  선에 얹으면 받는 쪽 기계가 문자열에 실린다.
- **크기는 안 따진다.** 조건이 "받는 레이어의 번호보다 크다" 하나뿐이라, 나중에 더 큰 값으로
  바꿔도 옛 문자열이 안 깨진다. 그리고 재부여가 도는 이상 저장된 번호는 그룹 크기 이하다.
- **3번은 "그 그룹"이 아니라 닿은 그룹 전부**다. 한 배치는 레이어 여럿·키 여럿에 떨어진다. 하나
  빠뜨리면 그 그룹만 MAGIC을 든 채 남고, 그건 다음 편집까지 조용하다.

**그리고 `importOrder`가 설 자리가 없어진다.** 합성 키 덕에 도착한 액션에 언제나 키가 있고, 순서는
위 셋이 다 처리한다.

**`PlaceLast`와 `GetNextSeq`는 이 그림에 없다.** 그 동작을 제약으로 놓고 설계하면 안 된다고
적어놨던 자리인데, **2026-08-15에 실제로 없어졌다** → `devdocs/legacy/renumbering-a-key-group.md`.
배치는 번호를 발급하지 않고, 재부여가 1부터 매긴다.

`seq` 자체의 결함(밴드를 넘을 때 안 따라간다)은 **임포트와 무관한 기존 문제**라 따로 세웠고,
그쪽은 **만들었다**. 위 3번이 그쪽의 재부여와 같은 물건이라 여기서 새로 지을 것은 없다 —
`Profile.lua`의 `PlaceImportedActions`가 이미 "도착 번호 + 넣기 + 닿은 그룹 전부 재부여"다.
**남은 것은 1번뿐이다**: 도착 번호에 더할 값이 지금은 배치 안의 자리다. 이 절이 서서 선에
`seq`가 실리면 그 자리에 실려온 `seq`가 들어간다.

### 새 모양 — 저장 구조 그대로

**경로가 곧 주소다.** 서술 테이블이 없어지고 `StoredActionsAt(scope, class, spec)`이 짚는 그
모양이 그대로 선다.

> **실물과 읽는 쪽 주의사항은 이 문서 앞의 "전송 포맷 v1 — 실제로 나오는 모양"에 있다.**
> 여기 한 벌 더 두지 않는다 — 그 절이 임포트를 짜는 사람이 보는 자리이고, 지금 모양이 문서
> 뒤쪽에 숨어 있던 것이 이 절이 만든 문제였다. 아래는 그 모양을 **왜** 고르게 됐는지다.

`exportedAt`과 `name`은 이 결정에 안 딸린다 — 아래 "전송 포맷에 메타데이터가 없다"의 것이고,
아직 안 실린다.

### 키를 빼고 보낼 때 — 합성 키는 **숫자**다

`stripKeys`는 키를 **떼는** 것이 아니라 **바꾸는** 것이다.

```lua
key = 1     -- 숫자. 같은 값이면 한 묶음
key = "F"   -- 실키는 언제나 문자열
```

**타입이 판정이다.** `type(action.key) == "number"` 하나로 완전히 갈린다.

- **겹칠 수 없다.** 문자열 접두사(`export#1` 같은 것)는 *"안 겹칠 것 같다"*인데 이건
  **구조적으로 불가능**하다. 바인딩 문자열은 언제나 `[수식어-]키이름` 꼴의 문자열이다.
  (참고로 `#1`도 실제로는 안 겹친다 — 그런 이름의 키가 없고 클라이언트 `KEY_*` 표에 `#`가
  아예 없다. 그래도 "없더라"와 "있을 수 없다"는 다른 보증이다.)
- **빠뜨렸을 때 조용하지 않다.** 이쪽이 더 큰 값이다. 접두사 방식은 가드를 하나 빠뜨리면 화면에
  `export#1`이 **조용히** 뜬다. 숫자는 `CompareKeys`가 `숫자 < 문자열`에서 **던지고**,
  `GetBindingText(3)`도 `SetBindingClick(3, ...)`도 정상이 아니다. 이 저장소가 제일 무서워하는
  것이 조용히 죽는 키인데, 숫자는 그 실패를 시끄러운 쪽으로 옮긴다.
- `==` 비교는 안전하다 — `action.key == "F"`는 숫자일 때 그냥 false다. 조용히 틀릴 자리가 아니다.
- **원래 키가 없던 액션은 키 없이 나간다.** "묶인 적 없는 액션에는 그룹을 안 준다"가 규칙이 아니라
  **표현으로** 바뀐다 — 키가 없으면 아무와도 같은 키 그룹이 아니다.
- **받을 때 번호를 다시 매긴다.** `1`은 그 문자열 안에서만 유일하므로 배치 둘이 동시에 기다리면
  1번이 둘이 된다. 지금 `NextImportGroupID`가 하는 그 일을 같은 자리에서 하되 결과가
  `importGroup` 대신 **키 자체**로 간다. 훑는 범위도 그대로 저장 전체다 — 안 보이는 레이어의
  번호를 재사용하면 그 직업으로 접속하는 날 둘이 된다.

### 합성 키는 프로필에 그대로 산다 — 그래서 막을 자리가 생긴다

받는 쪽이 숫자 키를 **그대로 저장한다.** 그러면 `importGroup`도 `importOrder`도 필요 없다 —
키가 있으니 번호가 나오고, 왼쪽 열은 이미 키로 묶어 그린다.

대신 **"이 키가 진짜냐"를 묻는 자리**가 생긴다. 판정은 전부 `type(key) == "number"` 하나다.

| 자리 | 해야 할 일 |
|---|---|
| `CompareKeys` | **여기가 제일 먼저 터진다.** 왼쪽 열이 키를 정렬할 때 숫자와 문자열이 섞이고, 손 안 대면 Lua가 던진다. 숫자를 뒤로 몰면 지금 "키 없음" 더미가 앉던 자리가 된다 |
| `BuildKeyMap` | **숫자 키를 건너뛴다.** 지금은 배지가 막지만 **승인하면 배지가 떨어진다** — 그때 막을 것이 없으면 죽은 키가 된다. 배지와 **따로** 걸어야 한다 |
| `DebindKeyHeaderMixin:Init` | `키를 모름 #3`으로 그린다. `KEY_GROUP_UNKNOWN_KEY`의 서식이 **이미 `%d`**라 그대로 맞는다 |
| 행의 단축키 칸 · 툴팁 · 익스포트 창 | 같은 낱말로 |
| 재익스포트 | 숫자 키를 든 프로필을 다시 내보내면 그대로 나간다. **그게 맞다** — 아직 키를 안 정한 키 그룹이라는 사실이 보존된다 |

**승인은 여전히 배지를 뗀다.** 숫자 키를 든 채로 승인하면 그 키 그룹은 "받아들였지만 키는 아직"인
상태가 되는데, 그게 정직한 상태다 — 지금 키 없이 승인한 것과 같다.

### 배지 달린 액션은 안 내보낸다 (2026-08-15, 소유자 결정. **만들었다**)

> *"accept하지 않은 액션은 우리 액션이 아니니까 내보내지 않는다. 이 결정이 바뀌지는 않을 것 같다."*
>
> **판정은 `DebindStorage.IsExportable` 하나**이고 선을 만드는 쪽과 창이 **같은 함수를 부른다.**
> 레이어 머리글 개수도 [전부 선택] 총계도 고를 수 있는 행도 전부 창의 목록에서 나오므로, 그 목록과
> 실제로 나가는 것이 갈리면 창이 "12개"라 해놓고 9개를 보낸다. 두 자리에 같은 뜻을 따로 적는 대신
> 한 함수를 두 번 묻는 것이 그걸 **합의가 아니라 사실로** 만든다. 두 번 묻는 이유는 남아 있다 —
> **이 창은 메인 창에 수명이 안 묶여 있어서** 열어둔 채로 배지가 붙거나 떨어지고, 그때 창이 든
> 선택은 낡은 집합이다.
>
> 같은 편집에서 `BuildLayers`가 **`EnumerateAllProfileLayers`로** 훑게 바꿨다. 손으로 `1..11`을
> 도는 것과 게임에서는 같은 열한 개지만 `/debtest`에서는 아니다(격리가 그 열거자를 갈아끼운다).
> 같은 열한 개를 두 갈래로 훑는 것 자체가 한쪽이 바뀌기를 기다리는 균열이다.
>
> **검사는 두 층으로 갈린다.** `tests/export_spec.lua`가 넷 — 안 나가는 것, 골라도 안 나가는 것,
> 한 키가 반만 나가는 것, 배지 없는 숫자 키는 그대로 나가는 것. 그리고 **헤드리스가 원리적으로
> 못 보는 것**, 즉 창의 목록과 문자열이 서로 갈리는 것은 `/debtest`의
> `Export: the window's count is what the string carries`가 본다 — 창이 센 수와, 나온 문자열을
> **받는 쪽처럼 디코드해서** 센 수를 맞대본다.
>
> ⚠ **그 테스트는 패널을 얻어오되 열지는 않는다.** 격리된 런은 레이어 하나로 좁혀지고 그 레이어의
> id가 실재하는 열한 개 밖이라(`GetTestLayer`), 목록을 그리면 그 id가 `GetLayerLabel`을 지나
> 클라이언트에 없는 특성 이름을 묻는다. 세는 데에는 화면이 필요 없다.

**내보내기가 하는 말은 "이게 내 세팅이다"인데, 배지 달린 액션은 아직 내 것이 아니다.** 받아만
놓고 결정을 안 한 남의 것이고, 격리 중이라 아무 일도 안 하고 있다. 그걸 실어 보내면 **결정 안 된
것이 사람을 건너 퍼진다** — 받는 쪽에서 또 배지를 달고 서고, 그 사람도 판단할 근거가 없다.

- `GroupSelectedActions`(`Export.lua`)가 `action.imported`를 건너뛴다.
- **익스포트 창의 개수도 같은 집합이어야 한다.** `EXPORT_LAYER_COUNT` · `EXPORT_SELECT_ALL_COUNT` ·
  고를 수 있는 행. 화면이 세는 것과 실제로 나가는 것이 갈리면, 창은 "12개"라 해놓고 9개를 보낸다.
- **한 키가 반만 나갈 수 있다.** F에 승인된 둘과 배지 달린 하나가 있으면 둘만 나간다. 그게
  맞다 — 배지 달린 하나는 아직 그 세팅의 일부가 아니다.
- 전부 배지면 페이로드가 빈다. 그 자리는 `EXPORT_EMPTY`가 이미 있다.

**승인했지만 키를 안 준 것(숫자 키)은 나간다.** 배지가 없으면 내 것이고, "아직 키를 안 정한 키 그룹"이라는
사실까지 그대로 실린다(위 절). 두 규칙이 서로 안 부딪힌다.

  둘 다 이 함수를 지나므로 가드를 여기 하나 놓았다.
- `Ordering.CompareKeys` — 숫자를 실키 전부의 뒤로 몬다. 표가 예고한 자리이고, 실제로 제일 먼저 닿는다.
- `Misc.GetKeyDisplayText` — 행의 단축키 칸 · 툴팁 · 헤더 · 익스포트 창이 전부 이걸 지난다.
  낱말을 네 군데 따로 쓰면 같은 창이 같은 것을 두 이름으로 부르게 된다.

### 아직 안 정한 것

- **미리보기를 어디에 두나** — bring 대화상자 안이냐, 임포트 탭이 오버뷰처럼 두 열이 되느냐.
  포맷 결론과 무관하다.
- **레이어 안에서 키별로 뭉쳐 낼 것인가.** 상대 순서만 지키면 되므로 필요는 없지만, 미리보기가
  키 그룹 단위로 그린다면 뭉쳐 있는 편이 읽기 쉽다. 미리보기 모양이 정해질 때 같이 본다.

## 전송 포맷에 메타데이터가 없다 (2026-08-15, 제안)

문자열이 보낸 사람에 대해 나르는 것은 **`class` 하나**다(`AddBatch` 주석이 그렇게 적어놨다).
나머지는 전부 받는 쪽이 만든 값이다:

| 서랍이 든 것 | 어디서 왔나 |
|---|---|
| `received = time()` | **받은** 시각. 붙여넣은 순간 |
| `source` | **받는 사람이** 붙여넣기 창에 친 자유 텍스트(`IMPORT_PASTE_SOURCE`, "Who it came from (optional)") |
| `class` | 문자열이 나른 유일한 것 |

**자기 백업을 되돌릴 때 그게 다 쓸모없다.** `received`는 오늘이 찍히고, `source`는 무슨 문자열인지
기억해야 칠 수 있다. 정작 알고 싶은 것은 "이걸 언제 만들었나"와 "이게 뭐였나"다.

### 선에 넣을 것 — 내보낸 시각

**에폭 정수**로 싣는다. 타임존이 없는 값이라 그리는 쪽이 자기 로케일로 푼다.

**받은 시각(`received`)은 그대로 둔다.** 내보낸 시각이 그걸 대신하는 것이 아니다 — 둘이 다른
물음에 답한다("언제 만든 것인가" / "내가 언제 받았나").

### 이름 — 필드는 두되, 지금은 언제나 비운다 (2026-08-15, 소유자 결정)

**포맷에 이름 필드를 둔다. 익스포트는 지금 그걸 채우지 않는다.** 미룬 것은 값이 아니라 **입력
UI**다 — 문자열을 만들 때마다 뭘 적으라고 시키는 것이 번거롭고, 어떻게 채우게 할지가 아직 안 정해졌다.
임포트의 목적이 수고를 더는 것인데 내보내는 쪽에 수고를 새로 만들면 안 된다.

**그래서 나머지 항목의 기준이 여기서 선다: 사용자에게 아무것도 안 시키는 것만 지금 넣는다.**
내보낸 시각도 `class`도 개수도 전부 자동으로 아는 값이다.

나중에 정할 것은 "매번 적게 하기"가 아닌 모양이다 — 기본값을 채워두고 그대로 두면 넘어가게 하거나,
**받은 뒤 서랍에서** 이름을 붙이게 하거나. 뒤엣것은 선을 아예 안 건드린다.

**읽는 쪽은 지금부터 처리한다.** 우리 익스포트가 안 채운다고 그 필드가 안 온다는 뜻이 아니다 —
손으로 만든 문자열이 채울 수 있고, 다음 판의 우리 자신이 채운다.

⚠ **그러니 쓰는 사람이 없는 읽기 경로가 생긴다.** 실행된 적 없는 코드는 검증된 적 없는 코드다.
헤드리스 스펙이 이름을 넣은 페이로드를 직접 지어서 그 길을 밟게 해야 한다 — 익스포트를 통해서는
그 입력이 안 나오므로.

이름을 안 실으면 `source`가 여전히 유일한 사람 손 텍스트다 — **받는 사람이** 붙여넣을 때 치는 것
(`IMPORT_PASTE_SOURCE`, "Who it came from (optional)"). 그건 자기 백업에는 소용이 적다(무슨 문자열인지
기억해야 칠 수 있다).

**스키마 버전은 안 올린다.** 그 주석이 *"Bump when a field changes meaning, not when one is
added"*라고 적어놨고, 모르는 필드를 건너뛰는 독자는 추가를 혼자 견딘다.

### 서랍 행의 제목이 아무 말도 안 한다

`BatchTitle`(`WorkbenchUI.lua`)이 `source`가 비면 `IMPORT_BATCH_UNNAMED`, 즉 **"Received string"**을
쓴다. 받은 문자열의 목록에서 "받은 문자열"은 아무것도 안 가른다 — 셋이 나란히 서면 셋 다 같은
제목이다.

**이름은 지금 언제나 비므로 이 자리를 못 메운다.** 그러니 제목은 **자동으로 아는 것**으로 세워야
한다. 문자열이 언제나 나르는 것은 `class`이고 여기에 내보낸 시각이 더해진다 — 둘 다 지금은 툴팁에만
있거나(`IMPORT_BATCH_FROM_CLASS`) 아직 없다.

차례는 **이름 → `source` → 자동으로 지은 것 → 총칭**이 될 것 같은데, 앞의 둘이 대개 비어 있으므로
**실질적인 제목은 셋째**다. 낱말은 그릴 때 정한다.

### 툴팁이 부실하다

지금 행 툴팁이 내는 것은 셋이다: 제목, 개수, 보낸 쪽 직업. **그중 제목과 개수는 행이 이미 들고
있다** — 툴팁이 실제로 더해주는 것은 직업 한 줄뿐이다.

메타데이터가 늘면 그것들이 갈 자리가 여기다. 행은 좁고(제목·개수·나이) 툴팁은 **스스로 불러서
읽는 글이라 길어도 된다.** 들어갈 것: 내보낸 시각, 받은 시각, 이름과 `source`(둘 다 있으면 둘 다),
보낸 쪽 직업, 개수, 키 유무(`hasKeys`), 이미 가져왔는지. (만료·핀은 없어졌다.)

행에 이미 있는 것을 툴팁이 되풀이할지는 그때 정한다 — 지금은 되풀이하고 있고, 그래서 툴팁을
열어도 새로 아는 것이 한 줄뿐이다.

### ⚠ 이름은 남이 준 텍스트를 화면에 그리는 첫 자리다

지금 서랍이 그리는 `source`는 **받는 사람이 직접 친 것**이라 이 문제가 없었다. 보낸 사람이 적은
이름은 다르다 — 붙여넣기가 남이 준 입력이라는 이 포맷의 전제가 여기서 화면까지 온다.

**길이 상한과 이스케이프를 걸러야 한다.** 와우 마크업(`|c`, `|H`, `|T`, `|n`)이 그대로 들어가면
색을 바꾸고 아이템 링크를 흉내내고 텍스처를 박고 줄을 늘린다. 서랍 한 행이 목록을 덮을 수 있다.

## ★ 애드온 경계 — UI는 Debind로 돌아온다 (2026-08-15, 소유자 결정)

> 상태: **옮겼다** (2026-08-15). 이름도 같은 날 `DebindStorage` → **`DebindStorage`**로 바꿨다.
> **화면으로는 아직 안 봤다** — 로그인 로드 순서와 패널 배달을 통째로 바꾼 변경이라 `/reload`가
> 유일한 확인이다.

```
DebindStorage   DebindStorageVars · Libs · Export.lua · Import.lua · Workbench.lua
Debind          나머지 전부 — ShareUI.* 와 WorkbenchUI.* 가 여기로 왔다
```

**실제로 한 것**

- 패널 둘이 `DebindFrame`의 XML 자식이 됐다(`parent=` + `parentKey=`). `PANELS`의
  `addon`/`panelGlobal` 갈래와 `TakeDelivery`(리페어런팅)가 통째로 없어지고 셋 다 `panelKey`다.
- `needsStore`가 그 자리를 대신한다. `ResolvePanel`이 그 탭에서만 `EnsureStore()`를 부르고,
  실패하면 `MissingPanel`이 선다 — **패널이 없는 게 아니라 읽을 것이 없는 것**이라 그 문장도
  같이 고쳤다(`PANEL_ADDON_MISSING`).
- 모델 손잡이는 **`DebindPrivate.Store`**. 저쪽 첫 파일이 `LoadAddOn` 창 안에서 자기 테이블을
  걸어주고, UI는 **호출 시점에** 읽는다(파일 스코프에서 잡으면 영원히 nil이다 — UI는 로그인에
  읽히고 저쪽은 아니다). 역할 이름이라 폴더 개명에 호출부가 안 움직였다.
- **`preferredWidth`가 `GetWidth()` 읽기에서 XML `KeyValue`로 바뀌었다.** 이건 안 하면 조용히
  깨지는 자리였다: 패널이 이제 처음부터 호스트에 4면 고정이라 `OnLoad`의 `GetWidth()`가 470이
  아니라 창 폭을 답한다. 탭마다 폭이 달라지는 기능이 소리 없이 죽었을 것이다.
- 프레임·믹스인 이름에서 `Share`를 뺐다(`DebindExportPanel`, `DebindCopyFrame`, …).

### 규칙

**UI는 포기할 수 없는 축이고, 분리는 리소스 절약이다. 그 정도는 감내한다.**

패널 둘이 로그인에 로드되는 값(Lua 1,191줄 + XML 665줄)을 치른다. 최적화가 양보할 수 없는 축을
제약하게 두지 않는다는 뜻이고, 그래서 이 결정은 재본 뒤에 바뀌는 종류가 아니다.

### 왜 지금 옮기나 — 경계가 설계를 조용히 비튼다

**작업대가 이미 이 실패로 죽었다.** 저쪽 폴더에 있으니 오버뷰에 손을 안 뻗고 자기 기능을 키웠고,
그러다 기본 UI를 넘어서는 역전이 나서 접었다(위 "임포트 — 작업대를 접었다").

경계를 남겨두면 같은 일이 또 난다. 행을 그리는 **두 번째 방법**이 생기고, 그것이 "재사용을 안 한
이유"로 굳는다 — 아직 값도 안 재본 경계를 지키느라. 특히 미리보기가 그 자리다: 임포트 창이
Debind의 행 템플릿과 `BuildSortedElements`로 그려야 하는데, 폴더가 갈려 있으면 그 대신 자기
템플릿을 짜게 된다.

> **아직 안 한 설계의 입력으로 모듈 경계를 쓰지 않는다.** 경계는 설계가 끝난 뒤에 값을 재서 긋는다.

이 저장소에서 두 번째 나온 자리라 원칙으로 적어둔다.

### 선이 왜 하필 거기인가 — 두 번 쟀고 같은 답이 나왔다

**로캘 문자열**

```
Export.lua / Import.lua / Workbench.lua    0 / 0 / 0
ShareUI.lua / WorkbenchUI.lua              13 / 33
```

**`DebindPrivate` 참조**

```
Workbench.lua   0개                        ← 서랍은 완전히 자립
Import.lua      4개   전부 모델
Export.lua      10개  전부 모델
ShareUI.lua     DebindUI · L · DisplayMessage (+ CompareKeys · GetProfileLayer)
WorkbenchUI.lua DebindUI · L · DisplayMessage
```

`DebindUI`도 `L`도 `DisplayMessage`도 **옮기는 파일 둘에만** 있다. 남는 쪽은 모델만 짚는다.
내가 그은 선이 아니라 코드가 이미 그어놓은 선이다.

`Export.lua`가 짚는 열 중 넷은 **순서 기계**다(`CompareActionOrder`,
`EnumerateAllProfileLayers`, `GetBindingInfoForAction`, `IsConditionalAction`). *"순서를 말하는
자리가 하나뿐이어야 한다"*가 애드온 경계를 넘어 뻗은 자리라 맞는 의존인데, **Debind의 순서 내부가
곧 DebindStorage의 API**라는 뜻이기도 하다 — `devdocs/legacy/renumbering-a-key-group.md`를 하면 `Export.lua`가
같이 움직인다.

### 남는 쪽은 이 물음과 무관하다

`DebindStorageVars`가 저쪽에 있는 이유는 개념이 아니라 **플랫폼 사실**이다: SavedVariables는 애드온이
로드될 때 통째로 읽히고 서랍은 계속 자란다. LoD가 그걸 미루는 유일한 수단이고, 취향이 아니다.
Libs(208K, 우리 코드보다 크다)와 선 코드는 그 데이터 없이는 쓸 일이 없으니 같이 남는다.

**애드온 경계와 코드 경계는 다른 종류의 근거로 서 있고, 그래도 된다.** 지금 잘못된 것은 애드온
경계가 코드 경계를 정해버린 것이다.

### 마감 — 첫 배포

**`DebindStorage`는 한 번도 배포된 적이 없다.** `v3.1.6`(2026-08-13) 트리에 그 폴더가 없다.
`DebindStorageVars`를 가진 사용자가 세상에 없으므로 **폴더를 지금 어떻게 째든 마이그레이션이 없다.**

첫 배포 순간 닫힌다. 그 뒤엔 옛 파일을 읽을 셸을 남겨야 하고, 그건 `Debounce/`가 왜 아직 저장소에
있는지와 같은 이야기가 된다(`.pkgmeta`의 `move-folders`가 SavedVariables 파일 이름을 정한다).

### 옮길 때 딸려 오는 것

- **`PANELS`의 `addon`/`panelGlobal` 갈래가 `panelKey`로** 바뀐다. 패널이 Debind의 XML 자식이 된다.
- **`LoadAddOn`이 "패널을 얻기 전"에서 "데이터를 만지기 전"으로** 옮겨간다. 패널이 그릴 때 한 번.
- **`PANEL_ADDON_MISSING`의 뜻이 달라진다.** 지금은 "탭의 패널을 못 얻었다"인데, 그 뒤로는 패널은
  늘 있고 **서랍이 없는** 것이다. 문장을 같은 편집에서 훑을 것.
- **로캘은 한 줄도 안 움직인다.** 이미 전부 `Debind/Locales`에 있고, 이 이동이 그걸 변칙에서 규칙으로
  바꾼다.

### 폴더 이름 — `DebindStorage` (2026-08-15, 소유자가 후보를 냈고 골랐다)

`DebindStorage`는 **기능 이름**인데 남는 것이 하는 일은 "문자열과 서랍"이었다. 한 번도 배포된 적이
없어 개명이 공짜였고(`.pkgmeta` 주석), 같은 날 같이 했다.

**떨어져 나간 후보들과 이유가 근거다.**

- **`DebindCodes`** — 처음 낸 것. *"백업은 코드 밖으로 나간다"*는 내 반론이 틀렸다는 것을 문서가
  말해줬다(백업은 익스포트한 문자열을 서랍에 한 줄로 넣는 것이라 그냥 또 하나의 코드다). 그래도
  낱말(문자열/코드)이 아직 안 정해져서 이름이 그 결정에 매달리게 된다.
- **`DebindVault`** — 소유자: *"볼트는 와우에서 사람을 희망고문하는 단어인데"*. 클라이언트가 쓰는
  낱말이냐가 아니라 **플레이어 귀에 뭘로 들리느냐**가 기각 사유다. 위대한 금고.
- **`Keep` / `Silo` / `Archive`** — 소유자가 낸 셋. `Keep`은 클라이언트에서 던전·지역 이름이고
  동사로도 읽힌다. `Silo`·`Archive`는 baggage가 없지만 **셋 다 장소 은유**다.
- **틀을 바꾼 것도 소유자다** — *"Debind Migration이란 애드온을 쓰고 있지. 같은 톤으로 생각해봐"*.
  동반 애드온의 `## Title`은 은유가 아니라 **일을 그대로 말하는 평범한 명사**다(Debind Migration,
  Debind Clique Fake). 그 톤에서 이 애드온의 일은 보관이고, `Storage`는 클라이언트가 그 뜻으로
  쓰는 낱말이다(하우징 **창고** — 소유하고 있지만 지금 배치돼 있지 않은 것이 있는 곳). 우리가
  들고 있는 것도 그렇다.

**폴더 이름과 `## Title`은 별개다.** `Debounce/`가 그 산 증거다 — 폴더는 SavedVariables 때문에
못 바꾸고 Title만 `Debind Migration`이다. 여기서는 둘 다 자유로워서 같이 갔다.
